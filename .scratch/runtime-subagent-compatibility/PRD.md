# 方案启动工具兼容性修复计划

## 目标与边界

恢复 Stage 2 的模型设置检查与受治理的隔离子 Agent 派发，保留一个
context-isolated 子 Agent 负责方案的职责划分。沿用已经确认的业务需求与
检查点，不修改业务代码、原需求、讨论状态或工作树状态。

修复涉及 workflow-pipeline 的设置解析与阶段协议、subagent-governance
插件源码，以及两者的实际安装版本。插件源码位置与安装命令需先核实；
缓存目录不是源码修改目标。不借此重构其他工作流。

## 已验证事实

- 当前诊断任务运行安装版及仓库版 `thread_settings.py resolve --current`
  均返回 `paginated rollout history is ambiguous`；两份脚本内容相同。
- 当前任务的 canonical rollout 与一个带后缀分页文件均声明
  `history_mode: paginated`、`history_base: null`。解析器要求唯一根及唯一叶，
  因此拒绝该输入。这是当前任务的复现，不等于已读取原报错任务的完整现场。
- 安装中的治理插件生成并校验 `task_name`、`fork_turns`；当前公开的
  `spawn_agent` 参数包含 `fork_context`，不包含上述两个字段，返回身份为
  `agent_id`。这里只做了源码与接口对照，尚未进行真实派发验证。
- `.agents/skills` 注册路径实际指向 `.cc-switch/skills`；安装版方案协议仍
  规定旧派发参数，仓库版已经将原生参数责任交给 adapter。

## 实施顺序

### 1. 核实契约并固定复现

读取当前可用的运行时文档、接口定义与必要的本机实现证据，确认：

- 是否存在可绑定当前任务与当前 turn 的权威模型及推理强度来源。
- 多个 `history_base: null` 文件的含义，以及活动分页的权威识别方式。
- 原生派发、通信、终态、关闭接口及 Hook 实际可见的工具名称和输入输出。
- 治理插件的源码仓库、当前安装来源，以及项目现有同步安装方式。

仅提取脱敏结构作为 fixture，不复制会话正文或真实身份。把原报错形态写成
可重复的聚焦检查，并记录各契约的证据与适用版本。

出口：有证据支持设置来源选择及接口映射。若仍无法确定活动分页，不猜测
最新文件、不按时间排序选取、不删除历史文件；记录缺失契约，再选择可证明
正确的替代来源。显式用户模型覆盖可以作为既有恢复路径，但不能冒充继承。

### 2. 修复模型设置来源和校验

主要位置：`skills/guided-implementation/scripts/thread_settings.py`、
`test_thread_settings.py` 与 `references/thread-settings-protocol.md`。

根据第 1 步证据选择最小实现：优先采用实际可用的权威设置来源；否则按已验证
分页契约读取。不要预先假定存在可调用的设置 API。

保留当前线程、谱系、文件身份和安全打开检查；真正歧义仍拒绝。维持
`resolve` 与 `verify` 的一致语义，设置变化仍使旧确认失效。
若来源或回执契约改变，明确是否升级协议，并同步所有直接消费者。

测试先覆盖：当前双 null 根形态的正确判定、已有合法分页链、真正无法判定的
多候选、身份冲突、根任务与子任务、设置未变与已变。正确判定必须来自第 1 步
证据，不能仅为了让 fixture 通过而接受所有双根输入。

### 3. 在治理插件源码中适配当前接口

统一调整派发参数生成、Hook 识别与参数校验、返回身份绑定；核对并按需修复
后续通信、终态归一化和关闭处理。

- 原生参数不传 `task_name`；治理身份保留在治理记录和必要的消息封装中。
- 隔离上下文映射到 `fork_context: false`。
- 使用实际返回的 `agent_id` 绑定唯一子 Agent，不通过名字或顺序推断身份。
- 当前接口默认继承模型与推理强度；没有用户明确覆盖时遵循接口要求省略
  `model`。协调阶段的设置披露、确认与治理校验，不能把解析出的继承值
  无条件变成显式模型覆盖。
- 保留派发前后契约一致性；创建结果不确定时不自动重派。

测试覆盖正确参数、篡改参数拒绝、重复回调、身份绑定、创建失败与结果不明、
消息发送和终态关闭。仅在证据要求时支持多个接口版本，不建立无依据的通用层。

项目阶段协议只描述目标、隔离要求、冻结来源、设置策略和交付证据；插件负责
原生接口细节，不把插件私有 schema 再复制回 skill。

### 4. 验证、同步安装并恢复入口

先运行设置解析聚焦测试、治理插件相关测试与项目必要的契约检查；按变更范围
运行仓库验证。复核通过后，用已有安装流程同步同源 workflow skills 和插件，
核对实际注册路径、来源版本与内容哈希，保存可回退的原版本信息。

安装后先做一次受治理的只读隔离子 Agent smoke test：设置检查、派发、精确
身份绑定、子任务回执、父任务接收、关闭和账本收尾。真实派发前按当时生效的
治理 skill 和 Hook 权威 session/entrypoint 执行，不能复用本文或旧任务身份。

再以隔离 fixture 验证 Stage 2 能通过启动门槛，接受冻结需求并报告 started；
测试不发布业务方案、不推进真实讨论状态。最后检查原任务的需求和检查点仍
可用，遵循原任务已有授权与确认状态恢复，避免重复完成过的步骤。

## 验收与回滚

- 原报错形态在有权威证据的情况下正确解析；真正不确定的设置仍失败关闭。
- 当前原生接口接受治理层参数，Hook 仍能拒绝契约偏移并绑定精确身份。
- 子 Agent 上下文隔离、模型继承或显式覆盖符合当前接口与用户选择。
- 聚焦测试及必要仓库检查通过；安装副本可追溯到已验证源码。
- 真实 smoke test 完成全生命周期，隔离 Stage 2 fixture 通过启动门槛。
- 不仅凭单元测试或“未再报错”宣称原工作流已恢复。

同步失败时恢复本次更改的安装版本组合；若已创建测试子 Agent，先核对真实
身份并按治理协议收尾，不清空账本或盲目重派。回滚后明确报告功能仍不可用，
不通过关闭校验或改由主任务代写方案掩盖故障。
