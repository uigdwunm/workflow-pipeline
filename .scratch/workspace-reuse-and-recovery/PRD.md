# 工作区复用与范围内恢复改造方案

Status: ready-for-agent
Lifecycle: completed
Review: 用户已确认方案并授权实施；实现与验收记录见 IMPLEMENTATION.md
Source: 当前对话已确认的四项改造范围

## 目标与明确不改项

让流程验证“已具备独立工作空间、明确需求版本、唯一执行者和正确交付”，而不是要求重复创建空间或让用户选择内部工具。保留阶段职责、用户业务决策和真实副作用授权。

用户明确要求保持以下两项交互设计：

1. 第 1 阶段默认准备专用对话，用户拒绝后复用当前对话；原确认和拒绝记忆规则不变。
2. 普通子话题／续接对话首轮仅接收交接，后续轮次才开始讨论；原首轮和轮次门槛不变。

话题拆分确认、方案独立上下文、阶段推进的逐阶段／连续模式、需求或权限扩张确认也不在本次调整范围。不增加新调度器、工作区注册库或第二套恢复账本。不自动迁移正在运行的旧流程，不修改本机安装包。

## D1：统一选择、验证和绑定工作区

Stage 2、独立 Stage 3、独立 Stage 4 共用一条选择规则：

1. 已有本次流程绑定时，验证并复用原绑定。无效绑定进入原恢复路径，不通过新建空间掩盖问题。
2. 没有绑定时，先检查当前对话所在的独立 Git worktree，再检查宿主已关联的空闲工作区。判断依据包括 Git 身份、分支／基线、现有文件以及宿主的任务与使用情况；“目录存在”或“Git 干净”均不能单独证明空闲。
3. 可用空间直接接纳。需要新空间时优先调用宿主托管创建能力，明确传入本次目标提交，不依赖工具默认的远端分支。只有宿主能力不可用且规则允许，或用户明确指定脚本方式时，才使用既有脚本创建。
4. 选择、创建结果、验证结果写入原 Controller checkpoint。创建结果不确定时核对原操作及关联资源，不能换名字再次创建。

新增只读 `bind-worktree` 接纳入口，与 `start-worktree` 共享绑定校验。Git 脚本不调用 Codex UI 工具；Controller 调宿主工具取得真实结果，脚本验证实际 Git 状态。宿主证据通过原 checkpoint 保存，不能靠调用者填 `exclusive=true` 自证归属。

初次接纳条件：同一 Git common directory、注册有效、独立于目标 checkout、可明确记录的基线和目标、没有其他活跃写者或归属不明的改动。托管工具返回 detached HEAD 时，在已确认可独占使用且状态合适的工作区创建本次分支后绑定；不重置 HEAD 或复用同名未知分支。

已有本任务提交可以保留，但必须识别其来源、包含在本次范围核对中；不能把当前 HEAD 随意当新基线，从而隐藏已产生的改动。无关未合并提交不能随本次交付进入目标。首次接纳前有未提交内容时，先区分任务内已授权成果与其他工作；原流程重试继续使用原绑定及恢复证据，不要求通过清空目录恢复资格。

工作区只是因为另一个任务正在使用而不合适时，可保留它并选择其他空间。若当前任务成果是否需要带入新空间无法判定，才询问具体归属问题；不让用户决定“用脚本还是用工具”。

## D2：记录工作区来源，并按来源结束流程

扩展 Worktree Binding，保留原 Git 身份，增加受原 Controller 记录约束的生命周期信息：

- 来源：本次流程创建／复用既有空间。
- 管理方式：宿主管理／普通 Git worktree。
- 完成处置：保留／删除本次临时资源。
- 证据引用：原宿主工作区身份或脚本创建回执，以及选择决定。不得仅凭字段声明获得删除权限。

默认处置矩阵：

| 空间 | 完成后的处置 |
| --- | --- |
| 复用当前或既有工作区 | 保留工作区和分支 |
| 本次通过宿主创建的托管工作区 | 保留工作区和分支，可供后续使用 |
| 本次脚本创建且明确属于流程的临时工作区 | 按原非强制删除规则清理 |

保留路径不执行 `git worktree remove`，也不把自动归档作为必须动作。以后用户要求归档托管工作区时，走宿主归档工具及其独立条件。

`complete-worktree` 先完成原候选校验和目标合并，再根据绑定执行处置。保留路径验证同一工作区及分支仍存在、最终候选已包含于目标，记录 `retained`；不为保留而重置分支。删除路径记录既有实际删除事实。上层完成条件改为“交付成功且约定处置已核验”，不再固定要求两个 removed 布尔值为真。

将处置结果贯穿 `supervision_protocol`、`workflow_progress`、`workflow_control`、`workflow_control_git`、`stage_handoff`、runner 结果及阶段 footer。恢复时保留与删除是不同路径：已合并未完成处置只恢复原处置，不重新发布；不能在恢复时将 retain 改成 delete。路径替换、分支漂移、未决写者继续阻断破坏性动作。

## D3：需求冻结与空间创建解耦

保留“需求必须有真实提交、内容摘要、唯一文档和目标交付证明”的要求，调整顺序依赖：

1. 已有冻结需求和有效交付时直接核验，不重新生成或提交。
2. 从当前对话进入 Stage 2 时，先确定需求文档的实际准备 checkout 和方案目标。当前独立空间合适时，可在该空间写入并单独提交本次需求；当前在目标 checkout 时沿用原路径。
3. 来源不在目标历史时，扩展现有 `requirement_delivery` 的有界文档交付能力，仅允许 Stage 2 当前对话快照及原 Controller 授权；复用既有逐路径、摘要、目标状态和不确定结果核对，不合并来源分支的其他历史。Stage 1 和讨论附着文档的归属及交付权限不变。
4. 在方案工作区中核验同一文档。只有受控需求提交的来源分支与目标交付分支分叉时，可在停写、干净状态下整合目标，核验差异仅限已授权内容；真实内容冲突交给原决策路径。
5. 冻结需求及目标交付核验完成后，再封存方案工作区基线并派发设计者。保留源提交与目标交付提交的区别，规划 diff 不把需求提交误算为设计者新增范围。

`entry_prepare` 应区分实际执行 checkout、需求来源 checkout 和交付目标，不能为通过 cwd 检查伪造宿主项目身份。`requirement_prepare` 保留真实来源，`requirement_delivery` 负责有限目标交付，`stage_handoff` 配对检查两者。适用路径没有缺少权限或实质冲突时，不新增用户确认。

## D4：方案子 Agent 的范围内受控恢复

优先续用原方案子 Agent。只有原执行者确实无法续用时，才进入替换：

1. 由原宿主核对旧执行者及其相关写者全部停止，未决创建／调用已结清。超时、idle 或终态消息本身都不构成充分证据。
2. 固定当前工作区、需求、授权、规划路径、已提交及未提交成果快照；保留历史完成和发布事实。
3. Controller 在原授权内记录恢复决定。目标、权限、需求和结果均不变时，不再要求终端用户批准“换一个 Agent”。
4. 在原 checkpoint 保存唯一恢复派发意图，记录实际新 Agent 身份。新执行者先只读核验快照和剩余工作，Controller 验证后激活写权。
5. 新旧身份、调用及成果证据保留可追溯关系；迟到的旧结果不能取得当前写权或覆盖新结果。创建结果未知时查询原意图，不重复派发。

复用 Stage 3 恢复已有的宿主停止证据、Git 快照和意图／回执机制，为 Stage 2 增加明确的角色与规划状态分支；不假造 Dispatcher 或 Execution Agent 记录，也不把 Stage 3 专用路径数组硬套给设计者。

方案已发布但回执未收齐时先恢复发布和验收，不启动新设计者重做方案。用户取消／暂停、宿主证据丢失、成果归属不明、需求或权限变化仍走各自现有门槛。按既有恢复历史上限约束重试，不能无限换 Agent。

每个切片同步必要协议、测试、规则和生成包；不能先放开复用、以后再补清理保护。修改 `src/` 后通过构建更新 `skills/`，不手改生成物。两个明确不改的交互设计列为回归保护项，不对其实施流程简化。

仓库另有尚未实施的 `.scratch/stage-scope-finalization/PRD.md`，与本方案共享 control/progress/handoff/runner 及版本键。本方案不依赖其未实现能力；实施前按真实合入状态确定基线和兼容版本，若同时实施需串行整合共享文件，避免两份方案各自占用同一新版本号。双方不修改对方的需求或已确认决定。

绑定／完成证据、Stage-2 恢复及需求交付资格发生语义变化，需要升级相关兼容键及持久结构版本，五包按同一组合验证。旧运行继续固定旧包，新包不自动解释缺少生命周期字段的旧绑定为可删除资源。本次不为旧运行新增迁移特例，不覆盖当前安装目录。

## 验收计划

1. 已有有效绑定、当前独立空间、已关联空闲空间分别走复用，均不调用创建接口；忙碌或不合格空间保留，按规则另选。
2. 宿主创建明确使用目标提交；detached 返回可按规则建立分支；未知创建结果不会产生第二个空间。主目录、错误仓库、错误分支或越界历史不得被接纳。
3. Stage 2 → 3 → 4 始终继承同一绑定；独立 Stage 3/4 也遵守相同选择和处置规则。无效继承不能降级为新建。
4. 复用和宿主管理空间在成功合并后保留，并能完成流程；脚本临时空间才删除。旧绑定缺字段、伪造来源、替换目录和漂移分支不能取得清理权限。
5. 在合并前、合并后、处置前后中断，均恢复原事务；不存在重复合并或把保留资源误删的路径。
6. 需求在目标或独立空间冻结都能进入方案；已有冻结不重复写入；有界交付不带入无关历史，保留其他暂存和未暂存改动，冲突／未知结果不盲重试。
7. Stage 2 原 Agent 可恢复时不替换；确认无法恢复后，在原范围内无需用户再批准；旧写者活跃、未决调用、错误快照、暂停／取消均阻断激活。旧结果迟到不覆盖新状态。
8. 已发布方案不因 Agent 丢失再次发布；需求／权限扩张仍要求原用户决策。
9. 两项用户保护的交互设计保持原行为，并检查其相关源码／规则未发生语义变化。
10. 使用真实临时 Git 仓库验证提交、分叉、保留和删除；宿主替身只覆盖宿主边界。执行仓库 `./scripts/validate.sh`，另列 Desktop 托管空间和真实原生 Agent 恢复现场验收，不能用替身通过冒充现场通过。

方案形成时仅核对源码；随后用户明确授权实施。实施结果、验证证据及未验证项由同目录 IMPLEMENTATION.md 记录。本方案不授权本机安装或旧运行迁移。
