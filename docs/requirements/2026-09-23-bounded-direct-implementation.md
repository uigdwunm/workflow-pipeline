# 局部修改的有限直接实现例外

Status: frozen
Source: 当前对话中用户确认的需求

## 目标

降低范围明确、影响局部任务的 Stage 3 协调成本，同时避免 Agent 将大多数任务自行判为简单任务。默认仍采用现有 Controller → Implementation Dispatcher → Execution Agent 流程；直接实现只能作为有依据的有限例外。

## 已确认行为

1. 仅当以下条件全部满足时，才允许由同一个 Implementation Dispatcher 直接编码、测试、整合并提交，省去额外 Execution Agent 的派发与交付验收：行为和验收条件明确且无待定设计；修改局限于一个职责且不改变跨模块接口、数据格式、权限或流程状态；能用明确的针对性检查验证、不依赖多方集成；已定位修改位置、不需要边探索边扩大范围。
2. 状态机、并发、恢复、数据迁移和公共接口变更必须保留完整流程；条件未知或证据不足同样使用完整流程。文件数和行数不作为准入硬阈值，单文件修改也可能属于高风险。
3. 开始时简短披露例外适用依据。不能由实现者用“很简单”等自我描述绕过默认流程。
4. 执行中发现条件不再满足，停止扩大修改范围并转回完整流程。保留已有工作与准确身份，不借转换机会重做未知副作用。
5. 独立审查、单一 Flow Worktree、候选绑定、必要验证和 Stage 4 归档保持不变；直接实现不等于主 Controller 自己修改代码，也不免除审查和验收。
6. 复用现有 Stage 3 流程和恢复机制，不新增独立简单任务协议、独立 runner 或另一套持久化状态机。

## 方案需要解决

在上述已确认范围内设计：谁作出并记录准入判断、证据如何随现有交接传递、执行及候选校验如何区分真实直接实现与伪造执行交付、发现越界后已有修改怎样转交完整流程、旧记录及固定包如何处理，以及面向真实生产调用链的测试。它们是本阶段的技术设计事项，不是已选定的实现。

## 验收要求

- 缺省、未知、任一条件不满足或触发排除项时，均不能进入直接实现。
- 有充分证据的局部修改可免去 Execution Agent，保留同一 Dispatcher、独立审查、同候选验证和归档。
- 单文件 checkpoint 恢复或并发修改不得因规模小而进入例外。
- 直接执行发现越界后不能继续扩大修改；已有改动可核查地进入原完整流程，未验证部分不能自动被接受。
- 完整流程的文件归属、停止屏障、未知启动/发布不重放、决策消费和用户已有改动保护保持有效。

## 非目标

不改变 Stage 0–2 的需求和方案流程；不精简历史快照、回执恢复、模型选择或包预检；不调整独立审查轴和最终发布清理契约；不授权本次实现、安装、部署或远程写入。
