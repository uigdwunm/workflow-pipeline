# Ticket 下函数级执行计划与实现期间内部修订

Status: frozen
Source: 当前对话中用户已明确确认的需求
Planning target: workflow-pipeline / main
Flow mode: stepwise

## 目标

保留 Ticket 作为大方案拆出的、小型独立可验收模块，在 Ticket 下增加具体执行计划。把执行时仍需临场补充的局部设计提前到 2方案，明确函数级能力和实现思路，同时允许实现过程中有依据的内部调整。

## 已确认要求

1. 层级为方案 → Ticket → 执行计划。Ticket 保留交付行为、验收条件和前置依赖；其下计划细到具体函数，描述函数应实现的能力、大致实现过程、必要依赖和实施顺序。
2. 执行计划是 2方案 的正式组成部分，须在进入 3实现 前完成；本次设计要明确其载体、身份、与 Ticket/Spec 的对应关系及就绪条件。
3. 计划包含必要的关键输入输出、失败行为和可验证预期。验证以行为为依据，多个函数可共用一个验证，执行 Agent 可以领取一组紧密关联的函数级计划，无需每个函数单独一个 Agent 或单独一项测试。
4. 3实现 保留上层对话 → Implementation Dispatcher → Execution Agent 的分工。上层对话拥有整体方案、用户决策和执行计划修订权；Dispatcher 安排依赖顺序、分配任务、收集及验收执行结果、运行统一验证、整理并提交候选；Execution Agent 根据分配计划编码和修复。Dispatcher 不亲自编码、不修改执行计划。
5. 实现中的计划调整由 Dispatcher 向上层对话报告具体理由和影响；上层核对依据并更新相关计划及必要的文件范围，之后 Dispatcher 重新派发受影响的任务。受影响任务在修订完成前暂停，已经验收的工作尽量保留，避免旧计划继续授予写入或重复已完成工作。
6. 在已确认影响范围内、保持功能和接口契约的函数移动、拆分、新增辅助函数、实现顺序调整及调用适配，由上层对话自行处理，无需向用户报告或再次请求确认。
7. 功能增减、扩大到其他业务模块或改变其行为、公共接口契约、验收条件，以及较大的架构调整，必须在受影响工作继续前由上层对话说明并询问用户。技术上的文件范围同步不能借机扩大已确认业务范围。
8. 用户确认的功能合同与可修订的执行计划分开对待。调整原因和版本使用现有文档、Git 和原工作流记录追溯；计划、文件权限、执行分配、审查依据和恢复状态必须保持一致，不另建通用调度服务或独立状态权威。

## 现有事实与约束

- 当前 Ticket 规则要求窄而完整、可独立验证的行为切片，大小适合一个新上下文窗口，并声明真实前置依赖。
- 现有 Stage 3 分配记录已经包含精确文件范围、行为和测试，但未强制 Ticket 下函数级计划。
- 现有实现阶段把规划文档作为受保护来源，scope-revise 只允许在 Stage 3 尚未准备或启动前使用；内部修订必须解决这些实际权限和版本约束。
- 仓库还存在局部修改的 bounded direct implementation 例外；新方案必须明确它与本次 Dispatcher 不编码要求的关系，不能留下互相矛盾的新运行规则。历史运行继续使用原固定包，不能通过迁移旧记录或伪造权限适配新规则。
- 保持现有单 Flow Worktree、明确文件归属、停止屏障、原生身份与回执核验、独立两轴审查、候选对应验证以及 Stage 4 集成归档职责。
- src 为维护源，skills 为生成包。规划载体使用 .scratch/ 下 Spec/Tickets 和 docs/adr/ 下必要 ADR；外部 Matt Skills 仍是外部依赖。

## 由 2方案 解决的工程问题

计划的数据和文档结构、稳定引用与版本；真实函数和调用链证据；计划就绪和依赖验证；计划调整的判断、权限及原子衔接；新增辅助函数或必要文件的授权；旧分配失效及已完成结果保留；审查和候选绑定；中断、失败、重试、暂停取消和未知结果恢复；现有独立 Stage 3 入口与直接实现例外的兼容边界；协议与生成包版本策略；最小完整测试和真实宿主验收安排。

上述事项由设计者在已确认行为内确定，不能留给 Stage 3 做实质方案选择。

## 可观察验收条件

- 2方案交付的实施 Ticket 可追溯到完整的函数级执行计划；覆盖能力、实现思路、依赖、关键契约及行为验证依据。
- 3实现 派发明确引用计划及有效版本，执行者按确定顺序和分配范围工作；Dispatcher 本身不能提交亲自编码的实现字节，也不能自行改写计划。
- 在合同和业务影响范围内的函数级调整可由原上层对话闭环完成，用户不被额外打断。
- 需要用户决策的功能、业务范围、接口契约或重大架构变化不能通过内部修订继续实现。
- 计划修订和文件权限同步后才重新派发；旧分配、旧结果及旧审查不能误算新计划下的有效交付；未受影响的已验收工作有依据地保留。
- 中断和重复请求能够恢复到唯一一致的计划、权限及执行状态；不重放未知副作用，不迁移或绕过旧运行固定身份。
- 方案给出实际生产调用链、必要关联文件、协议兼容策略、行为验证安排及一份代表性 Ticket/函数计划样例；实施后由仓库规定入口验证。

## 非目标与本次授权

本次只冻结需求并设计 Spec、必要 ADR 和 Tickets，完整方案审阅前不进入实现。不安装或更新本机 Skills，不部署、不创建 PR、不远程发布、不修改其他项目或任务，不做无关重构。不新增每函数必派一个 Agent、每函数必写一个测试、后台调度或通用计划系统。
