## 目标

保留方案 → Implementation Ticket → Function Execution Plan，让每个执行对话处理上下文有限、行为完整、可验证的小片工作，提高首次交付质量并减少全局返工、协作等待和恢复成本。不能以最终测试通过代替效率或成功率证据，不能以减少审查或删除恢复证据换取表面提速。

## 已确认要求

1. 小任务完成进行局部代码审查，有问题交回执行者修复再复查；Ticket 完成验收完整行为与各片组合；整体交付检查跨 Ticket 接口、共享状态及整体需求。明确三层职责，替代重复的整范围审查，不在旧流程上机械增加审查层。
2. 修复优先留在原执行上下文；审查针对修复及直接影响范围。只有公共契约、共享状态、跨片影响或无法可靠界定范围时扩大审查。最终候选仍有完整有效的验收依据，保留未受影响结论必须证明其适用性。
3. 测试按行为和影响组织。局部修复先运行对应回归和受影响测试，整体集成与交付完成必要完整验证；避免仅在所有审查收敛后才发现广泛夹具或契约适配遗漏。不能削弱原有效验证或跳过必要失败分支。
4. 保留函数级计划，执行按可验证的小行为分组，可包含一组紧密关联函数，不要求每函数一个 Agent 或单独测试。执行者只接收必要合同、相关计划、依赖结果和验证要求；不得每片都隐式读取整个历史。
5. 降低内部计划修订成本，明确函数体内选择、局部计划修订与公共合同变化的边界。内部改动尽量局部处理，保留未受影响任务和结果；必须保证共享 Git/文件写入、权限和停止证据的一致性。确需扩大用户可见功能或业务影响仍由用户确认。
6. 允许一个管理记录，但应只记录有意义的当前控制事实。当前状态、历史事件、原始证据职责明确，只有一个当前控制权威，不能拆成互相竞争的台账。
7. 当前记录随未完成工作有界增长，而不随轮询、重试、累计完成任务数无限增长。同一事实不反复复制；大快照和原始回执独立保存并用稳定引用关联。相同轮询结果合并，但未知调用、身份冲突、未完成事务等恢复必要信息必须保留。
8. 固定按 Ticket/工作批次拆分、按任务/Ticket/交付生命周期整理的规则。归档与删除分开，已完成历史退出活跃读取范围；未解决异常及仍被引用的证据不得删除。记录物理拆分后，恢复和 Agent 上下文也必须按需读取，不能每次重载全部文件。
9. 容量上限、整理阈值、引用完整性、原子保存/恢复和失败行为应在方案中明确。写入前保证产物可被下一次读取；达到阈值按固定规则整理或拒绝，失败保留上一个有效状态。不得把反复人工扩容作为正常任务运行路径。
10. 定义可比较的质量和效率指标：首次局部验收通过率、集成新增缺陷、返工轮数、总耗时及协调/验证耗时、活跃状态体积和恢复读取量。方案给出合理样本/基线与验收办法，不宣称尚未测得的改善。

## 兼容性与范围

- 新规则面向新运行；旧运行保持原固定包、原记录与恢复方式，本次不迁移旧记录、不清理旧任务证据。
- 历史证据默认先归档；自动删除必须有明确资格、保留条件和引用检查，具体政策由方案确定并供统一审阅。
- 覆盖当前已支持路径上本次变更必需的一致性修改；不顺带补齐既有延期的无 Ticket 修订、foreground ingress 或 attached 初始化能力。必须辨明受影响支持面与不支持面。
- 本轮只写需求和规划文档；不修改实现代码、安装包、全局配置，不部署、不远程发布，不自动进入 Stage 3。
- 保留用户已有工作。工程选择由设计阶段根据代码事实解决，不把普通实现选择反复交回用户。

## 已核实背景（事实，不是新需求）

旧生产任务「评估更细粒度的执行拆分」使用已安装 1.2.3/progress-v17 执行改造，新 1.3.0 机制在独立样例中验证。原检查点登记 12 个候选的两轴审查、37 个执行分配，其中 24 个以 review_ 命名；旧运行容量从 256 KiB 多次临时扩大，且遇到范围漏列测试、生命周期证据和宿主可用性问题。这不是旧/新流程成功率的对照试验，不能把全部耗时归因于函数拆分。

当前仓库协议的正式独立审查位于全部实施完成后的候选；替换候选重跑两轴。正式计划修订全停止，且会让旧候选/审查/最终验证成为历史。事实依据：src/shared/references/guided-implementation/{execution-protocol,originating-task-protocol,workflow-control-protocol}.md、docs/adr/0013-revise-function-plans-within-contract.md、.scratch/function-execution-plans/PRD.md。历史证据仅作为只读诊断，不导入旧运行权威。

## 可观察验收条件

- 能用具体 Ticket 展示：小片实现/审查/修复、Ticket 验收、整体集成三个闭环，且各层不重复承担同一完整审查。
- 普通局部修复保留无关验收；影响扩大的变化可靠触发对应重审；过期或不完整证据不能覆盖新候选。
- 计划修订的停止、重新派发和结果失效范围明确；共享写入/未知调用情况下没有并发越权或恢复歧义。
- 重复轮询与长串已完成任务不会线性膨胀活跃状态；所需历史和大证据按引用读取；归档前后下一步、权限、验收结论及恢复行为一致。
- 容量边界、整理中断、缺失/损坏引用、重复回执、未知结果、暂停/恢复都有明确可执行验收，不依赖人工增容。
- 方案覆盖真实生产调用链、测试/生成包影响、版本兼容和完整逐文件清单；Tickets 可独立验收，有依赖与函数级计划；没有留待实现时再问用户的实质选择。

## 交由方案解决的工程问题

审查粒度与证据继承模型、审查角色和上下文复用规则、测试提前时机、计划修订局部化可行边界、状态存储结构与原子事务、归档/删除资格与保留政策、容量和模型读取预算、测量基线、首个生产边界 TDD 切片、兼容版本与生成物同步。数值必须有样本依据或标注为待验证设计预算，不能冒充实测结论。
