# 1. 接收实现成果

逐项读取执行清单「已有结果产物」表中的文件或链接，
提取本次任务的实现范围、交付结果及资料中注明的待归档事项。

将影响后续归档的事项或资料缺口记入本步骤的简短记录。

资料无法读取时，记录具体位置和问题，暂停受影响的工作。

## 完成条件

清单中列出的结果产物已读取；
本次任务的实现范围、交付结果及资料中注明的待归档事项已提取。

# 2. 检查归档前提

结合已提取的交付信息和实际 Git 状态，核对：

- 集成 Worktree 属于清单记录的目标项目，
  实际分支和当前提交与清单中的集成分支、实现提交一致。
- 本次实现成果已提交，没有影响交付的未完成事项或未解决问题。
- 所需测试、审查和整改已完成，
  已有结果与当前实现状态一致，可以用于本次归档。
- 本次实现和整改工作已结束，
  没有其他执行者继续修改集成工作区。

检查未提交修改时，区分执行清单的正常更新与其他修改。
清单更新不影响本步骤的完成判断；
其他修改需要核对其归属及对交付的影响。

前提不满足或无法确认时，将具体问题和影响记入简短记录，
暂停受影响的后续归档工作。
需要补充实现、验证或整改时，待相关工作完成后重新核对。

## 完成条件

- 工作区、分支和实现提交与清单记录一致。
- 实现成果已提交，没有影响交付的未处理修改或未解决事项。
- 测试、审查和整改结果适用于当前实现。
- 集成工作区的相关实现写入已经结束。

# 3. 检查 main 的变化

读取清单中目标分支的当前状态，记录其实际提交，
检查它与待归档实现提交的关系：

- 目标分支的当前提交已包含在实现提交中，
  可以继续后续归档。
- 实现提交已包含在目标分支中，
  记录成果已经交付的事实，后续只处理尚未完成的事项。
- 双方存在尚未整合的提交，
  检查目标分支新增内容对本次实现的影响，
  按项目约定在集成 Worktree 中完成必要整合。

评估变化时，关注本次实现涉及的接口、共享逻辑、
依赖和相关文档，判断已有验证与审查结论是否仍然适用。

整合后，对受影响范围完成必要的验证和审查。
未受影响的部分可以复用已有结论。

需要改变已确认的目标、范围或设计时，
说明具体问题和影响，取得用户决定后再继续。

发生冲突时，按第 6 节中的“冲突处理”规则处理。

将目标分支提交、变化影响及处理结果记入简短记录。
整合产生新的实现提交时，
在必要验证和审查通过后更新清单中的实现提交。

## 完成条件

- 目标分支的当前提交及其与实现成果的关系已核实。
- 需要整合的变化已处理，没有未解决冲突。
- 必要验证和审查已通过，复用的结论仍适用于当前成果。
- 清单中的实现提交与最终集成成果一致，
  检查时的目标分支提交已记录。

# 4. 完成文档收尾

根据本次实现范围、待归档事项和项目文档约定，
确定需要调整的文档，例如 README、使用说明、
配置说明、技术文档或 CHANGELOG。

在集成 Worktree 中完成必要调整，
使文档与已确认的要求及最终实现一致，
沿用文档已有的格式和项目约定。

核对修改后的内容，对涉及的路径、链接、
配置和调用示例完成适用的检查。

发现文档与实现存在涉及已确认要求的冲突时，
说明具体差异及影响，取得用户决定后再继续。

检查本次文档差异，
将需要交付的文档修改提交到集成分支。
将文档调整结果及提交号记入本步骤的简短记录。

本次交付不影响文档，
或相关文档已经与最终实现一致时，
本步骤可以跳过，并记录判断依据。

## 完成条件

- 本次交付所需的文档与已确认要求及最终实现一致。
- 修改内容已完成必要检查。
- 需要交付的文档修改已提交到集成分支，
  修改结果及提交号已记录。

# 5. 核对最终待合并成果

读取集成分支的当前提交，确定最终待合并提交。
结合已核实的目标分支状态，核对：

- 本次实现和需要交付的文档修改均已包含。
- 待合并内容符合已确认的任务范围，
  没有混入其他任务的修改。
- 需要交付的修改均已提交。

对照已有验证和审查记录，
检查实现提交之后的变化及其影响，
确认哪些结论仍然适用。

未受影响的部分可以复用已有结论；
新增变化或受影响部分需要完成必要的验证和审查。

发现遗漏、范围偏差或尚未验证的变化时，
记录具体问题，待修正和必要检查完成后重新核对。

成果已经包含在目标分支中时，
核实本次实现和文档收尾均已交付，
记录实际交付状态。

保留已有验证结果所对应的实现提交记录，
将最终待合并提交、核对结果及必要的检查结果
记入本步骤的简短记录。

## 完成条件

- 本次实现和文档成果完整，符合已确认范围。
- 需要交付的修改均已提交，没有混入无关修改。
- 必要验证和审查已通过，
  复用结论的适用性已核对。
- 最终待合并提交及实际交付状态已明确并记录。

# 6. 合并并完成代码交付

默认合并到 main；用户明确指定其他目标分支时，
使用指定分支。

操作前再次核对目标分支的实际状态，
以及集成分支中待交付的提交，
确认它们与此前记录的核对结果一致。

成果已经交付时，核实实现和文档修改均已包含，
沿用实际交付结果，继续处理尚未完成的事项。

仍需交付，但目标分支或待合并内容发生变化时，
先完成受影响的整合、文档核对、验证和审查，
重新核对最终成果后再继续。

检查目标工作区的状态，
确保合并操作不会覆盖已有修改或无关文件。
存在影响合并的问题时，记录具体情况并暂停相关操作。

前述核对完成后，无冲突时直接合并。

按项目约定和本次任务已有授权完成交付：

- 仅要求本地交付时，合并到清单中的目标分支。
- 要求远程交付时，核对远程仓库、目标分支及交付方式，
  完成所需的推送或 PR 合并。
  所需操作尚未获授权时，说明具体操作及影响，
  取得用户同意后再执行。

## 冲突处理

发生冲突时，先读取冲突上下文、双方修改和相关任务要求，
判断能否保留双方有效的修改意图。

重复代码、位置重叠等能够明确判断，
且通过调整可以保留双方有效行为的冲突，自行解决。

同一功能的修改相互交织，无法判断正确组合，
或需要决定行为、优先级及保留范围时，
暂停相关冲突的处理，向用户确认。

等待用户确认时，可以先处理不依赖该决定的独立冲突；
全部待确认项明确后，再完成最终合并。

需要取舍时，逐项列明：

- 冲突位置和双方修改意图。
- 可选的合并方案及建议理由。
- 各方案会保留、舍弃或改变的内容。
- 需要用户决定的优先级或处理原则。

依据用户的明确决定处理，不能默默覆盖或舍弃有效内容。
已有明确决定覆盖本次取舍时，引用该依据继续处理。

冲突较多时，可以先建立冲突清单，
逐项区分“可自行解决”和“待用户确认”，
记录处理结论、依据及尚未解决的问题。

冲突解决后，核对完整合并结果，
确认双方修改已按确定的原则处理，
并完成受影响范围的必要验证和审查。

## 结果核对与接续

操作后核实目标分支中的实际内容，
确认本次实现和文档成果已经交付。
通过 PR 交付时，确认 PR 已实际合并，
不能将创建 PR 视为完成合并。

将实际目标提交、本地和远程交付结果，
以及适用的 PR 链接记入本步骤的简短记录。

失败时，保留集成成果，
记录已完成的操作和剩余事项。
结果不明确时，先核实 Git、远程分支或 PR 的实际状态，
再决定如何接续；已完成的操作只继续其剩余工作。

## 完成条件

- 本次实现和文档成果已进入指定目标分支，
  实际交付内容与核对通过的成果一致。
- 本次要求的远程交付已完成并核实；
  仅本地交付时，明确记录该范围。
- 实际目标提交及交付结果已记录。
- 没有影响本次交付的未解决问题或结果未知的操作。

# 7. 完成项目状态收尾

根据已有任务资料和项目约定，
定位本次需要维护的状态记录，
例如 Spec、Tickets 或 Issue 的完成状态。

核对这些记录与实际交付结果是否一致，
按项目约定补齐必要的状态更新。
已经正确更新的内容，只核对结果，避免重复操作。

只处理本次任务范围内的状态。
记录中包含其他未完成事项时，
保留与其完整范围相符的状态。

状态更新应反映实际完成程度，
遵守项目对实现完成、合并完成等状态的定义。

涉及外部系统写入时，核对已有授权；
所需操作尚未获授权时，
说明具体更新内容及影响，取得用户同意后再执行。

状态更新涉及需要交付的仓库文件时，
完成相应提交与交付，再核实最终状态。

将更新结果、相关记录位置及未处理事项
记入本步骤的简短记录。
操作结果不明确时，先查询实际状态，再决定如何接续。

本次没有需要维护的状态记录，
或用户明确要求不更新时，
本步骤可以跳过，并记录依据。

## 完成条件

- 本次需要维护的状态与实际交付结果一致。
- 必要状态更新已完成并核实。
- 涉及需要交付的仓库文件时，
  相应修改已提交并完成交付。
- 更新结果及相关记录位置已记录。
