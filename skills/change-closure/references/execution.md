# 1. 核对成果与归档前提

## 读取已有产物

逐项读取执行清单「已有结果产物」表中的文件或链接，
提取本次任务的实现范围、交付结果及资料中注明的待归档事项。

记录影响后续归档的事项或资料缺口。

## 核对归档前提

结合已提取的交付信息和实际 Git 状态，核对：

- 集成 Worktree 属于清单记录的目标项目，
  实际分支与清单中的集成分支一致。
  首次接收时，当前提交与清单中的实现提交一致；
  接续时，结合执行记录核对当前提交及本流程产生的后续提交，
  已确认的文档、整合提交不因改变 HEAD 而使首次接收核对失效。
- 本次实现成果已提交，没有影响交付的未完成事项或未解决问题。
- 所需测试、审查和整改已完成，
  已有结果与当前实现状态一致，可以用于本次归档。
- 本次实现和整改工作已结束，
  相关执行者已停止写入集成工作区。

检查未提交修改时，区分执行清单的正常更新与其他修改。
清单更新不影响本步骤的完成判断；
其他修改需要核对其归属及对交付的影响。

## 完成条件

- 结果产物已读取，实现范围、交付结果及待归档事项明确，
  工作区、分支和提交来源已核实。
- 实现、验证、审查和整改已完成，
  已有结论适用于当前成果，没有影响交付的未处理修改或持续写入。

# 2. 检查目标分支变化并完成文档

## 检查目标分支变化

读取清单指定目标分支的当前提交，记录提交号。
结合本次实现与目标分支的共同基线，
检查目标分支新增的提交和文件改动。

重点判断：

- 新增修改是否影响本次实现涉及的功能、接口、共享逻辑或依赖。
- 相关文档是否发生变化，本次文档调整是否需要据此修正。
- 已有验证和审查结论是否仍然适用，
  哪些范围需要在代码整合后重新检查。

将目标分支提交、变化影响，
以及合并时需要处理的事项记入简短记录。

检查结果涉及已确认目标、范围或设计的变化时，
说明具体问题和影响，取得用户决定后继续。

## 完成文档收尾

根据已确认要求、本次实现、目标分支变化及项目文档约定，
确定需要调整的 README、使用说明、配置说明、
技术文档或 CHANGELOG。

能够明确的文档调整，在集成 Worktree 中完成，
沿用已有格式，核对涉及的路径、链接、配置和调用示例，
将需要交付的修改提交到集成分支。

文档调整依赖尚未确定的合并方案时，
记录具体事项，
在“核对最终成果并合并交付”中完成。

无需调整文档时，记录判断依据。

将文档调整结果、提交号及待处理事项记入简短记录。

## 完成条件

- 目标分支提交、变化影响及需要重新检查的范围已核实并记录。
- 当前能够明确的文档调整已完成必要检查并提交；
  无需调整时，判断依据已记录。
- 合并时待处理的代码和文档事项已明确。

# 3. 核对最终成果并合并交付

## 整合并核对最终成果

核对目标分支的当前状态，
与第 2 步记录不一致时，补充检查变化及其影响。

依据已记录的变化影响，在集成 Worktree 中完成必要整合。
发生冲突时，按本节“冲突处理”规则处理。

补齐第 2 步记录的、依赖合并方案的文档调整，
将需要交付的修改提交到集成分支。

读取集成分支的当前提交，确定最终待合并提交。
结合已核实的目标分支状态，核对：

- 本次实现和需要交付的文档修改均已包含。
- 待合并内容符合已确认的任务范围，
  没有混入其他任务的修改。
- 需要交付的修改均已提交。

汇总整合、文档调整和冲突处理带来的变化，
对受影响范围完成必要验证、文档检查和审查；
未受影响的部分复用已有有效结论。
后续变化使结论失效时，只补查受影响部分，再核对最终成果。

发现遗漏、范围偏差或检查失败时，处理完成后重新核对。

保留已有验证结果所对应的实现提交记录，
将最终待合并提交、核对结果及必要的检查结果
记入本步骤的简短记录。

## 合并并完成交付

默认合并到 main；用户明确指定其他目标分支时，
使用指定分支。

合并前确认目标分支和待合并提交
仍与本步骤的核对结果一致。

成果已经交付时，核实实现和文档修改均已包含，
沿用实际交付结果，继续处理尚未完成的事项。

仍需交付，但目标分支或待合并内容发生变化时，
按“整合并核对最终成果”的要求处理受影响部分。

检查目标工作区的状态，
确保合并操作不会覆盖已有修改或无关文件。
前述核对完成后，无冲突时直接合并。

按项目约定完成本次要求的交付：

- 仅要求本地交付时，合并到清单中的目标分支。
- 要求远程交付时，核对远程仓库、目标分支及交付方式，
  完成所需的推送或 PR 合并。

## 冲突处理

发生冲突时，先读取冲突上下文、双方修改和相关任务要求，
判断能否保留双方有效的修改意图。

重复代码、位置重叠等能够明确判断，
且通过调整可以保留双方有效行为的冲突，自行解决。

同一功能的修改相互交织，无法判断正确组合，
或需要决定行为、优先级及保留范围时，
暂停相关冲突的处理，向用户确认。

等待用户确认时，可以先处理不依赖该决定的独立冲突；
全部待确认项明确后，再完成最终合并。

需要取舍时，逐项列明：

- 冲突位置和双方修改意图。
- 可选的合并方案及建议理由。
- 各方案会保留、舍弃或改变的内容。
- 需要用户决定的优先级或处理原则。

依据用户的明确决定处理，不能默默覆盖或舍弃有效内容。
已有明确决定覆盖本次取舍时，引用该依据继续处理。

冲突较多时，可以先建立冲突清单，
逐项区分“可自行解决”和“待用户确认”，
记录处理结论、依据及尚未解决的问题。

冲突解决后，核对完整合并结果，
确认双方修改已按确定的原则处理。
所需检查统一按“整合并核对最终成果”的要求完成。

## 核实交付结果

操作后核实目标分支中的实际内容，
确认本次实现和文档成果已经交付。
通过 PR 交付时，确认 PR 已实际合并，
不能将创建 PR 视为完成合并。

将实际目标提交、本地和远程交付结果，
以及适用的 PR 链接记入本步骤的简短记录。

## 完成条件

- 核对通过的实现和文档成果已进入目标分支，所需验证和审查结论有效。
- 本次要求的本地或远程交付已核实，没有影响交付的未解决事项或未知结果。
- 最终待合并提交、实际目标提交及交付结果已记录。

# 4. 更新项目状态

根据已有任务资料和项目约定，
定位本次需要维护的状态记录，
例如 Spec、Tickets 或 Issue 的完成状态。

核对这些记录与实际交付结果是否一致，
按项目约定补齐必要的状态更新。
已经正确更新的内容，只核对结果，避免重复操作。

只处理本次任务范围内的状态。
记录中包含其他未完成事项时，
保留与其完整范围相符的状态。

状态更新应反映实际完成程度，
遵守项目对实现完成、合并完成等状态的定义。

状态更新涉及需要交付的仓库文件时，
完成相应提交与交付，再核实最终状态。

记录更新结果及相关记录位置。

本次没有需要维护的状态记录，
或用户明确要求不更新时，
本步骤可以跳过，并记录依据。

## 完成条件

- 必要状态更新及相应仓库文件交付已核实，反映实际完成程度。
- 更新结果及相关记录位置明确。

# 5. 复检并处理 Worktree 与任务分支

## 整体复检

对照用户要求、已确认的任务范围和执行记录，
核对实现、文档、代码交付及项目状态。
前面适用步骤的完成判断应有实际依据，跳过事项应有明确理由。

已经核实且未受后续变化影响的结果可以复用。
发现遗漏或结果不一致时，先处理并重新核对，
确认交付和状态收尾完整后，再清理资源。

## 处理 Worktree

依据当前任务的创建或复用记录、Git Worktree 登记信息，
以及可查询的宿主信息，核对清单中工作区的实际位置和处理方式。

按来源处理：

- Codex 托管的 Worktree：
  交给 App 的归档和自动清理机制管理，本 Skill 不主动删除。
- 本流程自行创建的普通 Git 临时 Worktree：
  完成交付并通过本节的清理前核对后清理。
- 复用的长期或共享 Worktree：
  保留。

已有信息不足以确定来源、归属或清理范围时，
保留工作区，记录已知情况和具体缺口。
需要用户决定时，只针对该工作区的具体问题确认。

### 清理前核对

对本流程创建的普通 Git 临时 Worktree，核对实际内容和使用情况：

- 根据已有任务要求和实际 Git 状态，
  需要交付或已明确要求保留的内容均已处理。
- 当前任务的相关实现和整改写入已结束，
  现有任务记录及可查询信息中没有显示其他任务仍在使用该工作区。

检查工作区内容时，区分本次辅助资料与需要交付、保留的内容。
执行清单等本次辅助资料的正常更新，不单独阻止清理。

发现未交付的实现修改、归属不明确的文件，
或已知仍需使用工作区的任务时，保留工作区并记录具体原因。

条件满足后，按已确认的可清理范围使用 Git Worktree 清理机制，
移除对应工作区，核实实际结果。

保留或交由 App 管理时，记录实际路径和处理方式。

## 清理任务分支

根据清单和已有任务记录，
确定本次任务不再需要的集成分支及临时开发分支。

保留目标分支、历史保留分支、长期或共享分支，
以及用户明确要求保留的分支。

删除前核对：

- 分支属于本次任务，名称和当前提交已确认。
- 分支中的交付内容已进入指定目标分支，
  没有尚未交付的新修改。
- 该分支不再用于本次后续工作，
  已有记录中没有其他任务仍需使用它。

合并方式导致提交号变化时，
结合实际合并记录和内容差异核实交付结果，
不能仅凭提交号不同判断成果尚未交付。

### 处理 Worktree 占用

分支仍被其他任务或长期、共享工作区使用时，
保留分支并记录原因。

仅当分支被本次专用且保留的 Worktree 检出，
且不再需要在该分支上继续工作时，
保持当前提交和文件状态，
将该工作区切换为脱离分支的状态（detached HEAD），
再清理该分支。

### 执行清理

对满足条件的本地分支执行删除，并核实结果。
不能通过强制删除绕过归属和交付内容的核对。

本次明确要求清理远程分支时，
核对远程仓库和分支，再执行并核实。
分支已经不存在时，核实并记录即可。

## 完成条件

- 交付和项目状态收尾已通过整体复检。
- Worktree 和分支已按来源及用途完成清理、保留或交由 App 管理，
  实际结果已核实。
- 资源路径、分支名称、处理结果、保留原因及必要的剩余事项已记录。

明确要求清理但尚未完成的 Worktree 或分支，
保持未完成，继续处理或报告具体阻塞。

# 6. 核对结果并报告

核对资源清理、保留的实际结果，
结合已确认的代码交付和项目状态，整理最终结果。
确认报告与实际产物、Git 状态及必要的外部状态一致。

## 结果报告

根据实际结果向用户报告：

- 当前完成情况及本次工作摘要。
- 目标分支、本次交付提交及适用的 PR 链接。
- 文档调整和项目状态更新结果。
- 验证、审查结果及必要的未验证范围。
- Worktree 和分支的清理、保留情况及原因。
- 尚未完成的事项和需要用户处理的问题。

明确区分本地交付与远程交付，
以及已清理、保留和交由 App 管理的资源。

## 完成条件

- 报告与实际交付、状态更新及资源处理结果一致，必要的未完成事项已说明。
- 用户已收到结果报告。
