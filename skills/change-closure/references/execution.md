# 1. 接收成果与核对归档前提

本说明中的过程信息汇入当前大步骤的最终简要结果。进度文件只在大步骤完成时由入口脚本更新；确认、等待、冲突和整改过程不单独写入。

## 接收交接信息

从已有交接报告和执行记录中取得实现范围、交付结果、
验证与审查结论及其对应提交，以及待归档事项。
结合统一进度文件中归档输入的产物位置，按需读取相关文件或链接。

已有结论完整且仍适用时直接复用；信息缺失、状态变化或结论不一致时，
读取相关产物核查，记录影响后续归档的事项或资料缺口。

## 核对归档前提

结合已提取的交付信息和实际 Git 状态，核对：

- 集成 Worktree 属于进度文件记录的目标项目，
  实际分支与归档输入中的集成分支一致。
  首次接收时，当前提交与归档输入中的实现提交一致；
  接续时，结合执行记录核对当前提交及本流程产生的后续提交，
  已确认的文档、整合提交不因改变 HEAD 而使首次接收核对失效。
- 本次实现成果已提交，没有影响交付的未完成事项或未解决问题。
- 所需测试、审查和整改已完成，
  已有结果与当前实现状态一致，可以用于本次归档。
- 本次实现和整改工作已结束，
  相关执行者已停止写入集成工作区。

进度文件保存在临时 Worktree 之外，不属于实现交付范围。
检查未提交修改时，核对其归属及对交付的影响。

## 完成条件

- 交接信息已核实，实现范围、交付结果及待归档事项明确，
  工作区、分支和提交来源已核实。
- 实现、验证、审查和整改已完成，
  已有结论适用于当前成果，没有影响交付的未处理修改或持续写入。

# 2. 检查目标分支变化并完成文档

## 确定交付方式与合并策略

根据用户要求、项目约定和已有授权，确定并记录本次交付方式、
实际仓库、目标分支及合并策略。目标分支使用归档输入中的值。

- 本地交付：以本地目标分支为交付依据。
- 直接推送：以指定远程仓库的目标分支为交付依据，核对本地与远程差异。
- PR 合并：以 PR 的实际目标仓库和分支为交付依据，
  核对其与本次要求一致，按仓库规则完成交付，无需预先合入本地目标分支。

沿用项目规定的 merge、squash、rebase 或平台合并策略，
同时明确适用的分支保护和必需检查。
已有要求明确时直接使用；无法确定且会影响交付对象或历史处理方式时，
说明具体选择及影响，向用户确认。
本步骤确定操作路径，实际操作仍遵守入口的授权要求。

## 检查目标分支变化

本地交付时读取本地目标分支；远程交付时，先刷新指定远程的对应引用，
核实实际远程目标提交，不能用未刷新的引用或本地同名分支代替。
本地与远程不一致时，查明差异及归属，按已确定的交付方式处理；
本地独有提交不能因分支同名而混入远程交付。

记录本次检查所依据的目标提交。
结合本次实现与目标分支的共同基线，
检查目标分支新增的提交和文件改动。

重点判断：

- 新增修改是否影响本次实现涉及的功能、接口、共享逻辑或依赖。
- 相关文档是否发生变化，本次文档调整是否需要据此修正。
- 已有验证和审查结论是否仍然适用，
  哪些范围需要在代码整合后重新检查。

将目标分支提交、变化影响，
以及合并时需要处理的事项记入简短记录。

检查结果涉及已确认目标、范围或设计的变化时，
说明具体问题和影响，取得用户决定后继续。

## 完成文档收尾

根据已确认要求、本次实现、目标分支变化及项目文档约定，
确定需要调整的 README、使用说明、配置说明、
技术文档或 CHANGELOG。

能够明确的文档调整，以及项目允许在合并前更新的仓库内任务状态，
在集成 Worktree 中一并完成，
沿用已有格式，核对涉及的路径、链接、配置和调用示例，
将需要交付的修改提交到集成分支。

文档调整依赖尚未确定的合并方案时，
记录具体事项，
在“整合、验证并合并交付”中完成。
必须以合并成功为前提的状态留到第 4 步更新，
遵守项目对实现完成与合并完成的定义。

无需调整文档时，记录判断依据。

将文档调整结果、提交号及待处理事项记入简短记录。

## 完成条件

- 交付方式、实际仓库、目标分支、合并策略和适用检查已明确。
- 目标提交、变化影响及需要重新检查的范围已核实并记录。
- 当前能够明确的文档调整已完成必要检查并提交；
  无需调整时，判断依据已记录。
- 合并时待处理的代码和文档事项已明确。

# 3. 整合、验证并合并交付

## 整合并核对最终成果

按第 2 步确定的来源核对目标分支的当前状态，
与第 2 步记录不一致时，补充检查变化及其影响。

以已核实的目标提交为基础，按确定的合并策略准备最终整合结果。
目标分支有尚未纳入的变化时，在集成 Worktree 中完成整合，
或使用平台针对本次源提交和目标提交生成的可核实整合结果。
验证应覆盖双方组合后的内容，不能仅以任务分支上的旧结果代替。
发生冲突时，按本节“冲突处理”规则处理。

补齐第 2 步记录的、依赖合并方案的文档调整，
将需要交付的修改提交到集成分支。

读取集成分支的当前提交，确定最终待合并提交。
结合已核实的目标分支状态，核对：

- 本次实现和需要交付的文档、状态修改均已包含。
- 待合并内容符合已确认的任务范围，
  没有混入其他任务的修改。
- 需要交付的修改均已提交。

汇总整合、文档调整和冲突处理带来的变化，
对受影响范围完成必要验证、文档检查和审查；
即使没有文本冲突，也要检查接口、依赖、配置和共享逻辑的组合影响。
未受影响的部分复用已有有效结论，项目明确要求的检查仍须完成。
后续变化使结论失效时，只补查受影响部分，再核对最终成果。

发现遗漏、范围偏差或检查失败时，处理完成后重新核对。

保留已有验证结果所对应的实现提交记录，
将目标提交、最终待合并提交、整合结果及其对应的验证与审查结果
记入本步骤的简短记录。
平台生成整合结果时，记录能定位该结果及其检查的提交或链接。

## 合并并完成交付

使用第 2 步确定的交付方式、仓库、目标分支和合并策略。

合并前确认目标分支和待合并提交
仍与本步骤的核对结果一致。

成果已经交付时，按本节“核实交付结果”确认所需修改均已包含，
沿用实际交付结果，继续处理尚未完成的事项。

仍需交付，但目标分支或待合并内容发生变化时，
按“整合并核对最终成果”的要求处理受影响部分。

选择能够约束源提交、目标状态及合并结果的操作方式，
避免最后一次检查后意外产生未经验证的整合内容：

- 本地交付：核对需要操作的目标工作区，确保不会覆盖已有修改或无关文件。
  已验证的结果适合快进且项目允许时，使用只允许快进的方式交付；
  要求合并提交或其他策略时，确认产生的内容与已验证整合结果一致。
- 直接推送：推送已核对的明确提交到指定远程目标分支，
  避免依赖可能移动的源分支；遵守远程更新约束，不能强推绕过分支推进或保护规则。
- PR 合并：核对 PR 的源提交和目标分支，确认必需检查覆盖当前待合并结果，
  使用平台可用的源提交匹配、分支保护或合并队列等约束完成合并。
  平台更新了整合结果时，以更新后的结果完成必要检查。

核实所用机制实际约束的范围，源提交匹配不能单独证明目标未变化。
无法确认当前待合并结果受约束或被验证覆盖时，报告具体能力或证据缺口，暂停交付。

分支发生变化时，返回“整合并核对最终成果”，补充影响分析、整合和必要验证。
操作被拒绝时先查明原因；分支推进按前述规则处理，
权限、保护或检查未满足时按实际原因处理，不绕过约束继续交付。
操作结果未知时，先查询目标分支或 PR 的实际状态，再决定是否重试；
无法核实时记录已知结果并阻塞依赖交付的后续操作。

## 冲突处理

发生冲突时，先读取冲突上下文、双方修改和相关任务要求，
判断能否保留双方有效的修改意图。

重复代码、位置重叠等能够明确判断，
且通过调整可以保留双方有效行为的冲突，自行解决。

同一功能的修改相互交织，无法判断正确组合，
或需要决定行为、优先级及保留范围时，
暂停相关冲突的处理，向用户确认。

等待用户确认时，可以先处理不依赖该决定的独立冲突；
全部待确认项明确后，再完成最终合并。

需要取舍时，逐项列明：

- 冲突位置和双方修改意图。
- 可选的合并方案及建议理由。
- 各方案会保留、舍弃或改变的内容。
- 需要用户决定的优先级或处理原则。

依据用户的明确决定处理，不能默默覆盖或舍弃有效内容。
已有明确决定覆盖本次取舍时，引用该依据继续处理。

冲突较多时，可以先建立冲突清单，
逐项区分“可自行解决”和“待用户确认”，
记录处理结论、依据及尚未解决的问题。

冲突解决后，核对完整合并结果，
确认双方修改已按确定的原则处理。
所需检查统一按“整合并核对最终成果”的要求完成。

## 核实交付结果

操作后核实本次交付涉及的实际仓库和目标分支，
确认实现、文档及需交付的状态修改均已包含，且与已验证整合结果一致。
本地交付核实本地目标；直接推送核实远程实际结果；
通过 PR 交付时核对其目标和实际合并结果，不能将创建 PR 视为完成合并。

squash、rebase 或平台生成提交导致提交号变化时，
结合实际合并记录及内容差异确认与验证结果的对应关系。
目标分支随后又有其他提交时，区分本次交付结果与后续变化，
核实本次成果仍已包含，不能仅凭最新提交号不同判定交付失败。
若本次实际合入内容不同于已验证结果，返回前述影响分析与验证，
处理完成前不进入状态收尾和清理。

将实际目标提交、本地和远程交付结果，
以及适用的 PR 链接记入本步骤的简短记录。

## 完成条件

- 核对通过的实现、文档和适用状态成果已进入目标分支，
  实际交付内容与验证结果对应，所需验证和审查结论有效。
- 本次要求的本地或远程交付已核实，没有影响交付的未解决事项或未知结果。
- 检查所依据的目标提交、最终待合并提交、实际交付提交及交付结果已记录。

# 4. 更新项目状态

根据已有任务资料和项目约定，
定位本次需要维护的状态记录，
例如 Spec、Tickets 或 Issue 的完成状态。

核对这些记录与实际交付结果是否一致，
按项目约定补齐合并成功后才能进行的更新和其余未完成项。
已经正确更新的内容，只核对结果，避免重复操作。

只处理本次任务范围内的状态。
记录中包含其他未完成事项时，
保留与其完整范围相符的状态。

状态更新应反映实际完成程度，
遵守项目对实现完成、合并完成等状态的定义。

状态更新涉及需要交付的仓库文件时，
按第 2、3 步确定的交付方式和规则完成相应提交与交付：
核对最新目标状态、改动范围，完成与实际改动相称的必要检查，
再核实交付及最终状态。未受影响的已有结论可复用。
主体 PR 已合并时，后续提交需要新的交付记录，不能复用主体 PR 的完成状态。
记录这些后续提交，最终报告包含本次主体交付与状态交付的结果。

记录更新结果及相关记录位置。

本次没有需要维护的状态记录，
或用户明确要求不更新时，
本步骤可以跳过，并记录依据。

## 完成条件

- 必要状态更新及相应仓库文件交付已核实，反映实际完成程度。
- 更新结果及相关记录位置明确。

# 5. 清理资源并报告

## 清理前确认交付完整

对照用户要求、已确认的任务范围和执行记录，
核对实现、文档、代码交付及项目状态。
前面适用步骤的完成判断应有实际依据，跳过事项应有明确理由。

已经核实且未受后续变化影响的结果可以复用。
发现遗漏或结果不一致时，先处理并重新核对，
确认交付和状态收尾完整后，再清理资源。

## 处理 Worktree

依据当前任务的创建或复用记录、Git Worktree 登记信息，
以及可查询的宿主信息，核对归档输入中工作区的实际位置和处理方式。

按来源处理：

- 本 Skill 不负责管理 Codex 托管的 Worktree。
- 本流程自行创建的普通 Git 临时 Worktree：
  完成交付并通过本节的清理前核对后清理。
- 复用的长期或共享 Worktree：
  保留。

已有信息不足以确定来源、归属或清理范围时，
保留工作区，记录已知情况和具体缺口。
需要用户决定时，只针对该工作区的具体问题确认。

### 清理前核对

对本流程创建的普通 Git 临时 Worktree，核对实际内容和使用情况：

- 根据已有任务要求和实际 Git 状态，
  需要交付或已明确要求保留的内容均已处理。
- 当前任务的相关实现和整改写入已结束，
  现有任务记录及可查询信息中没有显示其他任务仍在使用该工作区。

检查工作区内容时，区分本次辅助资料与需要交付、保留的内容。
统一进度文件位于临时 Worktree 之外，清理工作区时继续保留。

发现未交付的实现修改、归属不明确的文件，
或已知仍需使用工作区的任务时，保留工作区并记录具体原因。

条件满足后，按已确认的可清理范围使用 Git Worktree 清理机制，
移除对应工作区，核实实际结果。

保留工作区时，记录实际路径和保留原因。

## 清理任务分支

根据进度文件和已有任务记录，
确定本次任务不再需要的集成分支及临时开发分支。

保留目标分支、历史保留分支、长期或共享分支，
以及用户明确要求保留的分支。

删除前核对：

- 分支属于本次任务，名称和当前提交已确认。
- 分支中的交付内容已进入指定目标分支，
  没有尚未交付的新修改。
- 该分支不再用于本次后续工作，
  已有记录中没有其他任务仍需使用它。

合并方式导致提交号变化时，
结合实际合并记录和内容差异核实交付结果，
不能仅凭提交号不同判断成果尚未交付。

### 处理 Worktree 占用

分支仍被其他任务或长期、共享工作区使用时，
保留分支并记录原因。

本次专用但保留的 Worktree 仍检出任务分支时，默认连同分支保留。
用户明确要求删除该分支时，先完成上述归属、交付和使用情况核对，
再按宿主允许的方式解除占用，保持当前提交及需保留的文件状态后清理。
无法安全解除占用时保留并报告具体阻塞。

### 执行清理

对满足条件的本地分支执行删除，并核实结果。
不能通过强制删除绕过归属和交付内容的核对。

本次明确要求清理远程分支时，
核对远程仓库和分支，再执行并核实。
分支已经不存在时，核实并记录即可。

明确要求清理但尚未完成的 Worktree 或分支，
保持未完成，继续处理或报告具体阻塞。

## 结果报告

资源操作后的结果在对应操作中核实一次，
结合已有交付和状态记录直接整理报告；未受后续变化影响的结果无需重复查询。
按入口[固定结果报告](../SKILL.md#固定结果报告与结束)的要求调用报告脚本。前四个大步骤的简要结果和第五步资源处理参数应涵盖：

- 当前完成情况及本次工作摘要。
- 目标分支、本次交付提交及适用的 PR 链接。
- 文档调整和项目状态更新结果。
- 验证、审查结果及必要的未验证范围。
- Worktree 和分支的清理、保留情况及原因。
- 尚未完成的事项和需要用户处理的问题。

报告开头从进度文件读取本任务原始问题和目标，说明本次工作是为了解决什么。阶段耗时从同一文件计算，只显示实际进入过的阶段；累计值不包含阶段间等待。

成功生成报告时，报告脚本同时写入第五步及阶段结束时间。保留完整输出供最终回复原样展示，再按入口要求处理整个任务结束后的临时进度文件。报告或写入失败时保留文件，核实后补齐，不重新执行已经完成的资源操作。

明确区分本地交付与远程交付，
以及已清理、保留和不由本 Skill 管理的资源。

## 完成条件
