本 Skill 编排 `grill-with-docs`。拷问、术语表和 ADR 等工作的执行要求以该 Skill 及其依赖为准，本 Skill 补充执行对话的选择、已有讨论文档的维护和结果交接要求。

进入本 Skill 时，记录包含时区的 ISO 8601 开始时间，供收尾脚本计算总耗时。

# 输入与前置条件

## 输入

接受当前对话中已讨论的内容，也接受用户指定的文件、issue、链接或其他资料。

根据用户请求和现有上下文，明确：

- **拷问依据**：本次使用哪些内容作为依据。用户指定资料时，以其指定的资料和范围为准。
- **拷问目标**：用户希望讨论和澄清什么问题，以及已经明确的范围和约束。
- **目标项目**：本次讨论属于哪个项目，需要结合哪个代码库或项目背景。

这些信息已明确时直接使用；无法确定时，只针对影响拷问的缺口向用户确认。

指定资料无法读取或缺少必要内容时，说明具体问题并请用户补充。多个来源存在影响讨论的矛盾、且无法确定采用哪个时，向用户确认。

## 已有讨论文档

进入本 Skill 时，检查此前的对话是否已经为本次讨论持续维护文档。

这类文档不要求使用特定名称或格式。根据当前讨论和用户指定资料确定其归属，记录实际路径或链接；无法确定且会影响维护对象时，向用户确认。

- 已有讨论文档时，在执行 `grill-with-docs` 的过程中继续维护，沿用其结构，及时记录讨论结果，并区分已确认内容与待讨论内容。
- 没有已有讨论文档时，本阶段不额外创建这类文档。

已有讨论文档的维护是补充工作。`grill-with-docs` 原有的术语表维护、ADR 等工作仍按原流程执行。

## 前置条件

确认 `grill-with-docs` 的实际入口可读取，并核实其要求的 `grilling` 和 `domain-modeling` 可用。

用户明确指定 Skill 入口时，使用其指定入口。未指定时，从当前宿主针对目标项目的完整 Skills 登记信息中，按精确名称核实启用状态和实际入口。

前置检查仅核对登记信息和入口可读取性，不加载 Skill 正文。

优先使用宿主已有的完整登记查询能力。Codex 没有直接查询工具时，使用 Python 3 调用本 Skill 的[登记查询脚本](scripts/list-skills.py)，传入 `--cwd '/目标项目的实际绝对目录'`；脚本路径使用当前已加载 Skill 中的实际绝对路径。其他宿主使用自身提供的完整查询能力。

查询结果至少包含每项的名称、实际入口和启用状态。初始 Available Skills 名单不作为完整登记信息；关闭隐式调用不视为禁用。

依赖不存在、已禁用、入口无法读取、同名多入口且无法确定采用哪个，或查询失败时，说明具体问题并暂停依赖该 Skill 的工作，按意外中断规则处理。安装、启用状态或入口发生变化后，重新核实。

输入明确且前置条件满足后，进入执行流程。

# 执行流程

## 1. 选择执行方式并执行

先确认当前环境是否具备本流程所需的新对话能力，包括：

- 在目标项目下创建新对话，并提交首条消息。
- 用户能够在新对话中继续讨论。
- 可靠取得并核实原对话的身份。
- 将完成结果传回原对话，并使原对话接续执行。
- 将界面返回原对话。

不具备上述完整能力时，由当前对话执行。

具备上述完整能力时，根据本次讨论所需的信息判断：

- 当前对话中有大量相关信息，需要结合原始讨论继续梳理和澄清时，由当前对话执行，利用当前已经积累的上下文。
- 所需资料基本集中在用户指定的文件或其他明确资料中时，准备资料引用和必要的初始信息，使用新对话执行。
- 所需信息主要在对话中，但数量较少、能够快速完整提取时，先整理完整的初始信息，再使用新对话执行。
- 具备上述完整能力，但不满足上述新对话适用条件时，由当前对话执行。

确定执行方式后：

- 当前对话执行：读取并执行[当前对话执行说明](references/main-execution.md)。
- 新对话执行：读取并执行[新对话执行说明](references/new-conversation-execution.md)。

仅读取并执行所选分支的执行说明。

执行完成后，进入结果处理。

## 2. 处理执行结果

### 任务完成

按照[结果与完成条件](#结果与完成条件)核对讨论结果和实际文档。

已经完成的用户确认可以复用，无需在原对话重复确认同一内容。

核对通过后，进入收尾与交接。发现遗漏或不一致时，交回原执行对话补充或修订，再重新核对。

### 意外中断

暂停后续流程，根据已有执行信息总结中断原因、已完成内容和未完成事项。

向用户报告情况，并给出针对性的处理建议，由用户决定如何继续。无法确认中断原因时，如实说明不确定之处。

用户决定继续后，先核对已有讨论、实际文档和执行状态，仅继续尚未完成的工作。

创建新对话或回传结果不明确时，先核实原操作，核实前暂停重复执行；无法核实时，说明已知状态及缺失的信息，保持相关操作暂停。

## 3. 收尾与交接

核对通过后，在原对话中汇总本次成果。

根据已确认的讨论结果和已有资料，提出下一步建议：

- 需要制定技术方案和实施计划时，建议进入 2方案。
- 已有满足 3实现输入要求的已确认 Spec 和必要 Tickets 时，可以建议直接进入 3实现，并说明依据。

下一阶段的 Skill 可用情况，根据收尾时针对目标项目的完整登记信息核实。仅核对启用状态和入口可读取性，不加载正文。结果报告脚本的 `--next-skill-available` 参数按以下规则填写：

- `true`：已核实对应 Skill 已启用且入口可读取。
- `false`：已确认对应 Skill 不存在、已禁用或入口无法读取。
- `unknown`：查询失败或无法确定采用哪个入口。说明具体问题，照常报告已验收的本阶段成果，仅暂停对应交接。

使用 Python 3 调用[结果报告脚本](scripts/render-result.py)。脚本路径使用当前已加载 Skill 中的实际绝对路径。

报告包含：

- 本次拷问摘要和已确认结论。
- 本次实际维护或生成的文档及其位置；没有文档产物时如实说明。
- 本阶段总耗时。
- 建议进入的下一阶段及理由。
- 下一阶段对应 Skill 的可用情况。

将脚本标准输出中的 Markdown 原样展示给用户，等待用户选择：

- 用户明确同意进入 2方案且对应 Skill 已核实可用时，读取已核实的 `solution-design` 完整正文，传入本次讨论结果、资料位置、目标项目及仍有效的执行要求，按其原流程执行。
- 用户明确同意进入 3实现且对应 Skill 已核实可用时，读取已核实的 `guided-implementation` 完整正文，传入已确认的 Spec、必要 Tickets、目标项目及仍有效的执行要求，按其原流程执行。
- 用户选择的 Skill 当前无法使用时，暂停对应交接，等待用户检查其安装、启用状态及入口。
- 用户选择的 Skill 可用情况尚未核实时，先重新核实，再按对应分支处理；仍无法核实时，保持交接暂停并说明具体问题。

脚本执行失败时，按照“意外中断”的处理要求处理。

# 结果与完成条件

## 验收标准

核对讨论结果及本次实际维护或生成的文档：

- `grill-with-docs` 已按原流程执行完成，用户已确认双方理解一致。
- 最终结论准确保留本次讨论中仍有效的目标、范围、约束和决定，没有将待讨论内容或未经确认的建议作为已确认结论。
- 进入时已有讨论文档的，已继续维护，最终内容与讨论结果一致。
- 原 Skill 要求的术语表、ADR 等适用工作已完成。
- 新对话执行时，完成结果已传回原对话，已返回原对话，后续交接在原对话中进行。
- 下一阶段建议有实际依据，所引用资料存在且能够读取。

## 完成条件

拷问已完成，结果核对通过，适用的文档维护和必要回传已完成，且没有影响本阶段交付的未解决事项时，本阶段完成。

发现遗漏或不一致时，按照任务完成分支补充或修订；执行中断时，按照意外中断分支处理。
