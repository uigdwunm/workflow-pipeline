本 Skill 编排 `grill-with-docs`。拷问、术语表和 ADR 等工作的执行要求以该 Skill 及其依赖为准，本 Skill 补充执行对话的选择、已有讨论文档的维护和结果交接要求。

本 Skill 默认连续接续后续阶段。用户明确限定执行范围时，在指定阶段结束；仅调用本 Skill 不视为只执行本阶段。

首次进入本阶段时取得包含时区的 ISO 8601 开始时间，写入任务进度文件；接续时沿用本轮记录，供收尾脚本计算耗时。

# 输入与前置条件

## 输入

接受当前对话中已讨论的内容，也接受用户指定的文件、issue、链接或其他资料。

根据用户请求和现有上下文，明确：

- **拷问依据**：本次使用哪些内容作为依据。用户指定资料时，以其指定的资料和范围为准。
- **拷问目标**：用户希望讨论和澄清什么问题，以及已经明确的范围和约束。
- **目标项目**：本次讨论属于哪个项目，需要结合哪个代码库或项目背景。

这些信息已明确时直接使用；无法确定时，只针对影响拷问的缺口向用户确认。

目标项目和本次任务明确后，先按[任务进度](#任务进度)创建或复用进度文件，再继续前置检查。已有交接时接收同一进度文件的绝对路径、任务标识和原目标项目的绝对路径。

指定资料无法读取或缺少必要内容时，说明具体问题并请用户补充。多个来源存在影响讨论的矛盾、且无法确定采用哪个时，向用户确认。

## 已有讨论文档

进入本 Skill 时，检查此前的对话是否已经为本次讨论持续维护文档。

这类文档不要求使用特定名称或格式。根据当前讨论和用户指定资料确定其归属，记录实际路径或链接；无法确定且会影响维护对象时，向用户确认。

- 已有讨论文档时，在执行 `grill-with-docs` 的过程中继续维护，沿用其结构，及时记录讨论结果，并区分已确认内容与待讨论内容。
- 没有已有讨论文档时，本阶段不额外创建这类文档。

已有讨论文档的维护是补充工作，任务进度文件由原对话维护。`grill-with-docs` 原有的术语表维护、ADR 等工作仍按原流程执行。

## 前置条件

确认 `grill-with-docs` 的实际入口可读取，并核实其要求的 `grilling` 和 `domain-modeling` 可用。

用户明确指定 Skill 入口时，使用其指定入口。未指定时，从当前宿主针对目标项目的完整 Skills 登记信息中，按精确名称核实启用状态和实际入口。

前置检查仅核对登记信息和入口可读取性，不加载 Skill 正文。

优先使用宿主已有的完整登记查询能力。Codex 没有直接查询工具时，使用 Python 3 调用本 Skill 的[登记查询脚本](scripts/list-skills.py)，传入 `--cwd '/目标项目的实际绝对目录'`，按本次需核实的名称重复传入 `--name`，例如 `--name grill-with-docs --name grilling --name domain-modeling`；脚本路径使用当前已加载 Skill 中的实际绝对路径。其他宿主使用自身提供的完整查询能力。

脚本仍查询和校验完整登记，仅筛选输出；同名多入口全部保留，`missing` 列出未登记名称。`ok: true` 只表示查询成功，仍须核对缺失项、启用状态及入口可读取性。省略 `--name` 时输出完整名单。

查询结果至少包含每项的名称、实际入口和启用状态。初始 Available Skills 名单不作为完整登记信息；关闭隐式调用不视为禁用。

依赖不存在、已禁用、入口无法读取、同名多入口且无法确定采用哪个，或查询失败时，说明具体问题并暂停依赖该 Skill 的工作，按[意外中断规则](references/clarification-flow.md#意外中断)处理。安装、启用状态或入口发生变化后，重新核实。

输入明确且前置条件满足后，进入执行流程。

# 本地文本写入

遵守目标项目的文件写入约定，优先使用宿主文件编辑工具。使用 Python 写入文本时，在源码前两行声明 `# coding: utf-8`，文件读写显式指定 `encoding="utf-8"`。长文正文使用多行文本或独立数据输入，避免嵌成超长单行源码。交给新对话或子 Agent 执行时，传递本节要求。

# 任务进度

使用本 Skill 的[进度脚本](scripts/task-progress.py)，由原对话维护本任务唯一的临时 Markdown 文件。只记录以下大步骤的完成结果，步骤名称由脚本内置：

| 序号 | 大步骤 |
| --- | --- |
| 1 | 确认讨论要点 |
| 2 | 执行拷问 |
| 3 | 验收与交接 |

创建前，区分原目标项目与本次执行工作区。优先沿用已有交接中的原目标项目；首次进入时，根据用户指定的项目及已知仓库关系核实，不直接将当前 `cwd` 或临时 Worktree 作为原目标项目。用户明确指定 Worktree 为目标项目时遵从其要求。执行工作区变化不改变已确定的任务归属。

首次进入体系时，遵守目标项目的写入约定，选择用户指定或项目约定的位置；没有约定时，使用宿主现有临时目录中的唯一文件路径。文件位于临时 Worktree 之外，父目录须已存在。用一次 `create` 创建文件并保存本阶段开始时间：

```sh
python3 '/Skill绝对路径/scripts/task-progress.py' create \
  --output '/本任务进度文件绝对路径' \
  --project '/原目标项目绝对路径' \
  --summary '本任务原始要解决的问题和目标' \
  --stage 1 --at '进入本阶段时取得的含时区ISO时间'
```

保存返回的 `file`、`task_id`、`project` 和本轮 `started_at`。已有交接时，沿用同一文件，用 `show` 核对归属和实际成果，再用 `enter --stage 1` 进入或复用本阶段；首次追加时用 `--at` 传入本阶段实际开始时间，接续时复用原时间。后续命令均传入同一组 `--file`、`--task-id` 和 `--project`。接续文件缺失、损坏或归属不明时，先核实并保留已有信息，不能另建文件替代。

使用 `complete --steps` 登记已完成的大步骤，参数为非空 JSON 列表；单步也使用一个元素的列表。每项包含整数 `step` 和单行 `note`，可选含时区的 ISO 8601 时间 `at`；必要的成果位置写入 `note`：

```sh
python3 '/Skill绝对路径/scripts/task-progress.py' complete \
  --file '/本任务进度文件绝对路径' \
  --task-id '创建时返回的任务标识' \
  --project '/原目标项目绝对路径' \
  --stage 1 --steps '[{"step":1,"note":"本大步骤的实际完成结果"}]'
```

未提供 `at` 的列表项统一使用本次登记时间；已有可靠事件时间时填入该项的 `at`。列表中的步骤须连续递增，不能重复、乱序或跳过未完成步骤。整批校验通过后一次写入，任一项失败则原记录不变。最后一个大步骤完成时自动结束阶段。更新只返回简短回执；恢复任务或生成报告需要完整记录时才用 `show`。同一结果重试保留首次时间；已完成的步骤保持原记录，必要返工在当前未完成大步骤的最终结果中简述。

默认完成一步即登记；连续完成的简短步骤可合并为一次列表登记。遇到等待、中断或较长执行前，先保存已完成进度，不为凑批次延迟记录。依赖已登记进度的操作仍按顺序执行；先登记报告所需的前序步骤，再生成报告，成功后登记最后一步。

普通确认、等待和中断不更新文件；恢复时核对实际成果，从尚未完成的大步骤接续，沿用本轮开始时间。阶段用时按起止时间计算，包含阶段内等待，不包含阶段间等待。后续阶段传递同一进度身份及必要成果信息；执行工作区变化不改变原目标项目。

确实重新执行已结束阶段时用 `enter --new-run` 追加一轮。明确取消当前阶段或改走其他阶段时，用 `stop --stage 1 --note '具体原因'` 保留已完成记录并结束本轮；暂停和等待不使用 `stop`。整个任务明确结束且结果报告已保留后，按项目清理授权调用 `cleanup --task-finished`。等待接续时保留文件。

# 执行流程

## 1. 总结相关讨论并取得确认

先向用户总结前面相关讨论中的目标、已有想法与决定、范围和约束、未决问题，同时说明默认连续执行后续阶段；用户已明确限定阶段时，说明对应执行范围。模型推断的内容单独标明，不作为用户已确认的结论。

用户确认后再进入拷问；用户纠正或补充时，更新相关要点并取得确认。没有足够前文时，简要列出已知内容和必要缺口。此处确认的是理解是否准确，不代表想法已经通过检查。

理解确认后，用 `complete --stage 1 --steps '[{"step": 1, "note": "本步骤的实际完成结果"}]'` 记录已确认目标、范围和讨论要点的一句结果，传入同一进度身份，结果填入列表项的 `note`。

## 2. 判断并进入分支

根据用户确认的讨论要点自行判断；实在无法判断时，询问用户当前想法的状态，不要求用户手动选择分支。

**确认想法**：想法仍需澄清时，执行[完整拷问流程](references/clarification-flow.md)。

**查漏补缺**：已有较明确的想法，主要希望检查遗漏时，携带以下补充要求执行[完整拷问流程](references/clarification-flow.md)：

- 以用户已确认的讨论要点为基线，重点检查遗漏、矛盾和关键假设。
- 先结合已有讨论和项目事实检查，复用已有明确答案；发现已有决定存在问题时，说明依据和影响，再与用户讨论。
- 围绕影响当前目标的遗漏、矛盾和关键假设提问，说明建议；事实问题自行查明，需要用户作出的决定交给用户。现有行为能够满足目标时，以保持该行为为基线；替代设计只有在解决本次问题确有必要，或用户明确要求比较方案时，才纳入讨论，不将无关优化变成必须回答的待决问题。

讨论、文档维护和最终确认仍按 `grill-with-docs` 及其依赖的要求完成。

## 拷问末尾的测试范围

在拷问接近收敛、最终确认双方理解一致前，结合任务目标、改动风险和项目已有约定，判断本任务是否需要明确测试范围。需要时，提出拟覆盖的行为和关键场景、明确排除项（如有）及必要的验证方式，说明建议依据，将尚需用户决定的部分纳入本轮最终确认。已有明确确认的内容直接复用；任务无需明确测试范围时，跳过这项提问。

本阶段确认足以约束后续方案和验收的测试边界；依赖技术方案才能确定的模块划分、具体用例和工具选择，留给方案阶段在该边界内细化。仍需后续决策的事项如实标为未决。

将适用的测试范围结论、用户确认依据及仍未解决的事项随最终结论保留，供后续阶段复用。

# 结果与完成条件

## 最终交付

阶段结束时，在原对话中原样、完整、展开地展示[结果报告脚本](scripts/render-result.py)生成的 Markdown，包括成果及适用的下一阶段建议和交接提示。连续模式且下一阶段可直接接续时，使用可继续执行的进度消息，展示后再进入下一阶段；用户限定本阶段结束、需要等待用户决定或交接受阻时，使用最终回复展示报告。补充的结论摘要放在报告之外，不能替代报告。

用户明确限定执行范围时，按其指定的结束阶段交付，不再询问是否进入范围之外的阶段。用户明确要求省略后续阶段建议时，按其指定范围调整报告。

## 验收标准

核对讨论结果及本次实际维护或生成的文档：

- `grill-with-docs` 已按原流程执行完成，用户已确认双方理解一致。
- 已按[拷问末尾的测试范围](#拷问末尾的测试范围)完成适用判断；需要明确测试范围时，最终结论保留已确认边界、确认依据及尚待方案阶段解决的事项。
- 最终结论准确保留本次讨论中仍有效的目标、范围、约束和决定，没有将待讨论内容或未经确认的建议作为已确认结论。
- 进入时已有讨论文档的，已继续维护，最终内容与讨论结果一致。
- 原 Skill 要求的术语表、ADR 等适用工作已完成。
- 新对话执行时，完成结果已传回原对话，已返回原对话，后续交接在原对话中进行。
- 有下一阶段建议时，建议有实际依据，所引用资料存在且能够读取。
- 准备发送的阶段结果消息已按[最终交付](#最终交付)核对，交接内容与当前用户要求、连续模式和下一阶段 Skill 的可用状态一致。

## 完成条件

拷问已完成，结果核对通过，适用的文档维护和必要回传已完成，且没有影响本阶段交付的未解决事项，并满足以下条件时，本阶段完成：

- 大步骤结果及阶段起止时间已写入同一进度文件，后续接续所需的进度身份已准备好。

- 完整报告已按[最终交付](#最终交付)展示给用户，并按其中的交接提示接续、结束或等待决定。报告生成成功和进度登记成功不替代最终交付。

发现遗漏或不一致时，按照[任务完成要求](references/clarification-flow.md#任务完成)补充或修订；执行中断时，按照[意外中断规则](references/clarification-flow.md#意外中断)处理。
