# 完整拷问流程

## 1. 选择执行方式并执行

先确认当前环境是否具备本流程所需的新对话能力，包括：

- 在目标项目下创建新对话，并提交首条消息。
- 用户能够在新对话中继续讨论。
- 可靠取得并核实原对话的身份。
- 将完成结果传回原对话，并使原对话接续执行。
- 将界面返回原对话。

不具备上述完整能力时，由当前对话执行。

具备上述完整能力时，根据本次讨论所需的信息判断：

- 当前对话中有大量相关信息，需要结合原始讨论继续梳理和澄清时，由当前对话执行，利用当前已经积累的上下文。
- 所需资料基本集中在用户指定的文件或其他明确资料中时，准备资料引用和必要的初始信息，使用新对话执行。
- 所需信息主要在对话中，但数量较少、能够快速完整提取时，先整理完整的初始信息，再使用新对话执行。
- 具备上述完整能力，但不满足上述新对话适用条件时，由当前对话执行。

确定执行方式后：

- 当前对话执行：读取并执行[当前对话执行说明](main-execution.md)。
- 新对话执行：读取并执行[新对话执行说明](new-conversation-execution.md)。

仅读取并执行所选分支的执行说明。

执行完成且新对话路径的结果已返回原对话后，用 `complete --stage 1 --steps '[{"step": 2, "note": "本步骤的实际完成结果"}]'` 记录一句执行结果，传入 [SKILL.md“任务进度”](../SKILL.md#任务进度)中的同一进度身份，结果填入列表项的 `note`，再进入结果处理。分支和执行过程不单独登记。

## 2. 处理执行结果

### 任务完成

按照[验收标准](../SKILL.md#验收标准)核对讨论结果和实际文档。阶段记录和结果报告在收尾中完成。

已经完成的用户确认可以复用，无需在原对话重复确认同一内容。

核对通过后，进入收尾与交接。发现遗漏或不一致时，交回原执行对话补充或修订，再重新核对。

### 意外中断

发生执行异常时，先核对实际状态和已有操作结果。

能在已有授权和已确认的设计范围内恢复时，自行处理，完成必要验证后继续。子 Agent 无法继续时，向主对话报告，由主对话核实进展并安排接续。

主对话收到子 Agent 或其他对话的模型繁忙、容量不足等临时服务错误提示时，等待 30 秒后重试；仍出现同类错误时，再分别等待 60 秒、120 秒重试。最多重试 3 次；仍未恢复时，暂停相关接续，按现有中断规则向用户报告。

需要用户作出新的决定、补充授权，或无法核实已有操作结果时，暂停受影响的工作，向用户说明问题、已完成内容、未完成事项及继续所需的信息或决定。等待期间，可以继续不依赖该决定的工作。

用户另有明确的停工或报告要求时，按用户要求执行。

用户决定继续后，用 `show` 核对同一进度文件，并核对已有讨论、实际文档和执行状态，仅继续尚未完成的工作；暂停和恢复不单独写入进度。

创建新对话或回传结果不明确时，先核实原操作，核实前暂停重复执行；无法核实时，说明已知状态及缺失的信息，保持相关操作暂停。

## 3. 收尾与交接

核对通过后，在原对话中汇总本次成果。

根据已确认的讨论结果和已有资料，提出下一步建议：

- 需要制定技术方案和实施计划时，建议进入 2方案。
- 已有已确认的 Spec 和必要 Tickets，或已确认改动的目标和范围明确、影响局部、风险低、没有未决的重要设计取舍，且能够通过一次短小连贯的实现完成时，可以建议直接进入 3实现，并说明依据。进入后由 `guided-implementation` 按其路径规则核对；不符合小改动条件时，由其建议进入 2方案并等待用户决定。

下一阶段的 Skill 可用情况，根据收尾时针对目标项目的完整登记信息核实。仅核对启用状态和入口可读取性，不加载正文。

使用 Python 3 调用[结果报告脚本](../scripts/render-result.py)。脚本路径使用当前已加载 Skill 中的实际绝对路径。

调用示例，替换为本次任务的实际参数：

```sh
python3 '/Skill绝对路径/scripts/render-result.py' \
  --summary '本次拷问摘要和已确认结论' \
  --artifacts '[]' \
  --started-at '2026-10-10T09:00:00-07:00' \
  --recommended-stage 2 \
  --recommendation '需要制定技术方案和实施计划' \
  --continuous-mode false \
  --next-skill-available true
```

| 参数 | 内容 |
| --- | --- |
| `--summary` | 本次拷问摘要和已确认结论，包含适用的测试范围结论及仍未解决的事项；确认依据可引用实际讨论或文档位置。 |
| `--artifacts` | 本次实际维护或生成的文档，使用 JSON 数组，每项仅包含 `name` 和 `location`，分别填写成果名称及实际绝对文件路径或 HTTP(S) 链接，两者均为非空单行文本。没有文档产物时传入 `[]`。 |
| `--started-at` | 同一进度文件中本轮 1拷问的 `started_at`，接续时沿用。 |
| `--recommended-stage` | 根据已确认讨论结果建议进入的阶段：`2` 为 2方案，`3` 为 3实现。 |
| `--recommendation` | 建议进入该阶段的理由。 |
| `--continuous-mode` | 根据本次任务最新的用户要求判断。已明确要求连续模式且没有撤销或缩小该要求时为 `true`，否则为 `false`。 |
| `--next-skill-available` | 根据完整登记信息和入口可读取性判断：已核实可用时为 `true`，已确认不存在、已禁用或入口无法读取时为 `false`，查询失败或无法确定采用哪个入口时为 `unknown`。为 `unknown` 时说明具体问题，照常报告已验收成果，仅暂停对应交接。 |

连续模式用于自动衔接后续阶段；各阶段内部的设计确认、授权和验收仍按原规则执行。

报告脚本成功返回后保留完整标准输出，按[最终交付要求](../SKILL.md#最终交付)准备并核对最终回复。非连续模式且下一阶段可用时，核对回复包含进入询问和连续模式选项；连续模式或 Skill 不可用、尚未核实时，核对回复保留对应的接续或受阻说明。

最终回复核对通过后，以实际报告生成完成时刻调用 `complete --stage 1 --steps '[{"step": 3, "note": "成果验收通过，报告和交接资料已准备", "at": "实际报告生成完成时刻的含时区ISO时间"}]'`，传入同一进度身份。脚本自动结束阶段；等待用户选择不计入已结束的阶段。写入失败时保留报告和原文件，核实后补齐记录再交接。

收到成功回执后，将已核对的报告放入最终回复，根据报告中的交接提示执行：

- 报告提示直接进入建议阶段时，立即按下文对应分支调用 Skill。
- 报告询问用户时，等待回复。用户明确同意进入下一阶段时，按其选择调用；明确要求开启连续模式时，记录该要求后，按用户指定或报告建议的阶段继续。仅同意进入下一阶段，不视为开启连续模式。
- 报告提示对应 Skill 当前无法使用时，暂停对应交接，等待用户检查其安装、启用状态及入口。
- 报告提示可用情况尚未核实时，先重新核实，再按对应可用状态处理。核实可用后，沿用已记录的用户选择或连续模式要求继续；没有相应要求时，等待用户选择。仍无法核实时，保持交接暂停并说明具体问题。

用户选择不同于报告建议的阶段时，先核实其对应 Skill 的可用情况，再按同样规则处理。交接分支如下：

- 进入 2方案：读取已核实的 `solution-design` 完整正文，传入本次讨论结果、资料位置、目标项目及仍有效的执行要求，包括是否开启连续模式，按其原流程执行。
- 进入 3实现：读取已核实的 `guided-implementation` 完整正文，按实际情况传入已确认的 Spec 和必要 Tickets，或已确认的改动要求、范围、约束及已有验收约定，并传入目标项目及仍有效的执行要求，包括是否开启连续模式，按其原流程执行。

交接至 2方案或 3实现时，一并传递适用的测试范围结论、用户确认依据及未决事项，以及本次文档成果的实际位置及已知的提交状态，供下一阶段复用已确认内容并核对工作区中的内容和交付范围。传递同一进度文件的绝对路径、任务标识和原目标项目的绝对路径，要求沿用本任务唯一的进度文件。等待接续时保留文件；整个任务明确结束后，按 [SKILL.md“任务进度”](../SKILL.md#任务进度)中的清理规则处理。

脚本执行失败时，按照“意外中断”的处理要求处理。
