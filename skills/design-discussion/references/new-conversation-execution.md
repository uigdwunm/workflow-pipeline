本说明由原对话执行，负责新对话的启动、结果接收和返回后的接续。

交接信息中沿用同一进度身份及 `execution_scope`，区分任务执行终点与本次拷问的委派职责；范围由原对话维护，回传完成后仍由原对话处理后续接续。

准备新对话前，由原对话先通过[完整流程的入口检查](clarification-flow.md)，取得本轮已确认的 `points` 及 `confirmation`。由本说明直接恢复执行时也先检查；新对话接收已确认内容，沿用同一确认记录。

# 1. 确定模型与强度

用户或其他适用提示词已规定模型、推理强度或选择规则时，按相应要求执行。以下默认规则仅补充未被约定的部分。

通过当前宿主已有的工具说明、查询能力、配置或会话信息，获取当前对话设置、用户默认设置，以及可用于新对话的模型和各模型支持的推理强度。

默认以当前对话模型和用户默认模型中较贵的那个作为价格上限，根据本次拷问需要选择不超过该上限的可用模型。模型能力和模型下限不作限制。

比较价格时，优先使用已有知识，不为此专门联网查询。用户默认模型无法获取，或无法可靠比较价格时，按下文的回退规则处理。

推理强度根据任务需要，在所选模型支持的档位中选择，不受当前对话或用户默认强度限制。

在创建新对话时，通过宿主支持且允许的方式应用所选设置。

模型或推理强度无法确定时，优先沿用当前对话的模型和强度；无法沿用时，使用宿主默认的模型和强度。使用宿主支持的继承或默认机制时，无需额外查明具体值。

宿主无法应用明确要求的设置时，按照 [完整流程中“意外中断”的处理要求](clarification-flow.md#意外中断)处理。

# 2. 准备执行信息

使用 [SKILL.md 的“输入与前置条件”](../SKILL.md#输入与前置条件)中已经明确的内容，取得目标项目的实际绝对目录，以及已经核实的原对话标识。

创建工具需要项目标识时，通过宿主的项目查询能力取得，核对其属于目标项目。

原对话标识必须来自可核实的宿主会话信息，不能使用对话标题、列表顺序或协作 Agent 标识代替。

核对本次创建新对话、应用所选模型与强度、必要的对话间消息和界面切换是否已有明确授权。已有授权覆盖时直接使用；缺少时，向用户说明具体对象和操作，取得明确同意后继续。

宿主要求用户明确指定具体模型时，将选定的模型和强度纳入本次创建确认。已有明确指定时直接使用，无需重复确认。

记录结果和中断报告回传的授权范围及可核实的用户确认出处，作为新对话的回传授权信息传入。创建、模型设置等启动信息由原对话保留。

# 3. 生成首轮提示词

根据已经明确的任务内容和执行信息，准备以下参数。

使用 Python 3 调用[首轮提示词生成脚本](../scripts/render-new-conversation-prompt.py)。调用时使用当前已加载 Skill 中该脚本的实际绝对路径。

| 参数 | 生成要求 |
| --- | --- |
| `--project` | 目标项目的实际绝对目录，目录必须已存在。 |
| `--goal` | 根据用户请求，整理本次希望讨论和澄清的问题，以及预期结果。使用非空文本。 |
| `--context` | 完整传递入口检查返回的 `points` 及 `confirmation`，以及新对话所需的背景、项目特有术语说明、范围、约束、已有决定和待讨论内容，保留其实际确认状态。展开依赖原对话才能理解的指代，包含已核实的 `grill-with-docs` 实际入口，以及与本次讨论和文档维护相关的用户要求。使用非空文本，可分行描述。 |
| `--sources` | 列出本次需要参考的实际资料。使用 JSON 数组，每项仅包含 `name` 和 `location`，分别填写资料名称及绝对文件路径或 HTTP(S) 链接，两者均为非空单行文本。没有额外参考资料时传入空数组。 |
| `--discussion-documents` | 列出进入本阶段时已有讨论文档的名称和实际位置。使用与参考资料相同的 JSON 格式；没有时传入空数组。 |
| `--origin-thread-id` | 已经可靠取得并核实的原对话标识，供完成或中断时回传结果。 |
| `--return-authorization` | 结果和中断报告回传的已有用户授权范围及可核实的确认出处。使用非空文本，可分行描述。 |
| `--notes` | 传入所选分支的补充要求、同一进度文件的绝对路径、任务标识和原目标项目。说明进度由原对话维护，新对话回传结果，不创建或更新进度文件。 |

保存脚本标准输出中的完整提示词，对照当前有效讨论核对目标、范围、约束、决定、待讨论内容、实际入口和回传授权信息。核对新对话仅凭提示词及所引用资料即可理解任务；模型选择和创建过程等启动信息由原对话保留。

提示词应明确新对话已经是本次拷问的执行对话，直接调用 `grill-with-docs`；结果核对和后续交接由原对话负责。

需要修正时，调整参数后重新生成。核对准确后，将完整提示词原样作为新对话的首条消息。

脚本执行失败时，按照 [完整流程中“意外中断”的处理要求](clarification-flow.md#意外中断)处理。

# 4. 创建并确认启动结果

使用当前宿主的原生新对话工具，在目标项目下创建新对话，应用已确定的模型和强度，或使用前述继承或默认机制，将生成的提示词原样作为首条消息提交。

使用目标项目现有工作目录。

记录工具返回的新对话标识和创建回执，供后续检查、通信和接续使用。

“创建成功”必须同时满足：

- 新对话已创建，所属项目正确。
- 已取得可用于后续操作的真实对话标识。
- 首条提示词已成功提交。
- 模型和强度已通过宿主支持的方式应用；使用继承或默认机制时，已按对应机制创建，无需额外查明具体值。

异步启动时，通过宿主原生状态查询或等待能力核实启动结果。仅取得临时标识或结果尚不明确时，保留已有回执，继续核实；无法核实时，按照意外中断要求处理，核实前暂停重复创建。

确认创建成功后，打开新对话，供用户继续讨论。

原对话保留本次输入、开始时间和新对话标识，进入结果等待。

# 5. 等待并处理新对话结果

创建成功后，原对话暂停主动推进拷问和后续交接，使用宿主原生等待或结果回传机制，等待新对话的完成结果或中断报告。

用户直接在新对话中回答问题并完成确认。等待用户回答或一轮回复结束，仍属于拷问执行过程。

## 任务完成

新对话按照首轮提示词，在 `grill-with-docs` 原流程、所需用户确认和适用的文档维护完成后，向原对话回传明确的完成结果，包括：

- 本次讨论的最终结论。
- 实际维护或生成的文档及其位置；没有文档产物时如实说明。
- 用户确认双方理解一致的情况及可核实的依据。

原对话收到完成结果后，核对其来自本次创建的新对话，且属于本次任务。

使用宿主原生导航能力返回并打开原对话。确认返回成功后，由原对话返回主流程登记“执行拷问”完成，按[任务完成要求](clarification-flow.md#任务完成)验收讨论结果和实际文档。通过后继续[收尾与交接](clarification-flow.md#3-收尾与交接)，调用报告脚本并在原对话中原样展示完整报告，最后按执行范围接续或结束。

需要补充或修订时，将具体问题反馈给同一个新对话。需要继续与用户讨论时，打开该新对话；补充或修订完成后，重新接收完成结果并返回原对话核对。

## 意外中断

收到新对话的中断报告，或创建、通信、返回过程中发生导致流程无法继续的意外时，按照 [完整流程中“意外中断”的处理要求](clarification-flow.md#意外中断)处理。

用户决定继续后，先核对已有讨论、文档和实际执行状态，将已核实的进展及剩余工作传给原新对话，仅继续尚未完成的工作。

结果尚不明确的操作，核实前保持暂停。
