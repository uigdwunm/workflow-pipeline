本 Skill 编排 Matt 系列的 `implement-spec`，以其原流程为基础，补充本次实现所需的执行要求。

进入本 Skill 时，记录包含时区的 ISO 8601 开始时间，供收尾脚本计算总耗时。

# 输入与前置条件

## 输入

根据本次已确认的 Spec 和必要的 Tickets 开展实现。资料可以来自当前对话，也可以是用户指定的文件、issue、链接或其他资料。

根据用户请求和现有上下文，明确：

- **实现依据**：本次使用哪些 Spec 和 Tickets。用户指定资料时，以其指定的资料和范围为准。
- **实现目标**：用户希望实现什么结果，以及已经明确的范围、约束和决策。
- **目标项目**：实现属于哪个项目，需要在哪个代码库中执行。

这些信息已明确时直接使用；无法确定时，只针对影响实现的缺口向用户确认。

指定资料无法读取或缺少必要内容时，说明具体问题并请用户补充。多个来源存在影响实现的矛盾、且无法确定采用哪个时，向用户确认。

复用方案中已确认的测试边界；缺少必要的测试边界约定时，按 `tdd` 原流程完成确认。

## 前置条件

- 从当前宿主针对目标项目的完整 Skills 登记信息中，按精确名称确认 `implement-spec`、`tdd` 和 `code-review` 已启用，并核对实际入口可读取，记录三项入口。前置检查仅核对登记信息和入口可读取性，不加载 Skill 正文。
- 目标项目的 `docs/agents/issue-tracker.md` 已存在且可读取，issue tracker 及任务关闭方式约定已明确。读取并复用该文件中的约定；文件缺失时，提示用户先运行 `$setup-matt-pocock-skills` 完成配置。文件无法读取或约定缺少必要内容时，报告具体问题并按意外中断规则处理。

优先使用宿主已有的完整登记查询能力。Codex 没有直接查询工具时，使用 Python 3 调用本 Skill 的[登记查询脚本](scripts/list-skills.py)，传入 `--cwd '/目标项目的实际绝对目录'`；脚本路径使用当前已加载 Skill 中的实际绝对路径。其他宿主使用自身提供的完整查询能力。查询结果至少包含每项的名称、实际入口和启用状态。初始 Available Skills 名单不作为完整登记信息；关闭隐式调用不视为禁用。

查询必须成功且完整。登记中不存在的依赖，提示用户从 [Matt 官方 Skills 仓库](https://github.com/mattpocock/skills) 安装；已登记但禁用的依赖，提示启用。入口无法读取、同名多入口且无法确定采用哪个，或查询失败时，说明具体问题并暂停依赖该 Skill 的工作，按意外中断规则处理。安装、启用状态或入口发生变化后，重新查询。原生流程实际需要其他条件性依赖时，按同一规则定位其入口。

输入明确且前置条件满足后，进入执行流程。

# 本地文本写入

遵守目标项目的文件写入约定，优先使用宿主文件编辑工具。使用 Python 写入文本时，在源码前两行声明 `# coding: utf-8`，文件读写显式指定 `encoding="utf-8"`。长文正文使用多行文本或独立数据输入，避免嵌成超长单行源码。交给新对话或子 Agent 执行时，传递本节要求。

# 执行流程

## 1. 确定工作区

检查当前对话是否已有属于目标项目的独立 Worktree。复用前，核对 Worktree 的实际仓库、分支和代码基线是否符合本次任务要求，并确认已有工作归属及是否存在其他写入者。

适合本次任务时复用，保留已有修改；不适合时选择其他合适的独立 Worktree。没有合适的独立 Worktree 时，创建一个。

将选定的 Worktree 作为本次实现的集成工作区。无法确定归属或协调写入，或无法确定或创建工作区时，说明具体问题并向用户询问。

## 2. 调用 implement-spec

### 准备输入

使用“输入与前置条件”中已明确的实现依据、目标、范围、约束和项目约定，准备本次调用所需的信息及资料引用。

附带已核实的 `implement-spec`、`tdd` 和 `code-review` 实际入口，将这些执行信息与用户的设计要求分开说明。

确定并记录覆盖本次实现范围的审查基准提交。已有明确基准时复用；没有时，根据本次实现范围确定，包含本次任务已有的实现改动。

确认当前环境是否具备本流程所需的子 Agent 协作能力，包括：

- 在当前主对话下创建子 Agent，并提交首条消息。
- 主对话与该子 Agent 双向通信。
- 主对话等待并接收该子 Agent 的完成或中断消息。

### 整理补充要求

根据以下条件附带要求：

- **Skill 入口传递**：向需要使用 `tdd` 或 `code-review` 的执行者传递已核实的实际入口；使用时先读取完整正文，再执行原流程。实际需要其他条件性依赖时，由主对话按前置条件中的完整登记查询规则定位并传递入口。入口无法读取或需要重新定位时，向主对话报告并暂停相关工作。
- **集成工作区**：使用已选定的 Worktree 作为集成工作区，在其中复用或创建本次实现的集成分支。
- **最小完整实现**：完成满足当前已确认 Spec 和 Tickets 的最小完整实现。新增复杂度应有明确的需求依据，避免为尚未确认的未来需求增加额外抽象、通用框架或扩展机制。
- **设计边界**：

  可以自行补充已商量好的主体流程和设计框架内的实现细节，保持已确认的目标、功能范围、对外行为、约束和关键设计决策。

  以下情况需要用户确认：

  - 需要改变已确认内容。
  - 需要增加额外设计或机制。
  - 补充细节需要改动既有重要设计。

  已有明确授权覆盖对应变化时，无需重复确认。上述要求同样适用于审查后的整改。方案调整及必要决策缺口按下文“方案更新与同步”处理。

- **已确认设计要点**：Spec 或 Tickets 中有已确认设计要点时，实现每个 Ticket 前读取其中适用的要点。向相关实现和审查子 Agent 提供要点编号及 Spec 位置，可以使用资料引用。审查时核对这些要点是否落实。需要修改、撤销或偏离某条要点时，说明对应编号、原约定、拟议变化、原因和影响，按设计边界中的规则处理。
- **方案更新与同步**：

  子 Agent 发现方案需调整或缺少必要决策时，先暂停相关工作并向主对话报告缺口，或说明拟修改内容、原因及影响。

  主对话通知所有受影响的子 Agent 暂停相关工作，并确认它们已暂停；按设计边界判断是否需要用户确认，并取得必要的用户决定。内容明确后，更新 Spec 和相关 Tickets，将变更内容及最新资料位置发给这些子 Agent，通知它们重新读取，并核对已有工作是否需要调整。

  主对话重新检查剩余 Tickets 的依赖关系和执行安排，完成同步和调整后再继续。

- **审查依据**：调用 `code-review` 时，提供已记录的审查基准提交，以本次确认的 Spec 和必要的 Tickets 作为 Spec 审查依据。
- **审查后的整改与复查**：完成整改后，对整改内容及受影响范围重新审查，确认原问题已解决，且没有引入影响本次交付的新问题。仍有经核实需要整改的问题时，继续整改和复查，通过后再收尾。
- **集成与最终验证**：合并相互关联的 Tickets 或修改公共接口、共享逻辑后，及时运行受影响的集成检查。审查和整改完成后，在最终集成提交上完成项目要求的交付验证。最终实现发生变化时，重新完成必要检查。复用已有测试或审查结论时，确认对应内容、相关依赖和共享部分均未受后续改动影响。
- **重复问题的诊断与整改**：同一问题修复后再次出现、相关路径出现同类问题，或连续审查和测试表明同一实现方式存在问题时，先诊断再继续整改。优先由当前负责整改的执行者对照此前的问题与修复，说明修复无效的原因，确定能捕获该问题的最小有效验证，并检查相关路径是否受到影响。根据诊断结果整改，再按既有要求完成验证和复查。
- **使用子 Agent 时的模型与强度**：读取[模型与强度规则](references/agent-settings.md)，作为探索、实现、合并和审查子 Agent 的创建要求一并传入。向负责创建子 Agent 的执行者提供该文件的实际绝对路径。
- **子 Agent 中断与接续**：无法继续时，向主对话说明当前处理的 Ticket 或 Spec、正在执行的步骤、中断原因、已完成和未完成的工作、已有成果的实际位置，以及结果尚不明确的操作。保留已有成果，暂停后续执行，等待主对话核实进展并给出处理结论。收到结论后，仅继续尚未完成的工作；创建、合并或发布结果尚不明确时，核实前暂停重复执行。
- **不具备完整子 Agent 能力时**：由当前主对话承担原流程中的探索、实现、合并和审查职责，按 Tickets 的依赖顺序完成实现和提交。保留原流程的 TDD、code-review 和必要验证要求；其中需要子 Agent 承担的职责同样由主对话完成，code-review 的 Standards 和 Spec 两个方面分别检查。
- **本次方案已确认无需拆分 Tickets 时**：以 Spec 作为单一实现单元完成开发、验证和审查。

### 调用并执行

在当前主对话中，从已核实的实际入口读取 `implement-spec` 的完整 `SKILL.md`，传入准备好的输入、本次适用的补充要求，以及用户已明确提出且仍然有效的执行要求，按其原流程执行。入口无法读取或需要重新定位时，按前置条件和意外中断规则处理。

调用其他 Skill 或给子 Agent 分配任务时，把需要它遵守的具体要求一并传入。要求中涉及其他规则时，将相关规则写进任务消息；需要另行读取文件时，提供文件的实际绝对路径或资料链接，写明需要读取的章节，并要求执行者先读取再执行。

执行完成后，进入收尾与交接。

## 3. 收尾与交接

### 任务完成

根据实际产物、执行记录和 Git 状态，核对：

- Spec 和必要的 Tickets 已完成实现，没有影响本次交付的未处理问题。
- 实现成果已汇总并提交到集成分支。
- 测试、审查和整改有实际结果，且与最终实现状态一致。

发现未完成项、新改动或未解决问题时，继续处理并完成受影响部分的检查。

完成核对后，保留集成 Worktree 和分支，进入结果报告。

### 意外中断

发生执行异常时，先核对实际状态和已有操作结果。

能在已有授权和已确认的设计范围内恢复时，自行处理，完成必要验证后继续。子 Agent 无法继续时，向主对话报告，由主对话核实进展并安排接续。

主对话收到子 Agent 或其他对话的模型繁忙、容量不足等临时服务错误提示时，等待 30 秒后重试；仍出现同类错误时，再分别等待 60 秒、120 秒重试。最多重试 3 次；仍未恢复时，暂停相关接续，按现有中断规则向用户报告。

需要用户作出新的决定、补充授权，或无法核实已有操作结果时，暂停受影响的工作，向用户说明问题、已完成内容、未完成事项及继续所需的信息或决定。等待期间，可以继续不依赖该决定的工作。

用户另有明确的停工或报告要求时，按用户要求执行。

用户决定继续后，先核对已有产物和实际执行状态，仅继续尚未完成的工作。创建、合并或发布结果不明确时，先核实原操作，核实前暂停重复执行；无法核实时，说明已知状态及缺失的信息，保持相关操作暂停。

### 结果报告与交接

完成核对后，使用 Python 3 调用[结果报告脚本](scripts/render-result.py)。脚本路径使用当前已加载 Skill 中的实际绝对路径。

调用示例，替换为本次任务的实际参数值：

```sh
python3 '/Skill绝对路径/scripts/render-result.py' \
  --summary '本次实现摘要、集成分支、实现提交、验证与审查结果及待归档事项' \
  --artifacts '[{"name":"集成 Worktree","location":"/项目Worktree绝对路径"}]' \
  --started-at '2026-10-10T09:00:00-07:00' \
  --continuous-mode false \
  --closure-skill-available true
```

| 参数 | 内容 |
| --- | --- |
| `--summary` | 本次实现摘要，包含集成分支、实现提交、验证与审查整改结果，以及必要的待归档事项。 |
| `--artifacts` | 根据实际成果填写非空 JSON 数组，包含集成 Worktree，以及本次已有的其他交付位置。每项仅包含 `name` 和 `location`，分别填写成果名称及实际绝对文件路径或 HTTP(S) 链接，两者均为非空单行文本。 |
| `--started-at` | 进入本 Skill 时记录的开始时间。 |
| `--continuous-mode` | 根据本次任务最新的用户要求判断。已明确要求连续模式且没有撤销或缩小该要求时为 `true`，否则为 `false`。 |
| `--closure-skill-available` | 根据收尾时针对目标项目的完整登记信息判断：`change-closure` 已启用且入口可读取时为 `true`，已确认无法使用时为 `false`。仅核对登记信息和入口可读取性，不加载正文。查询失败或无法确定采用哪个入口时，按意外中断规则处理，保留已完成成果，不将查询失败当成依赖缺失。 |

将脚本标准输出中的 Markdown 原样展示给用户，根据报告中的交接提示执行：

- 报告提示直接进入 4归档 时，立即调用名为 `change-closure` 的 Skill。
- 报告询问用户时，等待用户回复。用户明确同意进入 4归档 时，调用 `change-closure`；用户明确要求开启连续模式时，记录该要求后调用 `change-closure`。仅同意进入 4归档 不视为开启连续模式。
- 报告提示当前无法使用 `change-closure` 时，暂停交接，等待用户检查其安装、启用状态及入口。

调用 `change-closure` 时，从收尾检查已核实的实际入口读取其完整正文，再按原流程执行。

脚本执行失败时，按照“意外中断”的处理要求处理。
