本 Skill 编排 Matt 系列的 `implement-spec` 和 `implement`。完成共同准备后，根据实际工作组织选择执行路径，分别完成实现及验收整改，再统一完成结果登记、交付、状态更新、资源清理和最终报告。

首次进入本阶段时取得包含时区的 ISO 8601 开始时间，写入任务进度文件；接续时沿用本轮记录，供收尾脚本计算耗时。

# 输入与路径选择

## 输入

接受已确认的 Spec 和必要的 Tickets，也接受当前对话或用户指定资料中的改动要求。

根据用户请求和现有上下文，明确：

- **实现依据**：本次使用哪些 Spec、Tickets 或改动要求。用户指定资料时，以其指定的资料和范围为准。
- **实现目标**：用户希望实现什么结果，以及已经明确的范围、约束和决策。
- **目标项目**：实现属于哪个项目，需要在哪个代码库中执行。

这些信息已明确时直接使用；无法确定时，只针对影响实现的缺口向用户确认。

目标项目和本次任务明确后，先按[任务进度](#任务进度)创建或复用进度文件，再判断路径及继续共同准备。已有交接时接收同一进度文件的绝对路径、任务标识和原目标项目的绝对路径。

指定资料无法读取或缺少必要内容时，说明具体问题并请用户补充。多个来源存在影响实现的矛盾、且无法确定采用哪个时，向用户确认。

## 选择路径

根据实际工作量、耦合程度及独立交付、验收和并行收益选择；已有 Spec 作为实现依据，不单独决定路径：

- **单一实现路径**：目标和范围明确、适合一次连贯完成，选择 `implement`。已有 Spec 时直接复用；没有时整理简短改动方案。
- **任务图路径**：已有 Spec 和必要的 Tickets，多个实现单元有独立交付、验收或并行收益，选择 `implement-spec`，按依赖调度。
- **缺少必要方案或存在未决的重要设计取舍**：说明原因，建议用户进入 `solution-design`（2方案），等待决定，不自动切换。

没有 Spec 时，直接实现仍须影响局部、风险低、没有未决的重要设计取舍，能通过一次短小连贯的实现完成。紧密耦合的工作保持连贯，不因涉及多个文件而拆票；已有 Tickets 时沿用仍有效的成果和状态，调整组织不改变已确认的需求与验收要求。

能够在当前对话中直接澄清的少量信息，可以先补齐再判断。指定 Spec 或必要 Tickets 缺失、无法读取、不完整或存在关键冲突时，先处理资料问题，不据此降低实现和验收要求。

建议进入 2方案后，暂停依赖未决方案的实现，可以继续不依赖该决定的核实。用户同意后，按下文的依赖查询规则核实 `solution-design` 入口，读取完整正文。准备调用时，用 `stop --stage 3 --note '实际转入方案阶段的原因'` 结束本轮实现记录，传入同一进度身份；保留已完成步骤。随后传递已有需求、资料、未决问题及同一进度身份，沿用原文件进入 2方案。仅提出建议或等待用户决定时保持阶段未结束。

# 任务进度

在阶段切换、主要任务完成或较长执行期间，由主对话适时用一两句话说明当前阶段或任务、已完成内容和剩余工作。有 Tickets 时沿用编号及完成数量，并行时说明各任务状态；返工或计划调整时说明进度变化。复用已有状态，避免为汇报额外统计或频繁查询；对话说明不另行登记进度，大步骤仍按下文记录。

执行范围随同一进度记录交接和恢复，首次 `create` 默认执行至本阶段收尾。进入被范围限制拒绝时，核对用户是否已明确要求继续；有新指令才用 `set-scope --end-stage 3 --scope-reply '用户新指令原话' --scope-source '可定位来源'` 更新，传入同一进度身份。普通确认和等待不修改执行范围。

使用本 Skill 的[进度脚本](scripts/task-progress.py)，由主对话维护本任务唯一的临时 Markdown 文件。只记录以下大步骤的完成结果，步骤名称由脚本内置：

| 序号 | 大步骤 | 具体职责与完成条件 |
| --- | --- | --- |
| 1 | 准备 | 判断实现路径，核实依赖与项目约定，确定独立 Worktree、集成分支和审查基准。必要输入及执行条件已明确。 |
| 2 | 执行实现 | 任务图路径调用 `implement-spec`，单一实现路径调用 `implement`。完成对应流程中的实现、必要验证、提交及首次审查，记录实际结果。 |
| 3 | 实现验收与整改 | 按所选分支核对实现是否满足已确认要求，完成审查问题整改及必要复查，核实最终实现提交与验证、审查结果对应。确认相关执行者已停止写入，统一登记后续交付需要的工作区、分支、提交和成果信息。 |
| 4 | 分支检查与文档收尾 | 根据用户要求、项目约定和已有授权确定交付方式、实际仓库、目标分支及合并策略，再保存归档输入。检查目标分支变化及影响，完成当前能够明确的文档调整并提交；依赖整合结果的事项留到第 5 步。 |
| 5 | 整合与交付 | 整合目标分支变化，处理冲突并补齐剩余文档。复用仍有效的验收结论，对受影响部分补充验证与审查，完成项目要求的交付检查。按约定交付，并核实实际目标中的内容与已验证成果一致。 |
| 6 | 更新项目状态 | 根据实际交付结果更新适用的 Spec、Tickets、Issue 等状态。涉及仓库文件时，完成必要检查、提交与交付。无需更新时，记录依据。 |
| 7 | 清理资源 | 第 6 步完成后，先清理已交付且不再使用的任务分支，再按来源处理 Worktree，核实结果并记录保留资源及依据。此时保留任务进度文件。 |
| 8 | 最终报告 | 汇总整个任务的实现、验证审查、交付、状态更新和资源处理结果，生成并保留最终报告，记录阶段完成。整个任务结束后，完成适用的临时进度文件清理，并向用户展示报告。 |

创建前，区分原目标项目与本次执行工作区。优先沿用已有交接中的原目标项目；首次进入时，根据用户指定的项目及已知仓库关系核实，不直接将当前 `cwd` 或临时 Worktree 作为原目标项目。用户明确指定 Worktree 为目标项目时遵从其要求。执行工作区变化不改变已确定的任务归属。

首次进入体系时，遵守目标项目的写入约定，选择用户指定或项目约定的位置；没有约定时，使用宿主现有临时目录中的唯一文件路径。文件位于临时 Worktree 之外，父目录须已存在。用一次 `create` 创建文件并保存本阶段开始时间：

```sh
python3 '/Skill绝对路径/scripts/task-progress.py' create \
  --output '/本任务进度文件绝对路径' \
  --project '/原目标项目绝对路径' \
  --summary '本任务原始要解决的问题和目标' \
  --stage 3 --at '进入本阶段时取得的含时区ISO时间'
```

保存返回的 `file`、`task_id`、`project` 和本轮 `started_at`。已有交接时，沿用同一文件，用 `show` 核对归属和实际成果，再用 `enter --stage 3` 进入或复用本阶段；首次追加时用 `--at` 传入本阶段实际开始时间，接续时复用原时间。后续命令均传入同一组 `--file`、`--task-id` 和 `--project`。接续文件缺失、损坏或归属不明时，先核实并保留已有信息，不能另建文件替代。

从 3实现转去 2方案后再返回时，旧实现轮次已经终止，使用 `enter --stage 3 --new-run` 追加新一轮，保留之前的记录和耗时。

不适用的操作经核实后，在对应大步骤结果中写明“跳过”及原因。大步骤的处理仍记为完成，不把跳过操作说成实际执行。

使用 `complete --steps` 登记已完成的大步骤，参数为非空 JSON 列表；单步也使用一个元素的列表。每项包含整数 `step` 和单行 `note`，可选含时区的 ISO 8601 时间 `at`；必要的成果位置写入 `note`：

```sh
python3 '/Skill绝对路径/scripts/task-progress.py' complete \
  --file '/本任务进度文件绝对路径' \
  --task-id '创建时返回的任务标识' \
  --project '/原目标项目绝对路径' \
  --stage 3 --steps '[{"step":1,"note":"本大步骤的实际完成结果"}]'
```

未提供 `at` 的列表项统一使用本次登记时间；已有可靠事件时间时填入该项的 `at`。列表中的步骤须连续递增，不能重复、乱序或跳过未完成步骤。整批校验通过后一次写入，任一项失败则原记录不变。最后一个大步骤完成时自动结束阶段。更新只返回简短回执；恢复任务或生成报告需要完整记录时才用 `show`。同一结果重试保留首次时间；已完成的步骤保持原记录，必要返工在当前未完成大步骤的最终结果中简述。

默认完成一步即登记；连续完成的简短步骤可合并为一次列表登记。遇到等待、中断或较长执行前，先保存已完成进度，不为凑批次延迟记录。依赖已登记进度的操作仍按顺序执行：3实现须先登记第 3 步，再保存归档输入，才能完成第 4 步；先登记前七步，再生成报告，最后登记第 8 步。

普通确认、等待和中断不更新文件；恢复时核对实际成果，从尚未完成的大步骤接续，沿用本轮开始时间。阶段用时按起止时间计算，包含阶段内等待，不包含阶段间等待。转入其他阶段时，传递同一进度身份及必要成果信息；执行工作区变化不改变原目标项目。

确实重新执行已结束阶段时用 `enter --new-run` 追加一轮。明确取消当前阶段或改走其他阶段时，用 `stop --stage 3 --note '具体原因'` 保留已完成记录并结束本轮；暂停和等待不使用 `stop`。整个任务明确结束且结果报告已保留后，按项目清理授权调用 `cleanup --task-finished`。等待接续时保留文件。

# 共同准备

## 依赖与项目约定

根据所选路径核对依赖：

- **任务图路径**：`implement-spec`、`tdd`、`code-review`。
- **单一实现路径**：`implement`、`code-review`；已有 Spec 或本次需要使用 TDD 时，再核实 `tdd`。

从当前宿主针对目标项目的完整 Skills 登记信息中，按精确名称确认所需 Skill 已启用，并核对实际入口可读取，记录入口位置。前置检查仅核对登记信息和入口可读取性，不加载正文。

优先使用宿主已有的完整登记查询能力。Codex 没有直接查询工具时，使用 Python 3 调用[登记查询脚本](scripts/list-skills.py)，传入 `--cwd '/目标项目的实际绝对目录'`，按所选路径和本次需核实的名称重复传入 `--name`；脚本路径使用当前 Skill 的实际绝对路径。其他宿主使用自身提供的完整查询能力。

脚本仍查询和校验完整登记，仅筛选输出；同名多入口全部保留，`missing` 列出未登记名称。`ok: true` 只表示查询成功，仍须核对缺失项、启用状态及入口可读取性。省略 `--name` 时输出完整名单。

查询结果至少包含名称、实际入口和启用状态。初始 Available Skills 名单不作为完整登记信息；关闭隐式调用不视为禁用。

查询必须成功且完整。登记中不存在的 Matt 依赖，提示从 [Matt 官方 Skills 仓库](https://github.com/mattpocock/skills) 安装；已登记但禁用的依赖，提示启用。入口无法读取、同名多入口无法确定采用哪个，或查询失败时，说明问题并按“意外中断”处理。

安装、启用状态或入口变化后重新查询。实际需要其他条件性依赖时，按同一规则定位入口。

读取目标项目的 `docs/agents/issue-tracker.md`，复用 issue tracker 和任务关闭约定。文件缺失时，提示用户先运行 `$setup-matt-pocock-skills`；无法读取或必要约定不明确时，按“意外中断”处理。两条路径均保留 `code-review` 所需的这项配置。

## 工作区与审查基准

接收已有交接中的用户常用工作区路径和检出状态；独立进入本阶段时，常用工作区默认指原目标项目目录，用户已指定其他位置时使用指定路径。核对实际状态，保留用户对分支和编辑器项目位置的选择。除用户明确要求外，不替用户切分支、进入 detached 状态、检出未交付候选，或将编辑器项目切到任务 Worktree；用户自行切换后不自动恢复旧状态。

检查当前对话是否已有属于目标项目的独立 Worktree。复用前，核对实际仓库、分支和代码基线是否符合本次任务要求，并确认已有工作归属及是否存在其他写入者。

适合时复用，保留已有修改；不适合时选择其他合适的独立 Worktree。没有合适的独立 Worktree 时，创建一个。

在选定 Worktree 中开展后续工作前，核对本次已有文档成果，包括术语表、ADR 和讨论文档的实际位置，以及相关改动是否已包含在该 Worktree 中。

- 需要随本次任务交付的仓库文档，已有内容可直接复用；尚未包含的本次相关改动，包括未提交修改和新文件，按任务范围带入选定 Worktree。保留来源工作区的已有内容，不整仓复制或混入其他任务的修改。
- 目标 Worktree 已有不同修改时，核对双方内容并处理冲突，保留仍有效的修改；归属或取舍无法确定时，暂停相关迁移并向用户确认，不直接覆盖。
- 核对本次文档成果已完整包含后，将后续使用的资料路径更新为选定 Worktree 中的实际位置，记录这些文档属于本次提交和交付范围。外部链接或仅作参考的资料继续引用原位置。

将选定 Worktree 作为本次实现的集成工作区，在其中复用或创建本次实现的集成分支。无法确定归属或协调写入，或无法确定或创建工作区时，说明问题并向用户询问。

代码开发、本地自动化测试和整改在任务 Worktree 中完成。固定入口的运行验收遵守项目现有约定，但不因此获得切换常用工作区检出状态或将候选代码替换到该目录的授权。无法同时满足验收约定和工作区保护要求时，报告具体冲突及证据缺口，保持相关验收未完成并保留接续资源，不自行修改项目约定或切换用户分支，也不以其他检出的运行结果代替候选验证。

确定并记录覆盖本次实现范围的审查基准提交。已有明确基准时复用；没有时，根据本次实现范围确定，包含本次任务已有的实现及文档改动。

## 子 Agent 能力

结合任务规模、已有上下文和独立产出或并行收益判断是否需要委派；主对话能够短小连贯完成的工作直接执行，必要的独立审查仍按原流程完成。需要委派时，再确认当前环境是否支持：

- 在当前主对话下创建子 Agent，并提交首条消息。
- 主对话与该子 Agent 双向通信。
- 主对话等待并接收其完成或中断消息。

需要创建探索、实现、合并或审查子 Agent 时，读取并执行[模型与强度规则](references/agent-settings.md)。向负责创建子 Agent 的执行者传入该说明及本次已选定偏好文件的实际绝对路径，并明确要求其沿用同一份偏好规则，在每次创建前执行选型、记录依据，创建后核实实际设置。该要求同样适用于其继续委派的子 Agent。

不具备完整子 Agent 能力时，由当前主对话承担所选流程中的相应职责，保留其测试、审查和必要验证要求。`code-review` 的 Standards（项目规范）和 Spec（需求符合性）两个方面分别检查。

# 执行与收尾

按顺序执行以下大步骤，只在执行到对应步骤时读取其说明。当前上下文中已读取的规则、项目约定和已完成的分析直接复用；内容发生变化、已有信息不足或无法可靠恢复时，仅补读相关部分，不因进入新步骤而重新加载整套资料或重复探索。分支、工作区及执行状态等可变信息，在实际依赖它们的操作前定向核对，不连带重读无关文档。恢复时先核对同一进度文件及实际成果，从尚未完成的工作接续。执行过程中遵守下文的全程规则，并将适用要求传给所调用的 Skill 和相关子 Agent。

## 1. 准备

共同准备完成后，用 `complete --stage 3 --steps '[{"step": 1, "note": "本步骤的实际完成结果"}]'` 记录一句准备结果，包含所选路径、常用工作区及其检出分支、集成 Worktree、集成分支及审查基准，传入同一进度身份，结果填入列表项的 `note`。已记录且仍有效的准备直接复用。

## 2. 执行实现

只读取所选路径的说明并执行：

- 任务图路径：[任务图实现说明](references/spec-execution.md)。
- 单一实现路径：[单一实现说明](references/small-change-execution.md)。

两条路径均在实现及首次审查结束后登记第 2 步结果，再进入第 3 步。

## 3. 实现验收与整改

继续所选路径中的验收整改：任务图路径执行 [整体验收与整改](references/spec-execution.md#4-整体验收与整改)，单一实现路径执行 [验收与整改](references/small-change-execution.md#5-验收与整改)。恢复时直接接续所选分支的未完成事项。

分支验收完成后，按[验收结果登记与接续](references/acceptance-handoff.md)统一登记第 3 步结果及后续交付所需的成果信息，再进入第 4 步。

## 4. 分支检查与文档收尾

读取并执行[分支检查与文档收尾说明](references/delivery-preparation.md)，先确定交付目标、方式和合并策略，再保存归档输入，继续检查目标分支变化、完成当前能够明确的文档调整，并登记第 4 步结果。恢复时若第 3 步已完成但输入尚未保存，在本步骤核实交付目标后补齐；已保存的输入核对后复用。

## 5. 整合与交付

读取并执行[整合与交付说明](references/delivery.md)，完成整合、必要的补充检查、实际交付及结果核实，并登记第 5 步结果。

## 6. 更新项目状态

根据已有任务资料和项目约定，定位本次需要维护的 Spec、Tickets、Issue 等状态记录。核对其与实际交付结果是否一致，补齐合并成功后才能进行的更新和其余未完成项；已经正确更新的内容只核对结果。仅处理本次任务范围，记录中包含其他未完成事项时，保留与其完整范围相符的状态，遵守项目对实现完成与合并完成的定义。

状态更新涉及需要交付的仓库文件时，沿用第 4 步确定的交付方式，按第 5 步[整合与交付说明](references/delivery.md)完成必要检查、提交与交付，包括核对最新目标状态及实际结果。未受影响的结论直接复用。主体 PR 已合并时，后续提交须有新的交付记录，不能复用主体 PR 的完成状态；本次状态交付不重复登记第 5 步，结果汇入第 6 步。

必要状态更新及相应仓库文件交付均已核实后，用 `complete --stage 3 --steps '[{"step": 6, "note": "本步骤的实际完成结果"}]'` 记录更新结果、记录位置及适用的后续交付提交或链接，传入同一进度身份，结果填入列表项的 `note`。本次没有需维护的状态或用户明确要求不更新时，记录跳过及依据，再继续第 7 步。

## 7. 清理资源

读取并执行[清理资源说明](references/cleanup.md)，先清理任务分支，再按来源处理 Worktree；核实结果后登记第 7 步完成。保留同一任务进度文件，供第 8 步生成报告。

## 8. 最终报告

前七步及归档输入均已完整记录，适用的交付和收尾均已核实，且没有影响完成的未解决或待决事项时，使用 Python 3 调用[结果报告脚本](scripts/render-result.py)。已核实且未受后续变化影响的结论直接复用。

生成报告前，对照同一进度文件和实际成果，分别整理完成内容、验证结果和收尾结果。同一事实集中表述一次，已解决的问题仅在影响最终结果或后续使用时保留。必须保留适用的失败、跳过、豁免、未验证范围，以及保留资源及原因；不能把未执行写成已通过，或把待决事项省略为完成。摘要是否忠于证据由主对话核对，脚本仅检查输入格式和完成条件。

调用前取得包含时区的本次报告时间，保存该值。以下示例替换为实际参数，脚本路径使用当前 Skill 的绝对路径：

```sh
python3 '/Skill绝对路径/scripts/render-result.py' \
  --file '/本任务进度文件绝对路径' \
  --task-id '创建时返回的任务标识' \
  --project '/原目标项目绝对路径' \
  --summary '整个任务的目标与最终确认范围' \
  --implementation-result '实际完成的改动与最终行为' \
  --validation-result '最终有效的测试、审查结论及验证限制' \
  --closure-result '文档和项目状态更新、资源清理及保留原因' \
  --artifacts '[{"name":"目标项目","location":"/原目标项目绝对路径"}]' \
  --delivery-method '已核实的实际交付方式' \
  --pending '无' \
  --at '本次报告采用的含时区ISO时间' \
  --complete
```

`--summary` 根据原始目标及后续已确认的范围整理，不以“归档代码”等操作名称代替任务目的。`--artifacts` 填最终实际成果位置，每项仅含非空单行的 `name` 和 `location`；位置为绝对路径或 HTTP(S) 链接，无额外位置时允许 `[]`。使用交付后的真实位置，不引用已删除的临时路径，也不把用户当前检出的其他版本标为本次成果。`--delivery-method` 沿用已核实的交付方式，明确本地交付、直接推送或 PR 合并等实际结果。

三个结果摘要参数均为必填的非空单行文本。`--implementation-result` 说明实际改动与最终行为；`--validation-result` 说明最终有效的测试、审查及适用的验证限制；`--closure-result` 说明文档和项目状态更新、资源处理及保留原因。未完成或已终止的报告也使用同一结构，如实说明已完成部分、未执行工作和缺口。

`--pending` 必须如实填写；仅在事项均已解决，或用户明确延期、排除且剩余范围验收通过时填“无”。脚本展示核对后的结果摘要，从同一进度读取项目身份、目标分支、已验收实现提交，并按实际进入过的阶段汇总耗时；不再逐条复述步骤备注。`--complete` 只控制报告的完成状态，不写入进度。

报告成功生成后，保留完整标准输出及本次报告时间，调用 `complete --stage 3 --steps '[{"step": 8, "note": "最终报告已生成并保留", "at": "本次报告采用的含时区ISO时间"}]'`，传入同一进度身份。登记成功后，按[任务进度](#任务进度)完成适用的临时进度文件清理。

以已保存的完整报告作为最终回复正文原样、展开地展示，不使用折叠块。前序阶段已展示的报告无需再次拼接；最终回复中的状态和后续提示须反映任务当前实际状态。报告须与实际交付及资源处理结果一致；报告已生成或步骤已登记不能替代向用户交付报告。

报告生成失败时不登记第 8 步；登记失败时保留报告、时间和进度文件，核实后仅补齐登记。第 8 步已经登记时沿用原记录，继续未完成的进度清理或报告展示，不重复交付、资源清理或改写结束时间。

执行受阻且需要报告实际结果时，省略 `--complete`，传入实际 `--pending`；交付方式尚未核实时省略 `--delivery-method`。此类报告不登记第 8 步，不结束阶段，不清理进度文件。普通等待用户答复按[意外中断](#意外中断)处理，不因等待触发报告。用户明确取消时，先按任务进度规则终止本轮，再生成已终止报告；整个任务明确结束且报告保留后，才进行适用的进度文件清理。

# 全程规则

## 交付授权

涉及远程 Git、PR、Issue 等外部操作时，核对操作对象、范围和已有授权。已有授权覆盖本次操作时直接执行；缺少授权时，说明具体操作及影响，取得用户同意后执行。进入交付收尾不需要额外的阶段切换确认，连续模式不替代具体操作的授权和验收要求。

## 用户答复与待决事项

用户答复应与具体待决事项对应，只将其实际明确决定的内容记为已确认，其余保持未决，推荐项不自动生效。结合上下文判断“可以”“继续”等简短答复；存在影响结果的歧义时，只澄清对应事项，再继续依赖该决定的工作，保留其他已确认内容。

## 最小完整实现与设计边界

完成满足当前已确认要求的最小完整实现。新增复杂度应有明确的需求依据，避免为尚未确认的未来需求增加额外抽象、通用框架或扩展机制。

以用户已确认的要求和方案为参照。额外改造是为完成原任务，增加其中未包含的改造工作，或改变已约定的职责、行为、接口、数据规则、失败恢复方式及成本取舍。既定范围内的实现选择，以及修正本次实现或合并遗漏以恢复已确认行为，可自行处理。

新增额外改造或改变已确认设计前，先说明原因、范围和影响，取得用户确认；只有用户明确授予此类变化的自主决定权时，才可自行处理。无法确定是否超出范围时，先说明具体变化并确认。任务必要性、测试失败和审查建议不代替这种授权；用户确认仅覆盖当次说明的事项。

此规则同样适用于测试整改、审查整改和冲突处理。发现已做出的额外改造缺少上述用户依据时，主动说明实际变化，暂停相关集成和交付，按用户决定保留或撤回，继续不依赖该决定的工作。

用户已确认的同一变化无需重复询问；确认或明确授予自主决定权的原话或可定位来源，随实现依据保留。

### 方案变更同步

子 Agent 发现必要决策缺口或方案需调整时，暂停受影响工作并向主对话报告缺口，或说明拟议变化、原因及影响。主对话通知所有受影响的执行者暂停，并确认已暂停；按上述设计边界取得必要的用户决定。

随后更新本路径的实现依据，将变更及最新资料位置同步给相关执行者，要求重新读取并核对已有工作是否需要调整，完成同步和调整后再继续。普通内部实现细节仍按上述设计边界自行处理。

## Skill 入口与要求传递

首次 `code-review` 由所选实现 Skill 按其流程调用。本 Skill 将审查基准、需求依据及适用补充要求传给实现 Skill，由其继续传入审查流程。外层不额外安排相同范围的首次审查。

向审查流程提供 Spec 或简短方案时，一并提供用户原始目标、范围排除项及相关变更的确认依据，可使用必要摘录或资料引用。Spec 轴同时核对方案对这些依据的忠实程度，以及实现对方案的符合程度。

向需要使用其他 Skill 的执行者传递已核实的实际入口；使用时先读取完整正文，再执行原流程。实际需要其他条件性依赖时，由主对话按完整登记查询规则定位并传递入口。

子 Agent 遇到入口无法读取或需要重新定位时，向主对话报告并暂停相关工作，由主对话核实。

调用其他 Skill 或给子 Agent 分配任务时，把需要遵守的具体要求一并传入。涉及其他规则时，将相关规则写进任务消息；需要另行读取文件时，提供实际绝对路径或资料链接，写明需要读取的章节，并要求先读取再执行。

将 Skill 入口、工作区等执行信息与用户的设计要求分开说明。

任务进度由当前主对话统一维护。向实现、合并和审查执行者说明：回传成果及必要接续信息，进度文件由主对话更新；不为 Ticket、确认、测试或整改另建进度记录。

## 执行中的验证与诊断

修改公共接口或共享逻辑后，及时运行受影响的集成检查。

测试或其他长时命令运行中，优先使用宿主提供的等待或完成通知能力。需要判断失败、停滞或异常时，定向读取相关日志；普通进度查看只取新增输出或简短状态，无新信息时延长查询间隔。命令结束后核实退出状态及结果摘要，已有有效输出直接复用。

同一问题修复后再次出现、相关路径出现新的同类问题，或连续审查和测试表明同一实现方式存在问题时，先诊断再继续整改。

优先由当前负责整改的执行者对照此前的问题与修复，说明修复无效的原因，确定能捕获该问题的最小有效验证，并检查相关路径是否受到影响。根据诊断结果整改，再完成必要验证和复查。

验证连续受阻于工具、环境或取证问题时，先核对已有证据、剩余缺口，以及下一次尝试能验证的具体判断。已取得且仍有效的证据直接复用，只补缺失部分。

子 Agent 无法提出能推进该判断的具体恢复动作，或继续处理需要扩大工具修复范围时，向主对话回传已有结果、缺口和建议，由主对话决定接续方式，不自行持续扩展排障。主对话在已有授权和验收边界内选择定向恢复或替代验证；无法补齐证据时报告具体限制，需要改变验收要求时取得用户决定。

### 测试失败归属与收敛

测试失败先用最小必要对照核对归属，优先复跑相关用例或文件，并对齐必要的配置、数据和环境。基线上同样失败仅证明问题已存在，还须核对本次改动对失败路径的影响及当前目标的验证证据。

确认不影响本次验收的既有失败，将失败表现、基线及对照条件、验证限制记入现有记录，有依据的同类原因可归组。相关代码和条件未变、没有新疑点时复用结论并停止扩展排查；继续调查须针对具体证据缺口。

仍阻断必要验收或项目明确要求全套通过时，保持相关验收未完成；额外修复或验收调整按设计边界取得用户决定。

- **先判断问题归属。** 测试失败涉及行为预期冲突时，对照当前已确认要求、相关实现和必要的变更记录，判断是实现问题、测试问题，还是需求存在缺口。不能仅凭现有断言认定必须保留某种行为或扩大改动范围。
- **修正时保持验收语义。** 修正实现或测试均须保持已确认要求；删除用例、放宽断言或更新行为基线前，核对是否改变验收标准，不为通过测试降低标准。
- **按已有依据推进。** 能依据已有确认解决的，直接修正并验证；仍有影响结果的歧义，或需要改变已确认要求时，按设计边界处理。

## 本地文本写入

遵守目标项目的文件写入约定，优先使用宿主文件编辑工具。使用 Python 写入文本时，在源码前两行声明 `# coding: utf-8`，文件读写显式指定 `encoding="utf-8"`。长文正文使用多行文本或独立数据输入，避免嵌成超长单行源码。交给新对话或子 Agent 执行时，传递本节要求。

## 意外中断

发生执行异常时，先核对实际状态和已有操作结果。

能在已有授权和已确认的设计范围内恢复时，由当前执行者自行修复、完成必要验证并继续，无需等待主对话或用户确认。路径查找、命令参数、测试夹具、迁移引用遗漏，以及可按既定设计解决的合并冲突，均按此处理；重要修正及验证结果在进展或完成报告中汇总。

需要改变设计、扩大范围、取得用户的新决定、补充授权，或无法核实操作结果时，暂停受影响工作，说明问题、已完成内容、未完成事项及继续所需条件。继续不依赖该决定的工作；没有可继续的独立工作时，等待用户答复。子 Agent 在现有条件下无法恢复时，向主对话报告，由主对话核实进展并安排接续。

子 Agent 的中断报告应包含当前任务、执行步骤、中断原因、已完成和未完成的工作、已有成果的实际位置，以及结果尚不明确的操作。保留成果，暂停受影响工作，等待处理决定。

主对话收到其他执行者的模型繁忙、容量不足等临时服务错误提示时，等待 30 秒后重试；仍出现同类错误时，再分别等待 60 秒、120 秒重试。最多重试 3 次；仍未恢复时，暂停相关接续并报告。

影响本任务范围、实现、验收或交付的用户问题，在得到明确答复前保持未决。已有范围限制用于约束可执行的改动，不能代替用户回答新提出的范围问题。仅在用户已明确决定延期或排除该项、剩余范围可独立验收时，按调整后的范围继续收尾。存在这类未决事项时，保留已有成果和待确认上下文，保持当前阶段及整个任务未完成；问题已提出后，等待本身不触发报告、进度更新或阶段结束，继续不依赖该决定的工作。连续模式同样遵守此条件。

用户另有明确的停工或报告要求时，按用户要求执行。

用户决定继续后，先核对已有产物和实际执行状态，仅继续尚未完成的工作。创建、合并或发布结果不明确时，先核实原操作，核实前暂停重复执行；无法核实时，说明已知状态及缺失信息，保持相关操作暂停。

恢复时用 `show` 核对同一进度文件，沿用本轮开始时间；暂停、恢复和普通等待不更新文件。已生成的报告和已完成且仍有效的操作直接复用，仅补齐尚未完成的工作及大步骤记录。
