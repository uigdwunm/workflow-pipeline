本 Skill 编排 Matt 系列的 `implement-spec` 和 `implement`。完成共同准备后，根据实现依据选择执行路径，再统一完成验收、整改、报告和归档交接。

首次进入本阶段时取得包含时区的 ISO 8601 开始时间，写入任务进度文件；接续时沿用本轮记录，供收尾脚本计算耗时。

# 输入与路径选择

## 输入

接受已确认的 Spec 和必要的 Tickets，也接受当前对话或用户指定资料中的改动要求。

根据用户请求和现有上下文，明确：

- **实现依据**：本次使用哪些 Spec、Tickets 或改动要求。用户指定资料时，以其指定的资料和范围为准。
- **实现目标**：用户希望实现什么结果，以及已经明确的范围、约束和决策。
- **目标项目**：实现属于哪个项目，需要在哪个代码库中执行。

这些信息已明确时直接使用；无法确定时，只针对影响实现的缺口向用户确认。

目标项目和本次任务明确后，先按[任务进度](#任务进度)创建或复用进度文件，再判断路径及继续共同准备。已有交接时接收同一进度文件的绝对路径、任务标识和原目标项目的绝对路径。

指定资料无法读取或缺少必要内容时，说明具体问题并请用户补充。多个来源存在影响实现的矛盾、且无法确定采用哪个时，向用户确认。

## 选择路径

可以读取相关代码辅助判断，按以下条件选择：

- **已有 Spec**：已有用户确认作为本次实现依据的 Spec，选择 `implement-spec` 路径。
- **没有 Spec，且适合小改动**：选择 `implement` 路径，在执行时整理简短改动方案。
- **没有 Spec，且不适合小改动**：说明原因，建议用户进入 `solution-design`（2方案），等待决定，不自动切换。

小改动应当目标和范围明确、影响局部、风险低，没有尚未解决的重要设计取舍，能够通过一次短小且连贯的实现完成。不单凭代码行数或缺少 Spec 作判断。

能够在当前对话中直接澄清的少量信息，可以先补齐再判断。指定 Spec 无法读取、不完整或存在关键冲突时，先处理资料问题，不据此改走小改动路径。

建议进入 2方案后，暂停依赖未决方案的实现，可以继续不依赖该决定的核实。用户同意后，按下文的依赖查询规则核实 `solution-design` 入口，读取完整正文。准备调用时，用 `stop --stage 3 --note '实际转入方案阶段的原因'` 结束本轮实现记录，传入同一进度身份；保留已完成步骤。随后传递已有需求、资料、未决问题及同一进度身份，沿用原文件进入 2方案。仅提出建议或等待用户决定时保持阶段未结束。

# 任务进度

使用本 Skill 的[进度脚本](scripts/task-progress.py)，由主对话维护本任务唯一的临时 Markdown 文件。只记录以下大步骤的完成结果，步骤名称由脚本内置：

| 序号 | 大步骤 |
| --- | --- |
| 1 | 准备 |
| 2 | 执行实现 |
| 3 | 验收与整改 |
| 4 | 报告与交接 |

首次进入体系时，遵守目标项目的写入约定，选择用户指定或项目约定的位置；没有约定时，使用宿主现有临时目录中的唯一文件路径。文件位于临时 Worktree 之外，父目录须已存在。用一次 `create` 创建文件并保存本阶段开始时间：

```sh
python3 '/Skill绝对路径/scripts/task-progress.py' create \
  --output '/本任务进度文件绝对路径' \
  --project '/原目标项目绝对路径' \
  --summary '本任务原始要解决的问题和目标' \
  --stage 3 --at '进入本阶段时取得的含时区ISO时间'
```

保存返回的 `file`、`task_id`、`project` 和本轮 `started_at`。已有交接时，沿用同一文件，用 `show` 核对归属和实际成果，再用 `enter --stage 3` 进入或复用本阶段；首次追加时用 `--at` 传入本阶段实际开始时间，接续时复用原时间。后续命令均传入同一组 `--file`、`--task-id` 和 `--project`。接续文件缺失、损坏或归属不明时，先核实并保留已有信息，不能另建文件替代。

从 3实现转去 2方案后再返回时，旧实现轮次已经终止，使用 `enter --stage 3 --new-run` 追加新一轮，保留之前的记录和耗时。

每个大步骤实际完成时只调用一次 `complete`，填序号和一句结果；必要的成果位置可写在结果中：

```sh
python3 '/Skill绝对路径/scripts/task-progress.py' complete \
  --file '/本任务进度文件绝对路径' \
  --task-id '创建时返回的任务标识' \
  --project '/原目标项目绝对路径' \
  --stage 3 --step 1 --note '本大步骤的实际完成结果'
```

完成时间默认由脚本取得；已有可靠事件时间时通过 `--at` 传入。最后一个大步骤完成时自动结束阶段。更新只返回简短回执；恢复任务或生成报告需要完整记录时才用 `show`。同一结果重试保留首次时间；已完成的步骤保持原记录，必要返工在当前未完成大步骤的最终结果中简述。

普通确认、等待和中断不更新文件；恢复时核对实际成果，从尚未完成的大步骤接续，沿用本轮开始时间。阶段用时按起止时间计算，包含阶段内等待，不包含阶段间等待。后续阶段传递同一进度身份及必要成果信息；执行工作区变化不改变原目标项目。

确实重新执行已结束阶段时用 `enter --new-run` 追加一轮。明确取消当前阶段或改走其他阶段时，用 `stop --stage 3 --note '具体原因'` 保留已完成记录并结束本轮；暂停和等待不使用 `stop`。整个任务明确结束且结果报告已保留后，按项目清理授权调用 `cleanup --task-finished`。等待接续时保留文件。

# 共同准备

## 依赖与项目约定

根据所选路径核对依赖：

- **Spec 路径**：`implement-spec`、`tdd`、`code-review`。
- **小改动路径**：`implement`、`code-review`；本次需要使用 TDD 时，再核实 `tdd`。

从当前宿主针对目标项目的完整 Skills 登记信息中，按精确名称确认所需 Skill 已启用，并核对实际入口可读取，记录入口位置。前置检查仅核对登记信息和入口可读取性，不加载正文。

优先使用宿主已有的完整登记查询能力。Codex 没有直接查询工具时，使用 Python 3 调用[登记查询脚本](scripts/list-skills.py)，传入 `--cwd '/目标项目的实际绝对目录'`，按所选路径和本次需核实的名称重复传入 `--name`；脚本路径使用当前 Skill 的实际绝对路径。其他宿主使用自身提供的完整查询能力。

脚本仍查询和校验完整登记，仅筛选输出；同名多入口全部保留，`missing` 列出未登记名称。`ok: true` 只表示查询成功，仍须核对缺失项、启用状态及入口可读取性。省略 `--name` 时输出完整名单。

查询结果至少包含名称、实际入口和启用状态。初始 Available Skills 名单不作为完整登记信息；关闭隐式调用不视为禁用。

查询必须成功且完整。登记中不存在的 Matt 依赖，提示从 [Matt 官方 Skills 仓库](https://github.com/mattpocock/skills) 安装；已登记但禁用的依赖，提示启用。入口无法读取、同名多入口无法确定采用哪个，或查询失败时，说明问题并按“意外中断”处理。

安装、启用状态或入口变化后重新查询。实际需要其他条件性依赖时，按同一规则定位入口。

读取目标项目的 `docs/agents/issue-tracker.md`，复用 issue tracker 和任务关闭约定。文件缺失时，提示用户先运行 `$setup-matt-pocock-skills`；无法读取或必要约定不明确时，按“意外中断”处理。两条路径均保留 `code-review` 所需的这项配置。

## 工作区与审查基准

接收已有交接中的用户常用工作区路径和检出状态；独立进入本阶段时，常用工作区默认指原目标项目目录，用户已指定其他位置时使用指定路径。核对实际状态，保留用户对分支和编辑器项目位置的选择。除用户明确要求外，不替用户切分支、进入 detached 状态、检出未交付候选，或将编辑器项目切到任务 Worktree；用户自行切换后不自动恢复旧状态。

检查当前对话是否已有属于目标项目的独立 Worktree。复用前，核对实际仓库、分支和代码基线是否符合本次任务要求，并确认已有工作归属及是否存在其他写入者。

适合时复用，保留已有修改；不适合时选择其他合适的独立 Worktree。没有合适的独立 Worktree 时，创建一个。

在选定 Worktree 中开展后续工作前，核对本次已有文档成果，包括术语表、ADR 和讨论文档的实际位置，以及相关改动是否已包含在该 Worktree 中。

- 需要随本次任务交付的仓库文档，已有内容可直接复用；尚未包含的本次相关改动，包括未提交修改和新文件，按任务范围带入选定 Worktree。保留来源工作区的已有内容，不整仓复制或混入其他任务的修改。
- 目标 Worktree 已有不同修改时，核对双方内容并处理冲突，保留仍有效的修改；归属或取舍无法确定时，暂停相关迁移并向用户确认，不直接覆盖。
- 核对本次文档成果已完整包含后，将后续使用的资料路径更新为选定 Worktree 中的实际位置，记录这些文档属于本次提交和交付范围。外部链接或仅作参考的资料继续引用原位置。

将选定 Worktree 作为本次实现的集成工作区，在其中复用或创建本次实现的集成分支。无法确定归属或协调写入，或无法确定或创建工作区时，说明问题并向用户询问。

代码开发、本地自动化测试和整改在任务 Worktree 中完成。固定入口的运行验收遵守项目现有约定，但不因此获得切换常用工作区检出状态或将候选代码替换到该目录的授权。无法同时满足验收约定和工作区保护要求时，报告具体冲突及证据缺口，保持相关验收未完成并保留接续资源，不自行修改项目约定或切换用户分支，也不以其他检出的运行结果代替候选验证。

确定并记录覆盖本次实现范围的审查基准提交。已有明确基准时复用；没有时，根据本次实现范围确定，包含本次任务已有的实现及文档改动。

## 子 Agent 能力

确认当前环境是否支持：

- 在当前主对话下创建子 Agent，并提交首条消息。
- 主对话与该子 Agent 双向通信。
- 主对话等待并接收其完成或中断消息。

需要创建探索、实现、合并或审查子 Agent 时，读取并执行[模型与强度规则](references/agent-settings.md)。向负责创建子 Agent 的执行者传入该文件的实际绝对路径，并明确要求其在每次创建前执行选型、记录依据，创建后核实实际设置。该要求同样适用于其继续委派的子 Agent。

不具备完整子 Agent 能力时，由当前主对话承担所选流程中的相应职责，保留其测试、审查和必要验证要求。`code-review` 的 Standards（项目规范）和 Spec（需求符合性）两个方面分别检查。

# 执行与收尾

共同准备完成后，用 `complete --stage 3 --step 1` 记录一句准备结果，包含所选路径、常用工作区及其检出分支、集成 Worktree、集成分支及审查基准，传入同一进度身份及 `--note`。已记录且仍有效的准备直接复用。

只读取所选路径的说明并执行：

- Spec 路径：[Spec 实现说明](references/spec-execution.md)。
- 小改动路径：[小改动实现说明](references/small-change-execution.md)。

执行过程中遵守下文的全程规则，并将适用要求传给所调用的 Skill 和相关子 Agent。

所选路径执行结束后，必须读取并执行[收尾说明](references/completion.md)，完成统一验收、必要整改、结果报告和交接处理。

# 全程规则

## 最小完整实现与设计边界

完成满足当前已确认要求的最小完整实现。新增复杂度应有明确的需求依据，避免为尚未确认的未来需求增加额外抽象、通用框架或扩展机制。

可以自行决定内部实现方式；但用户尚未确定、也未授权自行决定的模块职责、输入输出合同、校验和失败行为，不属于可自行补充的实现细节。实现依赖这些决定时，先说明具体缺口，不能以“配套调整”为由自行补全。

以下情况需要用户确认：

- 需要改变已确认内容。
- 需要增加额外设计或机制。
- 补充细节需要改动既有重要设计。

已有明确授权覆盖对应变化时，无需重复确认。上述要求同样适用于审查后的整改。

### 方案变更同步

子 Agent 发现必要决策缺口或方案需调整时，暂停受影响工作并向主对话报告缺口，或说明拟议变化、原因及影响。主对话通知所有受影响的执行者暂停，并确认已暂停；按上述设计边界核对已有授权，取得必要决定。

随后更新本路径的实现依据，将变更及最新资料位置同步给相关执行者，要求重新读取并核对已有工作是否需要调整，完成同步和调整后再继续。普通内部实现细节仍按上述设计边界自行处理。

## Skill 入口与要求传递

首次 `code-review` 由所选实现 Skill 按其流程调用。本 Skill 将审查基准、需求依据及适用补充要求传给实现 Skill，由其继续传入审查流程。外层不额外安排相同范围的首次审查。

向审查流程提供 Spec 或简短方案时，一并提供用户原始目标、范围排除项及相关变更的确认依据，可使用必要摘录或资料引用。Spec 轴同时核对方案对这些依据的忠实程度，以及实现对方案的符合程度。

向需要使用其他 Skill 的执行者传递已核实的实际入口；使用时先读取完整正文，再执行原流程。实际需要其他条件性依赖时，由主对话按完整登记查询规则定位并传递入口。

子 Agent 遇到入口无法读取或需要重新定位时，向主对话报告并暂停相关工作，由主对话核实。

调用其他 Skill 或给子 Agent 分配任务时，把需要遵守的具体要求一并传入。涉及其他规则时，将相关规则写进任务消息；需要另行读取文件时，提供实际绝对路径或资料链接，写明需要读取的章节，并要求先读取再执行。

将 Skill 入口、工作区等执行信息与用户的设计要求分开说明。

任务进度由当前主对话统一维护。向实现、合并和审查执行者说明：回传成果及必要接续信息，进度文件由主对话更新；不为 Ticket、确认、测试或整改另建进度记录。

## 执行中的验证与诊断

修改公共接口或共享逻辑后，及时运行受影响的集成检查。

同一问题修复后再次出现、相关路径出现同类问题，或连续审查和测试表明同一实现方式存在问题时，先诊断再继续整改。

优先由当前负责整改的执行者对照此前的问题与修复，说明修复无效的原因，确定能捕获该问题的最小有效验证，并检查相关路径是否受到影响。根据诊断结果整改，再完成必要验证和复查。

验证连续受阻于工具、环境或取证问题时，先核对已有证据、剩余缺口，以及下一次尝试能验证的具体判断。已取得且仍有效的证据直接复用，只补缺失部分。

子 Agent 无法提出能推进该判断的具体恢复动作，或继续处理需要扩大工具修复范围时，向主对话回传已有结果、缺口和建议，由主对话决定接续方式，不自行持续扩展排障。主对话在已有授权和验收边界内选择定向恢复或替代验证；无法补齐证据时报告具体限制，需要改变验收要求时取得用户决定。

修复测试时，保持已确认的验收语义。删除用例、放宽断言或更新行为基线前，核对是否改变验收标准；涉及已确认要求的变化时，按设计边界处理。

## 本地文本写入

遵守目标项目的文件写入约定，优先使用宿主文件编辑工具。使用 Python 写入文本时，在源码前两行声明 `# coding: utf-8`，文件读写显式指定 `encoding="utf-8"`。长文正文使用多行文本或独立数据输入，避免嵌成超长单行源码。交给新对话或子 Agent 执行时，传递本节要求。

## 意外中断

发生执行异常时，先核对实际状态和已有操作结果。

能在已有授权和已确认的设计范围内恢复时，由当前执行者自行修复、完成必要验证并继续，无需等待主对话或用户确认。路径查找、命令参数、测试夹具、迁移引用遗漏，以及可按既定设计解决的合并冲突，均按此处理；重要修正及验证结果在进展或完成报告中汇总。

需要改变设计、扩大范围、取得用户的新决定、补充授权，或无法核实操作结果时，暂停受影响工作，说明问题、已完成内容、未完成事项及继续所需条件。继续不依赖该决定的工作；没有可继续的独立工作时，等待用户答复。子 Agent 在现有条件下无法恢复时，向主对话报告，由主对话核实进展并安排接续。

子 Agent 的中断报告应包含当前任务、执行步骤、中断原因、已完成和未完成的工作、已有成果的实际位置，以及结果尚不明确的操作。保留成果，暂停受影响工作，等待处理决定。

主对话收到其他执行者的模型繁忙、容量不足等临时服务错误提示时，等待 30 秒后重试；仍出现同类错误时，再分别等待 60 秒、120 秒重试。最多重试 3 次；仍未恢复时，暂停相关接续并报告。

影响本任务范围、实现或验收的用户问题，在得到明确答复前保持未决。已有范围限制用于约束可执行的改动，不能代替用户回答新提出的范围问题。仅在用户已明确决定延期或排除该项、剩余范围可独立验收时，按调整后的范围继续收尾。存在这类未决事项时，保留已有成果和待确认上下文，保持当前阶段及整个任务未完成；问题已提出后，等待本身不触发报告、进度更新或阶段结束，也不进入最终归档。连续模式同样遵守此条件。

用户另有明确的停工或报告要求时，按用户要求执行。

用户决定继续后，先核对已有产物和实际执行状态，仅继续尚未完成的工作。创建、合并或发布结果不明确时，先核实原操作，核实前暂停重复执行；无法核实时，说明已知状态及缺失信息，保持相关操作暂停。

恢复时用 `show` 核对同一进度文件，沿用本轮开始时间；暂停、恢复和普通等待不更新文件。已生成的报告和已完成且仍有效的操作直接复用，仅补齐尚未完成的工作及大步骤记录。
