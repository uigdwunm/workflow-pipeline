# 收尾与交接

本说明适用于两条实现路径。所选实现 Skill 执行结束后，统一按以下步骤处理。

# 1. 核对实现、审查和整改

根据本次实现依据、实际产物、执行记录和 Git 状态，核对：

- Spec 和必要的 Tickets，或已确认简短方案中的要求，均已完成实现。
- 所选流程要求的审查已完成，且覆盖本次实现。
- 没有影响本次交付的未处理问题。

核对底层实现 Skill 已完成首次审查。未完成时，接续其审查步骤；已完成且相关实现未变化时，直接复用结果，不重新安排相同审查。

对经核实的问题完成整改和必要验证。整改产生的改动先提交到集成分支，再复查整改内容及受影响范围，确保审查覆盖实际修改。审查基准仍需覆盖本次任务范围，不能因提交整改而遗漏先前实现。

复查时确认原问题已解决，且没有引入影响本次交付的新问题。仍未通过时，继续整改和复查。

整改继续遵守入口中的设计边界、重复问题诊断和意外中断规则；涉及方案更新时，按所选分支的同步要求处理。

# 2. 最终验证与提交核对

审查和整改完成后，核对实现成果已汇总并提交到集成分支，在最终集成提交上完成项目要求的交付验证。

最终实现发生变化时，重新完成必要检查。复用已有测试或审查结论时，确认对应内容、相关依赖和共享部分均未受后续改动影响。

根据最终状态确认：

- 实现要求全部完成。
- 实现及整改成果均已提交。
- 测试、审查和整改有实际结果，且与最终实现状态一致。

发现未完成项、新改动或未解决问题时，继续处理并完成受影响部分的检查。无法继续时，按入口的“意外中断”规则处理。

完成核对后，保留集成 Worktree 和分支，进入结果报告。

# 3. 结果报告

按入口的登记查询规则，核实目标项目的 `change-closure` 是否启用、入口是否可读取。仅核对登记信息和入口，不加载正文。

使用 Python 3 调用[结果报告脚本](../scripts/render-result.py)。脚本路径使用当前 Skill 的实际绝对路径。

调用示例，替换为本次任务的实际参数：

```sh
python3 '/Skill绝对路径/scripts/render-result.py' \
  --summary '本次实现摘要、集成分支、实现提交、验证与审查结果及待归档事项' \
  --artifacts '[{"name":"集成 Worktree","location":"/项目Worktree绝对路径"}]' \
  --started-at '2026-10-10T09:00:00-07:00' \
  --continuous-mode false \
  --closure-skill-available true
```

| 参数 | 内容 |
| --- | --- |
| `--summary` | 本次实现摘要，包含集成分支、实现提交、验证与审查整改结果，以及必要的待归档事项。 |
| `--artifacts` | 根据实际成果填写非空 JSON 数组，包含集成 Worktree，以及本次已有的其他交付位置。每项仅包含 `name` 和 `location`，分别填写成果名称及实际绝对文件路径或 HTTP(S) 链接，两者均为非空单行文本。 |
| `--started-at` | 进入本 Skill 时记录的开始时间。 |
| `--continuous-mode` | 根据本次任务最新的用户要求判断。已明确要求连续模式且没有撤销或缩小该要求时为 `true`，否则为 `false`。 |
| `--closure-skill-available` | 根据收尾时针对目标项目的完整登记信息判断：`change-closure` 已启用且入口可读取时为 `true`，已确认无法使用时为 `false`。查询失败或无法确定入口时，按意外中断规则处理，保留已有成果，不将查询失败当成依赖缺失。 |

将脚本标准输出中的 Markdown 原样展示给用户。脚本执行失败时，按入口的“意外中断”规则处理。

# 4. 归档交接

根据报告中的提示执行：

- 报告提示直接进入 4归档时，立即调用 `change-closure`。
- 报告询问用户时，等待回复。用户明确同意进入 4归档时，调用 `change-closure`；明确要求开启连续模式时，记录该要求后调用。仅同意进入 4归档，不视为开启连续模式。
- 报告提示当前无法使用 `change-closure` 时，暂停交接，等待用户检查其安装、启用状态及入口。

调用 `change-closure` 时，从已核实的实际入口读取完整正文，再按其原流程执行。
