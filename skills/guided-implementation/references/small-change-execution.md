# 小改动实现

完成入口中的共同准备后，先核查影响并整理简短改动方案，再调用 `implement`。执行中遵守入口的全程规则。

# 1. 核查影响并整理简短方案

根据已确认要求，阅读改动点及直接相关代码，确认当前行为、预期变化和现有约束。

沿实际调用和数据流核查影响，重点关注调用方、下游使用方、共享逻辑，以及接口或数据格式的变化。发现连带影响时，继续追踪到足以确定修改范围和验收方式；核查范围由实际关联决定，不固定要求全仓扫描。

区分完成本次目标所必需的连带调整与无关的既有问题。必要调整纳入方案；超出已有授权的范围先确认，无关问题仅报告。

根据核查结果，重新确认任务是否符合入口的小改动条件。涉及多个文件本身不作为升级依据；影响范围无法确定、存在未解决的重要设计取舍，或无法通过一次短小连贯的实现完成时，先补齐必要信息。补齐后仍不符合小改动条件时，按入口的路径判断规则说明原因，建议进入 2方案并等待用户决定，不自动切换。

确认适合小改动后，在当前对话中简要说明：

- **目标与边界**：预期结果、修改范围和约束。
- **改法与影响**：具体改法、受影响的使用方，以及必要的连带调整。
- **验收方式**：如何验证目标行为，并覆盖受影响的既有行为。

已有方案直接复用，仅补齐缺失的影响核查及相应方案内容，不调用 `to-spec` 或 `to-tickets`。

涉及新的关键决定或缺少具体改动授权时，先取得必要确认；已有明确授权覆盖本次改动时，无需重复确认。

按 `implement` 要求，在适用且可行时使用 `tdd`，复用已确认的测试边界，即通过哪些接口或可观察行为验证改动。需要调用 `tdd` 时，先按入口规则核实其入口，读取完整正文并完成必要确认。

执行过程中发现新的影响时，补充核查并更新简短方案，按同一条件重新判断实现路径。

# 2. 准备输入

向 `implement` 提供：

- 已确认的简短改动方案全文及必要资料引用。
- 目标项目、集成 Worktree、集成分支和审查基准。
- 已核实的 `code-review` 及本次需要的 `tdd` 入口。
- 入口中适用的全程规则。
- 下文补充要求及仍有效的用户执行要求。

# 3. 补充执行要求

## 实施说明与工作区

简短改动方案替代 `implement` 所需的正式 Spec 或 Tickets，作为本次实施说明。

使用已选定的集成 Worktree 和集成分支；`implement` 所说的“当前分支”指本次集成分支。

## 已确认要求与方案同步

将已确认的设计要求保留在简短方案中，向相关实现和审查执行者提供，审查时核对是否落实。

需要修改、撤销或偏离某项要求时，说明原约定、拟议变化、原因和影响，按入口的设计边界处理。

按入口[方案变更同步](../SKILL.md#方案变更同步)执行；本路径更新简短方案，并向相关执行者传递最新内容。

## 传给 implement 的测试要求

根据实际影响范围和项目约定确定验证范围，覆盖修改行为及受影响的既有行为，不默认执行完整测试套件。项目明确要求、用户已确认的验收范围包含全量，或影响无法通过定向验证充分覆盖时，执行全量测试。测试失败后先修正并复测失败用例及受影响范围，再按需要执行全量；已有且仍有效的验证结果直接复用。本规则替代 `implement` 中无条件执行完整测试套件的要求。

## 传给 implement 的审查要求

由 `implement` 在其原流程调用 `code-review` 时，传入已记录的审查基准和已确认的简短方案全文。简短方案替代 Spec 查找步骤，其余审查流程保持不变。

## 提交与审查顺序

本路径将 `implement` 的顺序调整为：完成实现和必要验证 → 将本次改动提交到集成分支 → 调用 `code-review`。提交仅包含本次任务的改动，以确保审查使用的 `HEAD` 包含本次实现。

# 4. 调用并执行

在当前主对话中，从已核实入口读取 `implement` 的完整 `SKILL.md`，传入准备好的输入和补充要求，按其原流程执行。上文明示适配的步骤按补充要求执行。

调用时说明：复用已有简短方案和仍有效的影响核查结果，仅补充实现所需的缺口，无需重复探索、规划或确认已明确的内容。

所选实现 Skill 的原流程执行结束并回到主对话后，用 `complete --stage 3 --steps '[{"step": 2, "note": "本步骤的实际完成结果"}]'` 记录一句实际实现结果，包含集成提交及首次审查情况，传入入口[任务进度](../SKILL.md#任务进度)中的同一进度身份，结果填入列表项的 `note`。随后执行下文“验收与整改”，作为第 3 大步骤。执行中断时，按入口的“意外中断”规则处理。

# 5. 验收与整改

对照已确认的简短方案，核对目标、范围及验收要求是否落实，复用 `implement` 已完成的验证和首次审查结果。首次审查尚未完成时，接续其审查步骤。

仅对剩余问题进行整改，完成必要验证并提交到集成分支，再复查整改内容及受影响范围。审查基准仍覆盖本次任务的完整范围。问题仍未解决或出现影响交付的新问题时，继续整改和复查；涉及方案变化、重复问题或执行受阻时，遵守入口的全程规则。

交付前确认：

- 简短方案中的要求均已落实，实现和整改成果均已提交到集成分支。
- 验证与审查结论适用于最终实现提交；对应内容、相关依赖和共享部分未受后续变化影响时直接复用。仅在证据存在缺口或项目明确要求时补充检查。
- 没有影响本次交付的未处理问题或待答的用户问题；有其他执行者参与时，确认其已停止写入。

满足上述条件后，按[验收结果登记与接续](acceptance-handoff.md)登记第 3 步并进入共同收尾。存在未决事项时，按入口“意外中断”规则保留成果并接续，保持第 3 步未完成。
