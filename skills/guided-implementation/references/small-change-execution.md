# 单一实现

完成入口中的共同准备后，核对已确认的 Spec 或整理简短改动方案，再调用 `implement`。执行中遵守入口的全程规则。

# 1. 核对实现依据与影响

已有 Spec 时，将其及必要的 Tickets 直接作为实施依据，保留全部已确认要求与验收约定。没有 Spec 时，根据已确认要求整理简短改动方案。复用仍有效的影响核查，仅补充当前行为、预期变化和直接相关约束的缺口。

沿实际调用和数据流核查影响，重点关注调用方、下游使用方、共享逻辑，以及接口或数据格式的变化。发现连带影响时，继续追踪到足以确定修改范围和验收方式；核查范围由实际关联决定，不固定要求全仓扫描。

区分完成本次目标所必需的连带调整与无关的既有问题。必要连带调整先按入口的设计边界核对，涉及额外改造时先取得必要的用户决定，再纳入简短方案；无关问题仅报告。

根据核查结果，确认任务是否适合一次连贯完成。发现独立交付、验收或并行收益时，按入口重新判断是否采用任务图；涉及多个文件本身不作为拆分依据。缺少必要方案、影响范围无法确定或存在未决的重要设计取舍时，先补齐信息，仍需方案时建议进入 2方案并等待用户决定。

确认适合单一实现后，在当前对话中简要说明：

- **目标与边界**：预期结果、修改范围和约束。
- **改法与影响**：具体改法、受影响的使用方，以及必要的连带调整。
- **验收方式**：如何验证目标行为，并覆盖受影响的既有行为。

已有 Spec 或简短方案直接复用，仅补齐缺失的影响核查及相应方案内容，不重复生成实施文档。

涉及额外改造或未决的关键设计时，按入口的设计边界取得必要的用户决定；已明确确认的同一改动无需重复询问。

已有 Spec 的任务保留原有 TDD 要求；没有 Spec 时，按 `implement` 要求在适用且可行时使用 `tdd`。复用已确认的测试边界，需要调用 `tdd` 时，先按入口规则核实其入口，读取完整正文并完成必要确认。

执行过程中发现新的影响时，先核查是否涉及额外改造，按入口的设计边界取得必要的用户决定，再更新原实施依据并重新判断实现路径。

# 2. 准备输入

向 `implement` 提供：

- 已确认的 Spec 及必要 Tickets 的实际位置，或简短改动方案全文；一并提供必要资料引用。
- 目标项目、集成 Worktree、集成分支和审查基准。
- 已核实的 `code-review` 及本次需要的 `tdd` 入口。
- 入口中适用的全程规则。
- 下文补充要求及仍有效的用户执行要求。

# 3. 补充执行要求

## 实施说明与工作区

已有 Spec 时直接作为 `implement` 的实施说明；没有时使用已确认的简短改动方案。已有 Tickets 的要求和状态记录随任务保留。

使用已选定的集成 Worktree 和集成分支；`implement` 所说的“当前分支”指本次集成分支。

## 已确认要求与方案同步

向相关实现和审查执行者提供 Spec 或简短方案中的已确认设计要求，审查时核对是否落实。

需要修改、撤销或偏离某项要求时，说明原约定、拟议变化、原因和影响，按入口的设计边界处理。

按入口[方案变更同步](../SKILL.md#方案变更同步)执行；本路径更新原 Spec、相关 Tickets 或简短方案，并向相关执行者传递最新内容。

## 传给 implement 的测试要求

根据实际影响范围和项目约定确定验证范围，覆盖修改行为及受影响的既有行为，不默认执行完整测试套件。项目明确要求、用户已确认的验收范围包含全量，或影响无法通过定向验证充分覆盖时，执行全量测试。测试失败先按入口[测试失败归属与收敛](../SKILL.md#测试失败归属与收敛)核对；本次需修正的问题先修正并复测失败用例及受影响范围，再按需要执行全量。已有且仍有效的验证结果直接复用。本规则替代 `implement` 中无条件执行完整测试套件的要求。

## 传给 implement 的审查要求

由 `implement` 在其原流程调用 `code-review` 时，传入已记录的审查基准和已确认的 Spec、必要 Tickets 或简短方案全文。使用简短方案时替代 Spec 查找步骤，其余审查流程保持不变。

## 提交与审查顺序

本路径将 `implement` 的顺序调整为：完成实现和必要验证 → 将本次改动提交到集成分支 → 调用 `code-review`。提交仅包含本次任务的改动，以确保审查使用的 `HEAD` 包含本次实现。

# 4. 调用并执行

在当前主对话中，从已核实入口读取 `implement` 的完整 `SKILL.md`，传入准备好的输入和补充要求，按其原流程执行。上文明示适配的步骤按补充要求执行。

调用时说明：复用已有 Spec 或简短方案及仍有效的影响核查结果，仅补充实现所需的缺口，无需重复探索、规划或确认已明确的内容。

所选实现 Skill 的原流程执行结束并回到主对话后，用 `complete --stage 3 --steps '[{"step": 2, "note": "本步骤的实际完成结果"}]'` 记录一句实际实现结果，包含集成提交及首次审查情况，传入入口[任务进度](../SKILL.md#任务进度)中的同一进度身份，结果填入列表项的 `note`。随后执行下文“验收与整改”，作为第 3 大步骤。执行中断时，按入口的“意外中断”规则处理。

# 5. 验收与整改

对照已确认的 Spec、必要 Tickets 或简短方案，核对目标、范围及验收要求是否落实，复用 `implement` 已完成的验证和首次审查结果。首次审查尚未完成时，接续其审查步骤。

仅对剩余问题进行整改，整改前按入口的设计边界核对所需改动，额外改造先取得必要的用户决定。完成必要验证并提交到集成分支，再复查整改内容及受影响范围。审查基准仍覆盖本次任务的完整范围。问题仍未解决或出现影响交付的新问题时，继续整改和复查；涉及方案变化、重复问题或执行受阻时，遵守入口的全程规则。

交付前确认：

- Spec、必要 Tickets 或简短方案中的要求均已落实，实现和整改成果均已提交到集成分支。
- 对照实际改动及已确认依据，核对额外改造已有用户确认或明确自主决定权的依据；缺少依据时，暂停相关交付并说明实际变化。
- 验证与审查结论适用于最终实现提交；对应内容、相关依赖和共享部分未受后续变化影响时直接复用。仅在证据存在缺口或项目明确要求时补充检查。
- 没有影响本次交付的未处理问题或待答的用户问题；有其他执行者参与时，确认其已停止写入。

满足上述条件后，按[验收结果登记与接续](acceptance-handoff.md)登记第 3 步并进入共同收尾。存在未决事项时，按入口“意外中断”规则保留成果并接续，保持第 3 步未完成。
