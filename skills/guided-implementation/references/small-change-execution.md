# 小改动实现

完成入口中的共同准备后，先整理简短改动方案，再调用 `implement`。执行中遵守入口的全程规则。

# 1. 整理简短改动方案

阅读相关代码，根据已确认要求，在当前对话中简要说明：

- 目标、修改范围和约束。
- 具体改法。
- 验收方式。

已有内容已经明确时直接复用，不重复包装，也不调用 `to-spec` 或 `to-tickets`。

涉及新的关键决定或缺少具体改动授权时，先取得必要确认；已有明确授权覆盖本次改动时，无需重复确认。

按 `implement` 要求，在适用且可行时使用 `tdd`，复用已确认的测试边界，即通过哪些接口或可观察行为验证改动。需要调用 `tdd` 时，先按入口规则核实其入口，读取完整正文并完成必要确认。

整理方案或执行过程中发现任务已超出小改动条件时，按入口的路径判断规则说明原因，建议用户进入 2方案并等待决定，不自动切换。

# 2. 准备输入

向 `implement` 提供：

- 已确认的简短改动方案全文及必要资料引用。
- 目标项目、集成 Worktree、集成分支和审查基准。
- 已核实的 `code-review` 及本次需要的 `tdd` 入口。
- 入口中适用的全程规则。
- 下文补充要求及仍有效的用户执行要求。

# 3. 补充执行要求

## 实施说明与工作区

简短改动方案替代 `implement` 所需的正式 Spec 或 Tickets，作为本次实施说明。

使用已选定的集成 Worktree 和集成分支；`implement` 所说的“当前分支”指本次集成分支。

## 已确认要求与方案同步

将已确认的设计要求保留在简短方案中，向相关实现和审查执行者提供，审查时核对是否落实。

需要修改、撤销或偏离某项要求时，说明原约定、拟议变化、原因和影响，按入口的设计边界处理。

子 Agent 发现必要决策缺口或方案需调整时，先暂停相关工作并向主对话报告。主对话通知其他受影响的子 Agent 暂停并确认已暂停，取得必要决定后更新简短方案，将最新内容传给相关执行者，核对已有工作后再继续。

## 传给 implement 的审查要求

由 `implement` 在其原流程调用 `code-review` 时，传入已记录的审查基准和已确认的简短方案全文。简短方案替代 Spec 查找步骤，其余审查流程保持不变。

## 提交与审查顺序

本路径将 `implement` 的顺序调整为：完成实现和必要验证 → 将本次改动提交到集成分支 → 调用 `code-review`。提交仅包含本次任务的改动，以确保审查使用的 `HEAD` 包含本次实现。

# 4. 调用并执行

在当前主对话中，从已核实入口读取 `implement` 的完整 `SKILL.md`，传入准备好的输入和补充要求，按其原流程执行。上文明示适配的步骤按补充要求执行。

所选实现 Skill 的原流程执行结束并回到主对话后，用 `complete --stage 3 --step 2` 记录一句实际实现结果，包含集成提交及首次审查情况，传入入口[任务进度](../SKILL.md#任务进度)中的同一进度身份及 `--note`。再读取并执行[收尾说明](completion.md)。执行中断时，按入口的“意外中断”规则处理。
