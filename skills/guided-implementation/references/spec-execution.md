# Spec 实现

完成入口中的共同准备后，使用本说明调用 `implement-spec`。执行中遵守入口的全程规则。

# 1. 准备输入

读取本次已确认的 Spec 和必要的 Tickets，准备实现目标、范围、约束、项目约定及资料引用。

在派工或直接实现前，对照当前代码，核实 Spec 所依赖的接口、模块职责和关键前提是否仍然成立，以及必要的连带调整是否已由 Spec 和相关 Tickets 覆盖。发现偏差时，区分可自行处理的实现细节与需要确认的方案变化，按入口的设计边界处理；涉及方案变化时，按下文“方案更新与同步”更新相关资料和执行安排，再继续受影响工作。

复用已确认的测试边界，即通过哪些接口或可观察行为验证改动；缺少必要约定时，按 `tdd` 原流程完成确认。

向 `implement-spec` 提供：

- Spec 和必要的 Tickets 的实际位置。
- 目标项目、集成 Worktree、集成分支和审查基准。
- 已核实的 `tdd`、`code-review` 入口。
- 入口中适用的全程规则。
- 下文补充要求及仍有效的用户执行要求。

# 2. 补充执行要求

## 已确认设计要点

Spec 或 Tickets 中有已确认设计要点时，实现每个 Ticket 前读取其中适用的要点。

向相关实现和审查子 Agent 提供要点编号及 Spec 位置，可以使用资料引用。审查时核对这些要点是否落实。

需要修改、撤销或偏离某条要点时，说明对应编号、原约定、拟议变化、原因和影响，按入口的设计边界处理。

## 方案更新与同步

按入口[方案变更同步](../SKILL.md#方案变更同步)执行；本路径更新 Spec 和相关 Tickets。接续前，主对话还须重新检查剩余 Tickets 的依赖关系和执行安排，完成必要调整。

## 传给 implement-spec 的审查要求

由 `implement-spec` 在其原流程调用 `code-review` 时，传入已记录的审查基准，以及本次确认的 Spec 和必要的 Tickets。将适用的已确认设计要点一并传给审查执行者，要求核对是否落实。

## 集成与执行适配

使用已选定的集成 Worktree 和集成分支。合并相互关联的 Tickets 后，及时运行受影响的集成检查。

涉及模块装配、加载方式或宿主相关行为时，在相关任务派工中明确适用的运行环境约束，以及由当前执行者还是集成阶段完成对应验证。执行者回传已验证范围和仍需后续验证的部分，主对话据此安排并核实集成验收补齐。

首次运行验证前，核实实际运行项目、候选代码身份及项目要求的环境版本；不符合既定约定时，先处理差异，再开始验证。环境变化后，重新核对受影响的证据。

具备完整子 Agent 能力且已拆分 Tickets 时，按 `implement-spec` 的任务图调度：

- 初始派工及每次前置任务合并、必要检查通过后，重新核对就绪任务，在可用并发容量内及时启动可独立执行的任务。并发数量由实际依赖和独立验收条件决定。
- 并行任务开始前，明确各自修改范围，识别共享文件及接口，约定由谁接入或如何合并。根据实际冲突风险安排工作，文件有交集本身不作为整个任务串行的理由。
- 等待前置产物时，可提前安排不依赖该产物的只读探索，并将结果提供给后续执行者。
- 发现新的实际依赖时，记录所需产物并调整 Tickets 和执行安排；涉及方案变化时，按“方案更新与同步”处理。

不具备完整子 Agent 能力时，由当前主对话承担探索、实现、合并和审查职责，按 Tickets 的依赖顺序完成实现和提交，保留原流程的 TDD、code-review 和必要验证要求。

本次方案已确认无需拆分 Tickets 时，以 Spec 作为单一实现单元完成开发、验证和审查。此要求替代原流程的 Tickets 调度，不为执行该流程额外补建 Tickets。

# 3. 调用并执行

在当前主对话中，从已核实入口读取 `implement-spec` 的完整 `SKILL.md`，传入准备好的输入和补充要求，按其原流程执行。上文明示适配的步骤按补充要求执行。

所选实现 Skill 的原流程执行结束并回到主对话后，用 `complete --stage 3 --steps '[{"step": 2, "note": "本步骤的实际完成结果"}]'` 记录一句实际实现结果，包含集成提交及首次审查情况，传入入口[任务进度](../SKILL.md#任务进度)中的同一进度身份，结果填入列表项的 `note`。随后执行下文“整体验收与整改”，作为第 3 大步骤。执行中断时，按入口的“意外中断”规则处理。

# 4. 整体验收与整改

## 核对要求覆盖与集成结果

对照已确认的 Spec 和必要的 Tickets，核对设计要点及验收要求是否全部落实。各 Ticket 的完成结果作为依据，整体完成还须核对实际集成成果；未拆分 Tickets 时，按单一 Spec 核对。

确认各实现单元的成果已提交并汇总到集成分支，核对执行者回传的已验证范围和待补验证事项。补齐跨 Ticket 的接口配合、共享逻辑及适用运行环境等集成验证缺口，沿用上文的运行环境和候选代码身份核实要求。

核对 `implement-spec` 要求的首次审查已完成且覆盖本次实现。尚未完成时接续其审查步骤；已有验证和审查结论对应的内容、相关依赖及共享部分未受后续变化影响时，直接复用。

## 整改与复查

对经核实的问题，按问题归属和实际依赖安排整改。整改成果先提交到集成分支，再完成必要验证和复查，覆盖整改内容及受影响范围；审查基准仍覆盖本次任务的完整范围。

复查确认原问题已解决，且没有引入影响交付的新问题；未通过时继续整改和复查。涉及方案变化时，按上文“方案更新与同步”更新 Spec、相关 Tickets 和执行安排。重复问题及执行受阻按入口的全程规则处理。

## 确认可交付成果

在最终集成状态上确认：

- Spec 和必要的 Tickets 中的要求均已实现，成果及整改均已提交，集成验证缺口已补齐。
- 项目要求的实现验收已完成，验证、审查及整改结论与最终实现提交对应；最终实现发生变化时，补齐受影响部分的检查。
- 没有影响本次交付的未处理问题或待答的用户问题，相关实现及整改执行者已停止写入。

满足上述条件后，按[验收结果登记与接续](acceptance-handoff.md)登记第 3 步并进入共同收尾。存在未决事项时，按入口“意外中断”规则保留成果并接续，保持第 3 步未完成。
