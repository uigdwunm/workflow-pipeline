# Spec 实现

完成入口中的共同准备后，使用本说明调用 `implement-spec`。执行中遵守入口的全程规则。

# 1. 准备输入

读取本次已确认的 Spec 和必要的 Tickets，准备实现目标、范围、约束、项目约定及资料引用。

复用已确认的测试边界，即通过哪些接口或可观察行为验证改动；缺少必要约定时，按 `tdd` 原流程完成确认。

向 `implement-spec` 提供：

- Spec 和必要的 Tickets 的实际位置。
- 目标项目、集成 Worktree、集成分支和审查基准。
- 已核实的 `tdd`、`code-review` 入口。
- 入口中适用的全程规则。
- 下文补充要求及仍有效的用户执行要求。

# 2. 补充执行要求

## 已确认设计要点

Spec 或 Tickets 中有已确认设计要点时，实现每个 Ticket 前读取其中适用的要点。

向相关实现和审查子 Agent 提供要点编号及 Spec 位置，可以使用资料引用。审查时核对这些要点是否落实。

需要修改、撤销或偏离某条要点时，说明对应编号、原约定、拟议变化、原因和影响，按入口的设计边界处理。

## 方案更新与同步

子 Agent 发现方案需调整或缺少必要决策时，先暂停相关工作并向主对话报告缺口，或说明拟修改内容、原因及影响。

主对话通知所有受影响的子 Agent 暂停相关工作，并确认它们已暂停；按设计边界判断是否需要用户确认，并取得必要的用户决定。

内容明确后，更新 Spec 和相关 Tickets，将变更内容及最新资料位置发给这些子 Agent，通知它们重新读取，并核对已有工作是否需要调整。

主对话重新检查剩余 Tickets 的依赖关系和执行安排，完成同步和调整后再继续。

## 传给 implement-spec 的审查要求

由 `implement-spec` 在其原流程调用 `code-review` 时，传入已记录的审查基准，以及本次确认的 Spec 和必要的 Tickets。将适用的已确认设计要点一并传给审查执行者，要求核对是否落实。

## 集成与执行适配

使用已选定的集成 Worktree 和集成分支。合并相互关联的 Tickets 后，及时运行受影响的集成检查。

具备完整子 Agent 能力且已拆分 Tickets 时，按 `implement-spec` 的任务图调度：

- 初始派工及每次前置任务合并、必要检查通过后，重新核对就绪任务，在可用并发容量内及时启动可独立执行的任务。并发数量由实际依赖和独立验收条件决定。
- 并行任务开始前，明确各自修改范围，识别共享文件及接口，约定由谁接入或如何合并。根据实际冲突风险安排工作，文件有交集本身不作为整个任务串行的理由。
- 等待前置产物时，可提前安排不依赖该产物的只读探索，并将结果提供给后续执行者。
- 发现新的实际依赖时，记录所需产物并调整 Tickets 和执行安排；涉及方案变化时，按“方案更新与同步”处理。

不具备完整子 Agent 能力时，由当前主对话承担探索、实现、合并和审查职责，按 Tickets 的依赖顺序完成实现和提交，保留原流程的 TDD、code-review 和必要验证要求。

本次方案已确认无需拆分 Tickets 时，以 Spec 作为单一实现单元完成开发、验证和审查。此要求替代原流程的 Tickets 调度，不为执行该流程额外补建 Tickets。

# 3. 调用并执行

在当前主对话中，从已核实入口读取 `implement-spec` 的完整 `SKILL.md`，传入准备好的输入和补充要求，按其原流程执行。上文明示适配的步骤按补充要求执行。

所选实现 Skill 的原流程执行结束并回到主对话后，用 `complete --stage 3 --step 2` 记录一句实际实现结果，包含集成提交及首次审查情况，传入入口[任务进度](../SKILL.md#任务进度)中的同一进度身份及 `--note`。再读取并执行[收尾说明](completion.md)。执行中断时，按入口的“意外中断”规则处理。
