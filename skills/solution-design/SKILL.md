本 Skill 编排 Matt 系列的 `to-spec` 和 `to-tickets`。Spec 和 Tickets 的内容与生成规则以对应 Skill 为准，本 Skill 补充已确认设计要点的提取、记录和核对要求。

进入本 Skill 时，记录包含时区的 ISO 8601 开始时间，供收尾脚本计算总耗时。

# 输入与前置条件

## 输入

接受当前对话中已讨论的内容，也接受用户指定的文件、issue、链接或其他资料。

根据用户请求和现有上下文，明确：

- **方案依据**：本次使用哪些内容作为依据。用户指定资料时，以其指定的资料和范围为准。
- **方案目标**：用户希望解决什么问题、实现什么结果，以及已经明确的范围和约束。
- **目标项目**：方案属于哪个项目，需要结合哪个代码库或项目背景。

这些信息已明确时直接使用；无法确定时，只针对影响方案的缺口向用户确认。

指定资料无法读取或缺少必要内容时，说明具体问题并请用户补充。多个来源存在影响方案的矛盾、且无法确定采用哪个时，向用户确认。

## 已确认设计要点

**设计要点应同时涵盖用户自行提出或设计、最终未被否定或替代的内容，以及经过讨论后最终确定的设计内容。发生调整的部分，以讨论后的最终版本为准。**

根据本次方案依据，在生成 Spec 前整理当前仍有效的设计要求和关键决策，遵循以下规则：

- 回看用户的设计及后续讨论，保留仍有效的内容；后续未再提及，不视为放弃。用户明确标为待讨论的设想和未经用户确认的模型建议，作为未决内容处理；无法确定且会影响方案的内容，向用户澄清。
- 在 Spec 中设置独立的“已确认设计要点”章节，使用 `D-01`、`D-02` 等编号逐条记录，每条表达一个可判断是否满足的约定；必要时简述原因。按实际内容拆分，不规定数量。
- 在该章节写明，方案、Tickets 和实现均需遵守这些要点，变更需先取得用户确认。将要点纳入发布前自检，已明确确认的内容无需额外重复确认。
- 需要修改、撤销或偏离某条要点时，说明涉及的编号、原约定、拟议变化、原因和影响。取得用户对变更的明确同意后，先更新 Spec 和已有的相关 Tickets，再继续；已有明确授权覆盖该变化时，无需重复确认。

## 前置条件

- 从当前宿主针对目标项目的完整 Skills 登记信息中，按精确名称确认 `to-spec` 和 `to-tickets` 已启用，并核对实际入口可读取，记录入口位置。前置检查仅核对登记信息和入口可读取性，不加载 Skill 正文。
- 目标项目的 issue tracker、发布位置和 triage 标签约定已提供。复用现有约定；缺失时报告缺口，并提示用户先运行 `$setup-matt-pocock-skills` 完成配置。

优先使用宿主已有的完整登记查询能力。Codex 没有直接查询工具时，使用 Python 3 调用本 Skill 的[登记查询脚本](scripts/list-skills.py)，传入 `--cwd '/目标项目的实际绝对目录'`；脚本路径使用当前已加载 Skill 中的实际绝对路径。其他宿主使用自身提供的完整查询能力。查询结果至少包含每项的名称、实际入口和启用状态。初始 Available Skills 名单不作为完整登记信息；关闭隐式调用不视为禁用。

查询必须成功且完整。登记中不存在的依赖，提示用户从 [Matt 官方 Skills 仓库](https://github.com/mattpocock/skills) 安装；已登记但禁用的依赖，提示启用。入口无法读取、同名多入口且无法确定采用哪个，或查询失败时，说明具体问题并暂停依赖该 Skill 的工作，按意外中断规则处理。安装、启用状态或入口发生变化后，重新查询。

输入明确且前置条件满足后，进入执行流程。

# 本地文本写入

遵守目标项目的文件写入约定，优先使用宿主文件编辑工具。使用 Python 写入文本时，在源码前两行声明 `# coding: utf-8`，文件读写显式指定 `encoding="utf-8"`。长文正文使用多行文本或独立数据输入，避免嵌成超长单行源码。交给新对话或子 Agent 执行时，传递本节要求。

# 执行流程

## 1. 确定工作区

检查当前对话是否已有属于目标项目的独立 Worktree。复用前，核对 Worktree 的实际仓库、分支和代码基线是否符合本次任务要求，并确认已有工作归属及是否存在其他写入者。

适合本次任务时复用，保留已有修改；不适合时选择其他合适的独立 Worktree。没有合适的独立 Worktree 时，创建一个。

将选定的 Worktree 作为后续工作的工作目录。无法确定归属或协调写入，或无法确定或创建工作区时，说明具体问题并向用户询问。

## 2. 选择执行方式并执行

先确认当前环境是否具备本流程所需的子 Agent 协作能力，包括：

- 在当前主对话下创建子 Agent，并提交首条消息。
- 主对话与该子 Agent 双向通信。
- 主对话等待并接收该子 Agent 的阶段确认、完成或中断消息。

不具备上述完整能力时，由主对话执行。

具备上述完整能力时，根据方案所需的信息判断：

- 当前对话中有大量与方案相关、需要梳理和提炼的信息时，由主对话执行，利用当前已经积累的上下文。
- 所需资料基本集中在用户指定的文件或其他明确资料中时，准备资料引用和必要的初始信息，使用子 Agent 执行。
- 所需信息主要在对话中，但数量较少、能够快速完整提取时，先整理完整的初始信息，再使用子 Agent 执行。
- 具备上述完整能力，但不满足上述子 Agent 适用条件时，由主对话执行。

确定执行方式后：

- 主对话执行：读取[主对话执行说明](references/main-execution.md)，在选定的 Worktree 中执行。
- 子 Agent 执行：读取[子 Agent 执行说明](references/subagent-execution.md)，按该说明启动子 Agent。主对话等待其执行结果。

仅读取所选分支的执行说明。执行完成后，进入结果验收。

## 3. 处理执行结果

### 任务完成

按照[结果与完成条件](#结果与完成条件)验收实际产物。

验收通过后，进入收尾与交接。验收未通过时，指出问题，按对应执行说明修订后重新验收。

### 意外中断

暂停后续流程，根据已有执行信息总结中断原因、已完成内容和未完成事项。

向用户报告情况，并给出针对性的处理建议，由用户决定如何继续。无法确认中断原因时，如实说明不确定之处。

用户决定继续后，先核对已有产物和实际执行状态，仅继续尚未完成的工作。创建或发布结果不明确时，先核实原操作，核实前暂停重复执行；无法核实时，说明已知状态及缺失的信息，保持相关操作暂停。

## 4. 收尾与交接

验收通过后，使用 Python 3 调用[结果报告脚本](scripts/render-result.py)。脚本路径使用当前已加载 Skill 中的实际绝对路径。

调用示例，替换为本次任务的实际参数值：

```sh
python3 '/Skill绝对路径/scripts/render-result.py' \
  --summary '本次方案摘要' \
  --artifacts '[{"name":"Spec","location":"/项目绝对路径/spec.md"}]' \
  --started-at '2026-10-10T09:00:00+08:00' \
  --continuous-mode false \
  --implementation-skill-available true
```

| 参数 | 内容 |
| --- | --- |
| `--summary` | 本次方案摘要；未拆分 Tickets 时，包含未拆分的原因。 |
| `--artifacts` | 根据验收通过的实际成果填写非空 JSON 数组，包含 Spec 和本次需要的 Tickets。每项仅包含 `name` 和 `location`，分别填写成果名称及实际绝对文件路径或 HTTP(S) 链接，两者均为非空单行文本。 |
| `--started-at` | 进入本 Skill 时记录的开始时间。 |
| `--continuous-mode` | 根据本次任务最新的用户要求判断。已明确要求连续模式且没有撤销或缩小该要求时为 `true`，否则为 `false`。 |
| `--implementation-skill-available` | 根据收尾时针对目标项目的完整登记信息判断：`guided-implementation` 已启用且入口可读取时为 `true`，已确认无法使用时为 `false`。仅核对登记信息和入口可读取性，不加载正文。查询失败或无法确定采用哪个入口时，按意外中断规则处理，保留已完成成果，不将查询失败当成依赖缺失。 |

将脚本标准输出中的 Markdown 原样展示给用户，根据报告中的交接提示执行：

- 报告提示直接进入 3实现 时，立即调用名为 `guided-implementation` 的 Skill。
- 报告询问用户时，等待用户回复。用户明确同意进入 3实现 时，调用 `guided-implementation`；用户明确要求开启连续模式时，记录该要求后调用 `guided-implementation`。仅同意进入 3实现 不视为开启连续模式。
- 报告提示当前无法使用 `guided-implementation` 时，暂停交接，等待用户检查其安装、启用状态及入口。

调用 `guided-implementation` 时，从已核实的实际入口读取其完整正文，将以下内容作为本次实现的输入传达：

- 验收通过的最终 Spec 和 Tickets 的实际路径或链接；未拆分 Tickets 时，提供已确认的不拆分原因。
- 目标项目及本次选定 Worktree 的实际绝对路径，供 3实现核对并复用。
- Spec 中已确认设计要点和测试约定的位置，可以使用资料引用。
- 实现目标、范围、约束及用户仍有效的执行要求，包括是否开启连续模式。已记录在 Spec 中的内容可以直接引用。

脚本执行失败时，按照 [SKILL.md 中“意外中断”的处理要求](#意外中断)处理。

# 结果与完成条件

## 验收标准

验收时读取最终实际产物，核对其完整性及与已确认内容的一致性。

执行过程中已经确认或审查通过、且最终内容未发生变化的部分，可以复用原结论；发现变更、遗漏或不一致时，重新审查受影响的部分。

- Spec 及需要拆分时的 Tickets 已生成，实际产物存在且能够读取，格式、标签和发布位置符合项目约定及对应 Matt Skill 的要求。
- 方案覆盖用户要求的目标，并遵守已明确的范围、约束和决策。
- Spec 包含独立的“已确认设计要点”章节及变更确认要求；对照本次方案依据，清单完整、准确地保留了当前有效的设计要求和关键决策。
- 逐项核对方案对设计要点的落实情况；存在遗漏或未经用户确认的冲突时，验收不通过。
- Spec 中的主要实现决策足以指导实现：本次涉及的职责与接口约定，以及会影响结果的关键分支、状态转换和失败恢复规则，已经明确。关键验收条件有对应的、可观察的验证方式，没有遗漏影响方案成立的关键问题。与本次任务无关的维度无需补充。
- 已拆分 Tickets 时，Tickets 与 Spec 一致，符合 `to-tickets` 的切分规则；每个 Ticket 已记录适用的设计要点或明确引用其编号和 Spec 位置，交付结果和验收条件能够对应 Spec 的要求，整组 Tickets 覆盖本次必要的交付内容，阻塞关系清楚、有效。未拆分时，理由与任务规模相符。
- 主对话执行时，`to-spec` 原流程中要求的用户确认已经完成；Tickets 的粒度、依赖及合并拆分判断已由主对话按预先授权完成。
- 子 Agent 执行时，原流程中需要确认的事项及 Spec、必要的 Tickets 阶段产物，已由主 Agent 确认。

## 完成条件

所需产物齐全、验收通过，且没有影响本次方案交付的未解决事项时，本阶段完成。

产物缺失或验收未通过时，按照[任务完成分支](#任务完成)修订后重新验收；执行中断时，按照[意外中断分支](#意外中断)处理。
