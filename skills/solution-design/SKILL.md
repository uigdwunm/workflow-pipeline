本 Skill 编排 Matt 系列的 `to-spec` 和 `to-tickets`。Spec 和 Tickets 的内容与生成规则以对应 Skill 为准，本 Skill 补充已确认设计要点及任务依赖的记录和核对要求。

本 Skill 默认连续接续 3实现。用户明确限定执行范围时，在指定阶段结束；仅调用本 Skill 不视为只执行本阶段。进入时简要说明执行范围。

执行范围以用户明确要求为依据；“先讨论”等顺序表述不视为阶段限制，确认问题中也不得自行加入停止条件。

首次进入本阶段时取得包含时区的 ISO 8601 开始时间，写入任务进度文件；接续时沿用本轮记录，供收尾脚本计算耗时。

# 输入与前置条件

## 输入

接受当前对话中已讨论的内容，也接受用户指定的文件、issue、链接或其他资料。

根据用户请求和现有上下文，明确：

- **方案依据**：本次使用哪些内容作为依据。用户指定资料时，以其指定的资料和范围为准。
- **方案目标**：用户希望解决什么问题、实现什么结果，以及已经明确的范围和约束。
- **目标项目**：方案属于哪个项目，需要结合哪个代码库或项目背景。

这些信息已明确时直接使用；无法确定时，只针对影响方案的缺口向用户确认。

目标项目和本次任务明确后，先按[任务进度](#任务进度)创建或复用进度文件，再继续前置检查。已有交接时接收同一进度文件的绝对路径、任务标识和原目标项目的绝对路径。

指定资料无法读取或缺少必要内容时，说明具体问题并请用户补充。多个来源存在影响方案的矛盾、且无法确定采用哪个时，向用户确认。

## 已确认设计要点

**设计要点应同时涵盖用户自行提出或设计、最终未被否定或替代的内容，以及经过讨论后最终确定的设计内容。发生调整的部分，以讨论后的最终版本为准。**

根据本次方案依据，在生成 Spec 前整理当前仍有效的设计要求和关键决策，遵循以下规则：

- 回看用户的设计及后续讨论，保留原始目标、明确排除项及仍有效的范围、约束和决策；后续未再提及，不视为放弃。用户明确标为待讨论的设想和未经用户确认的模型建议或推断，作为未决内容处理；无法确定且会影响方案的内容，向用户澄清。
- 在 Spec 中设置独立的“已确认设计要点”章节，使用 `D-01`、`D-02` 等编号逐条记录，每条表达一个可判断是否满足的约定；必要时简述原因。按实际内容拆分，不规定数量。
- 在该章节写明，方案、Tickets 和实现均需遵守这些要点，变更按[设计边界与变更](#设计边界与变更)处理。将要点纳入发布前自检，已明确确认的内容无需额外重复确认。

## 用户答复与待决事项

用户答复应与具体待决事项对应，只将其实际明确决定的内容记为已确认，其余保持未决，推荐项不自动生效。结合上下文判断“可以”“继续”等简短答复；存在影响结果的歧义时，只澄清对应事项，再继续依赖该决定的工作，保留其他已确认内容。

## 设计边界与变更

制定满足当前已确认需求的最小完整方案。新增复杂度应有明确的需求依据，避免为尚未确认的未来需求增加额外抽象、通用框架或扩展机制。

以用户已确认的要求和方案为参照。额外改造是为完成原任务，增加其中未包含的改造工作，或改变已约定的职责、行为、接口、数据规则、失败恢复方式及成本取舍。既定范围内的实现选择，以及修正本次实现或合并遗漏以恢复已确认行为，可自行处理。

新增额外改造或改变已确认设计前，先说明原因、范围和影响，取得用户确认；只有用户明确授予此类变化的自主决定权时，才可自行处理。无法确定是否超出范围时，先说明具体变化并确认。任务必要性、测试失败和审查建议不代替这种授权；用户确认仅覆盖当次说明的事项，测试范围或验收方式的确认不代替设计变更确认。

修改、撤销或偏离已确认设计要点时，一并说明对应编号和原约定。取得用户确认或依据其明确授予的自主决定权作出决定后，更新 Spec 和已有的相关 Tickets，记录用户确认或自主决定权的原话或可定位来源，再发布为实施依据；已确认的同一变化无需重复询问。

发现已做出的额外改造缺少上述用户依据时，主动说明实际变化，暂停相关发布和交付，按用户决定保留或撤回，继续不依赖该决定的工作。

## 测试范围的承接与细化

生成 Spec 前，从方案依据中接收适用的测试范围结论、用户确认依据及未决事项。1拷问或此前讨论中已明确确认、且仍适用于当前任务的测试边界，直接作为 `to-spec` 测试边界确认环节的已完成输入，写入 Spec 的测试与验收约定。

在该边界内自行细化模块划分、具体用例和工具选择。只有本任务确实需要明确测试范围，且缺少必要的用户决定，或方案中新发现的问题要求实质改变已确认边界时，才说明具体缺口或变化、原因及影响，向用户补充确认受影响的部分。直接进入本阶段的任务也按此规则处理；无需明确测试范围的任务跳过该项询问。涉及已确认设计要点的变更时，沿用其变更规则。

## Tickets 依赖与并行机会

结合实际工作量和耦合程度，按独立交付、验收或并行收益决定是否拆分。适合一次连贯完成的工作保持单一实现单元；已有 Spec 不自动要求拆票。简要记录判断依据，已有分析直接复用。

需要拆分 Tickets 时，在 `to-tickets` 的切分规则内检查：

- 每条阻塞关系在相关 Ticket 中说明所需的具体前置产物，区分必须等待的依赖、实施顺序偏好和共享文件的合并风险。
- 对关键前置任务，核对下游需要的是整个交付结果还是其中一项可独立验收的产物；能独立实现和验收的部分可拆分并行，紧密耦合的工作保持连贯，不为凑并发数量拆分。
- 记录可并行的任务及已知共享文件或接口的协调需求。没有可并行任务时，保留有产物依据的依赖链。

上述判断随 Tickets 草案一起生成、核对和交接，遵守已确认的 Spec 和设计变更边界。

## 前置条件

- 从当前宿主针对目标项目的完整 Skills 登记信息中，按精确名称确认 `to-spec` 和 `to-tickets` 已启用，并核对实际入口可读取，记录入口位置。前置检查仅核对登记信息和入口可读取性，不加载 Skill 正文。
- 目标项目的 issue tracker、发布位置和 triage 标签约定已提供。复用现有约定；缺失时报告缺口，并提示用户先运行 `$setup-matt-pocock-skills` 完成配置。

优先使用宿主已有的完整登记查询能力。Codex 没有直接查询工具时，使用 Python 3 调用本 Skill 的[登记查询脚本](scripts/list-skills.py)，传入 `--cwd '/目标项目的实际绝对目录'`，按本次需核实的名称重复传入 `--name`，例如 `--name to-spec --name to-tickets`；脚本路径使用当前已加载 Skill 中的实际绝对路径。其他宿主使用自身提供的完整查询能力。查询结果至少包含每项的名称、实际入口和启用状态。初始 Available Skills 名单不作为完整登记信息；关闭隐式调用不视为禁用。

脚本仍查询和校验完整登记，仅筛选输出；同名多入口全部保留，`missing` 列出未登记名称。`ok: true` 只表示查询成功，仍须核对缺失项、启用状态及入口可读取性。省略 `--name` 时输出完整名单。

查询必须成功且完整。登记中不存在的依赖，提示用户从 [Matt 官方 Skills 仓库](https://github.com/mattpocock/skills) 安装；已登记但禁用的依赖，提示启用。入口无法读取、同名多入口且无法确定采用哪个，或查询失败时，说明具体问题并暂停依赖该 Skill 的工作，按意外中断规则处理。安装、启用状态或入口发生变化后，重新查询。

输入明确且前置条件满足后，进入执行流程。

# 本地文本写入

遵守目标项目的文件写入约定，优先使用宿主文件编辑工具。使用 Python 写入文本时，在源码前两行声明 `# coding: utf-8`，文件读写显式指定 `encoding="utf-8"`。长文正文使用多行文本或独立数据输入，避免嵌成超长单行源码。交给新对话或子 Agent 执行时，传递本节要求。

# 任务进度

在阶段切换、主要任务完成或较长执行期间，由主对话适时用一两句话说明当前阶段或任务、已完成内容和剩余工作。有 Tickets 时沿用编号及完成数量，并行时说明各任务状态；返工或计划调整时说明进度变化。复用已有状态，避免为汇报额外统计或频繁查询；对话说明不另行登记进度，大步骤仍按下文记录。

执行范围随同一进度记录交接和恢复。首次 `create` 默认执行至 3实现及收尾；用户明确限定本阶段结束时，增加 `--end-stage 2 --scope-reply '用户原话' --scope-source '可定位的用户消息来源'`。创建回执和 `show` 均返回 `execution_scope`。

用户明确修改范围时，用 `set-scope --end-stage '新的结束阶段' --scope-reply '用户新指令原话' --scope-source '可定位来源'` 更新，传入同一进度身份。主对话核对原话确实限定或修改了范围；普通设计确认、等待答复及入口受阻不修改执行范围。

使用本 Skill 的[进度脚本](scripts/task-progress.py)，由主对话维护本任务唯一的临时 Markdown 文件。只记录以下大步骤的完成结果，步骤名称由脚本内置：

| 序号 | 大步骤 |
| --- | --- |
| 1 | 确定工作区 |
| 2 | 生成方案 |
| 3 | 验收成果 |
| 4 | 报告与交接 |

创建前，区分原目标项目与本次执行工作区。优先沿用已有交接中的原目标项目；首次进入时，根据用户指定的项目及已知仓库关系核实，不直接将当前 `cwd` 或临时 Worktree 作为原目标项目。用户明确指定 Worktree 为目标项目时遵从其要求。执行工作区变化不改变已确定的任务归属。

首次进入体系时，遵守目标项目的写入约定，选择用户指定或项目约定的位置；没有约定时，使用宿主现有临时目录中的唯一文件路径。文件位于临时 Worktree 之外，父目录须已存在。用一次 `create` 创建文件并保存本阶段开始时间：

```sh
python3 '/Skill绝对路径/scripts/task-progress.py' create \
  --output '/本任务进度文件绝对路径' \
  --project '/原目标项目绝对路径' \
  --summary '本任务原始要解决的问题和目标' \
  --stage 2 --at '进入本阶段时取得的含时区ISO时间'
```

保存返回的 `file`、`task_id`、`project` 和本轮 `started_at`。已有交接时，沿用同一文件，用 `show` 核对归属和实际成果，再用 `enter --stage 2` 进入或复用本阶段；首次追加时用 `--at` 传入本阶段实际开始时间，接续时复用原时间。后续命令均传入同一组 `--file`、`--task-id` 和 `--project`。接续文件缺失、损坏或归属不明时，先核实并保留已有信息，不能另建文件替代。

使用 `complete --steps` 登记已完成的大步骤，参数为非空 JSON 列表；单步也使用一个元素的列表。每项包含整数 `step` 和单行 `note`，可选含时区的 ISO 8601 时间 `at`；必要的成果位置写入 `note`：

```sh
python3 '/Skill绝对路径/scripts/task-progress.py' complete \
  --file '/本任务进度文件绝对路径' \
  --task-id '创建时返回的任务标识' \
  --project '/原目标项目绝对路径' \
  --stage 2 --steps '[{"step":1,"note":"本大步骤的实际完成结果"}]'
```

未提供 `at` 的列表项统一使用本次登记时间；已有可靠事件时间时填入该项的 `at`。列表中的步骤须连续递增，不能重复、乱序或跳过未完成步骤。整批校验通过后一次写入，任一项失败则原记录不变。最后一个大步骤完成时自动结束阶段。更新只返回简短回执；恢复任务或生成报告需要完整记录时才用 `show`。同一结果重试保留首次时间；已完成的步骤保持原记录，必要返工在当前未完成大步骤的最终结果中简述。

默认完成一步即登记；连续完成的简短步骤可合并为一次列表登记。遇到等待、中断或较长执行前，先保存已完成进度，不为凑批次延迟记录。依赖已登记进度的操作仍按顺序执行；先登记报告所需的前序步骤，再生成报告，成功后登记最后一步。

普通确认、等待和中断不更新文件；恢复时核对实际成果，从尚未完成的大步骤接续，沿用本轮开始时间。阶段用时按起止时间计算，包含阶段内等待，不包含阶段间等待。后续阶段传递同一进度身份及必要成果信息；执行工作区变化不改变原目标项目。

确实重新执行已结束阶段时用 `enter --new-run` 追加一轮。明确取消当前阶段或改走其他阶段时，用 `stop --stage 2 --note '具体原因'` 保留已完成记录并结束本轮；暂停和等待不使用 `stop`。整个任务明确结束且结果报告已保留后，按项目清理授权调用 `cleanup --task-finished`。等待接续时保留文件。

# 执行流程

## 1. 确定工作区

先区分用户常用工作区与任务 Worktree。常用工作区默认是原目标项目目录，用户已指定其他位置时使用指定路径。核对其实际路径和检出分支，在后续交接中保留。该目录的分支和编辑器项目位置由用户控制；除用户明确要求外，不替用户切分支、进入 detached 状态、检出未交付候选，或将编辑器项目切到任务 Worktree。用户自行切换后保持其选择，不自动恢复旧状态。

检查当前对话是否已有属于目标项目的独立 Worktree。复用前，核对 Worktree 的实际仓库、分支和代码基线是否符合本次任务要求，并确认已有工作归属及是否存在其他写入者。

适合本次任务时复用，保留已有修改；不适合时选择其他合适的独立 Worktree。没有合适的独立 Worktree 时，创建一个。

在选定 Worktree 中开展后续工作前，核对本次已有文档成果，包括术语表、ADR 和讨论文档的实际位置，以及相关改动是否已包含在该 Worktree 中。

- 需要随本次任务交付的仓库文档，已有内容可直接复用；尚未包含的本次相关改动，包括未提交修改和新文件，按任务范围带入选定 Worktree。保留来源工作区的已有内容，不整仓复制或混入其他任务的修改。
- 目标 Worktree 已有不同修改时，核对双方内容并处理冲突，保留仍有效的修改；归属或取舍无法确定时，暂停相关迁移并向用户确认，不直接覆盖。
- 核对本次文档成果已完整包含后，将后续使用的资料路径更新为选定 Worktree 中的实际位置，记录这些文档属于本次提交和交付范围。外部链接或仅作参考的资料继续引用原位置。

将选定的 Worktree 作为后续工作的工作目录。无法确定归属或协调写入，或无法确定或创建工作区时，说明具体问题并向用户询问。

工作区和已有文档核对完成后，用 `complete --stage 2 --steps '[{"step": 1, "note": "本步骤的实际完成结果"}]'` 记录一句结果，包含常用工作区及其检出分支、实际任务 Worktree 和文档交付情况，传入同一进度身份，结果填入列表项的 `note`。

## 2. 选择执行方式并执行

先结合任务规模、已有上下文及独立产出或并行收益判断是否需要委派。主对话能够短小连贯完成时，直接选择下文的主对话执行分支。

需要委派时，再确认当前环境是否具备本流程所需的子 Agent 协作能力，包括：

- 在当前主对话下创建子 Agent，并提交首条消息。
- 主对话与该子 Agent 双向通信。
- 主对话等待并接收该子 Agent 的阶段确认、完成或中断消息。

不具备上述完整能力时，由主对话执行。

委派有明确收益且具备上述完整能力时，再根据方案所需的信息判断能否完整交接：

- 当前对话中有大量与方案相关、需要梳理和提炼的信息时，由主对话执行，利用当前已经积累的上下文。
- 所需资料基本集中在用户指定的文件或其他明确资料中时，准备资料引用和必要的初始信息，使用子 Agent 执行。
- 所需信息主要在对话中，但数量较少、能够快速完整提取时，先整理完整的初始信息，再使用子 Agent 执行。
- 具备上述完整能力，但不满足上述子 Agent 适用条件时，由主对话执行。

确定执行方式后：

- 主对话执行：读取[主对话执行说明](references/main-execution.md)，在选定的 Worktree 中执行。
- 子 Agent 执行：读取[子 Agent 执行说明](references/subagent-execution.md)，按该说明启动子 Agent。主对话等待其执行结果。

仅读取所选分支的执行说明。该分支执行完成并返回成果后，用 `complete --stage 2 --steps '[{"step": 2, "note": "本步骤的实际完成结果"}]'` 记录 Spec、必要的 Tickets 或不拆分原因，再进入结果验收。

## 3. 处理执行结果

### 任务完成

按照[验收标准](#验收标准)验收实际产物。阶段记录和报告在收尾中完成。

验收通过后，用 `complete --stage 2 --steps '[{"step": 3, "note": "本步骤的实际完成结果"}]'` 记录验收结论，再进入收尾与交接。验收未通过时，指出问题，交回原执行者修订后重新验收；必要返工在本大步骤完成时简述。

### 意外中断

发生执行异常时，先核对实际状态和已有操作结果。

能在已有授权和已确认的设计范围内恢复时，由当前执行者自行修复、完成必要验证并继续，无需等待主对话或用户确认；路径查找、命令参数和文本写入脚本等常规问题按此处理，重要修正及验证结果在进展或完成报告中汇总。同类问题重复出现时，先核对前次修复无效的原因，再继续修正。子 Agent 在现有条件下无法恢复时，向主对话报告，由主对话核实进展并安排接续。

主对话收到子 Agent 或其他对话的模型繁忙、容量不足等临时服务错误提示时，等待 30 秒后重试；仍出现同类错误时，再分别等待 60 秒、120 秒重试。最多重试 3 次；仍未恢复时，暂停相关接续，按现有中断规则向用户报告。

需要用户作出新的决定、补充授权，或无法核实已有操作结果时，暂停受影响的工作，向用户说明问题、已完成内容、未完成事项及继续所需的信息或决定。等待期间，可以继续不依赖该决定的工作。

用户另有明确的停工或报告要求时，按用户要求执行。

用户决定继续后，先核对已有产物和实际执行状态，仅继续尚未完成的工作。创建或发布结果不明确时，先核实原操作，核实前暂停重复执行；无法核实时，说明已知状态及缺失的信息，保持相关操作暂停。

中断恢复时用 `show` 核对同一进度文件和实际成果，仅继续未完成的大步骤，保留原开始时间。

## 4. 收尾与交接

下一步建议始终为进入 3实现，不受执行范围、连续模式或后续 Skill 可用状态影响。

验收通过后，使用 Python 3 调用[结果报告脚本](scripts/render-result.py)。脚本路径使用当前已加载 Skill 中的实际绝对路径。

调用示例，替换为本次任务的实际参数值：

```sh
python3 '/Skill绝对路径/scripts/render-result.py' \
  --file '/本任务进度文件绝对路径' \
  --task-id '本任务标识' \
  --project '/原目标项目绝对路径' \
  --summary '本次方案摘要' \
  --artifacts '[{"name":"Spec","location":"/项目绝对路径/spec.md"}]' \
  --implementation-skill-available true
```

| 参数 | 内容 |
| --- | --- |
| `--summary` | 本次方案摘要；未拆分 Tickets 时，包含未拆分的原因。 |
| `--artifacts` | 根据验收通过的实际成果填写非空 JSON 数组，包含 Spec 和本次需要的 Tickets。每项仅包含 `name` 和 `location`，分别填写成果名称及实际绝对文件路径或 HTTP(S) 链接，两者均为非空单行文本。 |
| `--file`、`--task-id`、`--project` | 同一进度身份；报告从当前 2方案记录读取开始时间和执行范围，须先完成前三步。 |
| `--at` | 可选的实际报告生成完成时间，须有时区，默认由脚本取得。 |
| `--implementation-skill-available` | 用户限定本阶段结束时传 `unknown`，无需核实后续入口。需要接续时，根据收尾时针对目标项目的完整登记信息判断：`guided-implementation` 已启用且入口可读取时为 `true`，已确认不存在、已禁用或入口无法读取时为 `false`，查询失败或无法确定采用哪个入口时为 `unknown`。仅核对登记信息和入口可读取性，不加载正文。需要接续且为 `unknown` 时说明具体问题，照常报告已验收成果，仅暂停对应交接。 |

连续模式用于自动衔接后续阶段；各阶段内部的设计确认、授权和验收仍按原规则执行。用户限定本阶段结束时，报告保留下一步建议并说明本次执行结束，展示后结束，不再询问是否进入 3实现。

报告脚本成功返回后保留完整标准输出，以实际报告生成完成时刻调用 `complete --stage 2 --steps '[{"step": 4, "note": "方案报告已生成，交接资料已准备", "at": "实际报告生成完成时刻的含时区ISO时间"}]'`，传入同一进度身份。脚本自动结束阶段；收到成功回执后按下文展示报告，再处理交接。写入失败时保留报告和原文件，核实后补齐记录再交接。

先将脚本标准输出中的 Markdown 原样、完整、展开地展示给用户。连续模式且可直接进入 3实现 时，使用可继续执行的进度消息；用户限定本阶段结束、需要等待用户决定或交接受阻时，使用最终回复展示报告。展示后根据报告中的交接提示执行：

- 报告提示直接进入 3实现 时，报告展示后立即调用名为 `guided-implementation` 的 Skill。
- 报告提示本次在 2方案 结束时，展示报告后结束本次执行。
- 报告提示当前无法使用 `guided-implementation` 时，暂停交接，等待用户检查其安装、启用状态及入口。
- 报告提示可用情况尚未核实时，先重新核实，再按对应可用状态处理。核实可用后，在用户仍有效的执行范围内继续；仍无法核实时，保持交接暂停并说明具体问题。

调用 `guided-implementation` 时，从已核实的实际入口读取其完整正文，将以下内容作为本次实现的输入传达：

- 验收通过的最终 Spec 和 Tickets 的实际路径或链接；未拆分 Tickets 时，提供已确认的不拆分原因。
- 原目标项目、用户常用工作区及其已核实的检出状态、本次选定 Worktree 的实际绝对路径，以及保护用户分支和编辑器项目选择的要求，供 3实现核对并复用。
- 需要随本次任务提交和交付的已有文档成果及其在选定 Worktree 中的实际位置。
- Spec 中已确认设计要点和测试约定的位置，可以使用资料引用。
- 实现目标、范围、约束及用户仍有效的执行要求，包括用户对后续阶段的限制。已记录在 Spec 中的内容可以直接引用。
- 同一进度文件的绝对路径、任务标识和原目标项目的绝对路径，供下一阶段核对归属并沿用。

脚本执行失败时，按照 [SKILL.md 中“意外中断”的处理要求](#意外中断)处理。

# 结果与完成条件

## 验收标准

验收时读取最终实际产物，核对其完整性及与已确认内容的一致性。

执行过程中已经确认或审查通过、且最终内容未发生变化的部分，可以复用原结论；发现变更、遗漏或不一致时，重新审查受影响的部分。

- Spec 及需要拆分时的 Tickets 已生成，实际产物存在且能够读取，格式、标签和发布位置符合项目约定及对应 Matt Skill 的要求。
- 方案覆盖用户要求的目标，并遵守已明确的范围、约束和决策。
- Spec 包含独立的“已确认设计要点”章节及变更确认要求；对照本次方案依据，清单完整、准确地保留了当前有效的设计要求和关键决策。
- 对照用户原始资料及后续明确确认的变更，核对整个 Spec 中的目标、范围、排除项和重要约束，既检查原要求是否完整落实，也检查新增内容是否有依据，并按[设计边界与变更](#设计边界与变更)核对授权；不能仅凭已整理的设计要点清单判断一致性。存在遗漏、冲突或未经授权的扩展时，验收不通过。
- Spec 中的主要实现决策足以指导实现：本次涉及的职责与接口约定，以及会影响结果的关键分支、状态转换和失败恢复规则，已经明确。关键验收条件有对应的、可观察的验证方式，没有遗漏影响方案成立的关键问题。与本次任务无关的维度无需补充。
- Spec 中适用的测试与验收约定遵守已确认的测试边界；按[测试范围的承接与细化](#测试范围的承接与细化)复用既有确认，必要的补充或变更确认已有依据。
- 已拆分 Tickets 时，Tickets 与 Spec 一致，符合 `to-tickets` 的切分规则；每个 Ticket 已记录适用的设计要点或明确引用其编号和 Spec 位置，交付结果和验收条件能够对应 Spec 的要求，整组 Tickets 覆盖本次必要的交付内容，并通过[依赖与并行机会检查](#tickets-依赖与并行机会)。未拆分时，理由与任务规模相符。
- 主对话执行时，`to-spec` 原流程中要求的用户确认已经完成；Tickets 的粒度、依赖及合并拆分判断已由主对话按预先授权完成。
- 子 Agent 执行时，原流程中需要确认的事项及 Spec、必要的 Tickets 阶段产物，已由主 Agent 确认。

## 完成条件

所需产物齐全、验收通过，且没有影响本次方案交付的未解决事项时，本阶段完成。

大步骤结果及阶段起止时间已写入同一进度文件，完整报告已按[收尾与交接](#4-收尾与交接)展示给用户，后续接续所需的进度身份已准备好。

产物缺失或验收未通过时，按照[任务完成分支](#任务完成)修订后重新验收；执行中断时，按照[意外中断分支](#意外中断)处理。
