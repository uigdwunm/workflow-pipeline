# 1. 生成 Spec

在 [SKILL.md 的“确定工作区”步骤](../SKILL.md)已确定的 Worktree 中，调用名为 `to-spec` 的 Skill，按其原流程执行。

使用已明确的方案依据，以及用户已确认的目标、范围、约束和关键设计决策，作为本次 Spec 的生成依据。

生成 Spec 时，遵循以下要求：

- 制定满足当前已确认需求的最小完整方案。新增复杂度应有明确的需求依据，避免为尚未确认的未来需求增加额外抽象、通用框架或扩展机制。
- 在已确认的设计基线内，不影响目标、功能范围、对外行为、约束和关键设计决策的实现细节调整，可以自行决定，无需额外向用户确认。
- 如果需要改变或扩展上述基线，且用户尚未明确授权对应变更，暂停后续流程，按照 [SKILL.md 中“意外中断”的处理要求](../SKILL.md#意外中断)，向用户说明触发原因、拟修改内容及影响，取得用户确认后再继续。

需求范围或方案方向中存在影响 Spec 成立的关键未决事项时，同样按照上述意外中断要求处理。`to-spec` 原流程中的测试边界讨论与确认正常进行。

执行完成后，记录已发布 Spec 的实际文件路径或 tracker 链接，供后续验收和结果报告使用。

`to-spec` 执行完成后，进入 Tickets 拆分判断。执行中需要用户确认时，在当前对话中完成确认后继续。

# 2. 判断是否拆分 Tickets

根据已生成的 Spec，结合工作量、是否包含需要分别交付和验收的部分，以及实施依赖关系进行判断。

通常需要拆分 Tickets。只有非常简单、能够通过一次短小且连贯的实现完成的小任务，才可以省略。

- 需要拆分时，进入下一步。
- 无需拆分时，记录原因，直接进入结束处理。

# 3. 生成 Tickets

以刚刚生成的 Spec 为依据，调用名为 `to-tickets` 的 Skill，执行 Tickets 的拆分和发布。

用户已授权主对话自行判断 Tickets 的粒度、阻塞关系，以及是否需要合并或进一步拆分。

在符合 `to-tickets` 原有切分规则的前提下，优先采用较细粒度。每个 Ticket 应有明确的交付结果，避免为了缩小粒度而拆出无法独立验证的零碎工作。

主对话根据 Spec 检查并调整拆分结果，自行确定真正必要的依赖关系，完成判断后继续发布，无需再针对上述三项向用户确认。拆分仍以已确认的 Spec 为依据。

Tickets 生成完成后，进入结束处理。

# 4. 结束或中断执行

- **正常完成**：Spec 和必要的 Tickets 已生成，按照 [SKILL.md 中“任务完成”的处理要求](../SKILL.md#任务完成)验收实际产物。
- **意外中断**：上述任一步骤发生意外时，暂停执行，按照 [SKILL.md 中“意外中断”的处理要求](../SKILL.md#意外中断)处理。
