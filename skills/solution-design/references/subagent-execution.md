本说明由主 Agent 执行，负责子 Agent 的启动和协作。

# 1. 确定模型与强度

用户或其他适用提示词已规定模型、推理强度或选择规则时，按相应要求执行。

通过当前宿主已有的工具说明、查询能力、配置或会话信息，获取当前对话设置、用户默认设置，以及可用于子 Agent 的模型和各模型支持的推理强度。

## 选择并读取偏好规则

已收到本次选定偏好文件的路径时，完整读取并沿用该文件，不重新选择偏好来源。否则，检查当前运行环境中用户主目录下的 `~/.config/workflow-pipeline/subagent-models.md`：

- 该路径存在时，完整读取该文件，作为本次子 Agent 选型的偏好规则。
- 只有确认该路径不存在时，才完整读取[内置默认偏好](../../../preferences/subagent-models.md)。

每次选型只使用上述选定的一份偏好规则。根据文件中的自然语言说明，结合实际任务和宿主支持的模型、推理强度确定配置。

选定文件无法读取，或文件内容存在任何问题时，说明具体问题并询问用户，等待用户回复后继续；不改读另一份偏好规则。

向需要继续创建子 Agent 的执行者，传入本次已选定偏好文件的实际绝对路径。下级执行者直接读取并沿用该文件，不重新选择偏好来源；根据自己交付的子任务确定模型和推理强度。文件无法读取或内容存在任何问题时，报告主对话，由主对话询问用户。

## 记录、应用与核实

在现有进度记录或创建前说明中，简要记录：任务难点、所选模型与强度、选择依据，以及是否使用继承。任务特征和配置相同的一批子 Agent，可以合并说明。

先确定所需模型和强度，再选择能够应用这些设置的创建方式。

宿主允许显式设置时，将所选模型和强度传入创建工具。完整历史继承模式不支持覆盖设置时，任务能够完整交接的，使用独立上下文创建，并传入必要背景、约束和资料。

任务确实依赖完整历史时，可以保留继承方式，但应说明该依赖，并确认继承配置能够满足任务需要。

创建后，由创建者通过工具回执或可查询的会话设置，核实所创建子 Agent 的实际模型与推理强度；仅发出了创建请求，不视为已经应用成功。被创建者无需重复核实自身设置；它继续创建下级子 Agent 时，承担相同的创建者责任。

无法确定可用设置、无法确认继承符合要求，或宿主无法应用要求的设置时，按照 [SKILL.md 中“意外中断”的处理要求](../SKILL.md#意外中断)处理。

# 2. 生成首轮提示词

根据 [SKILL.md 的“输入与前置条件”](../SKILL.md#输入与前置条件)中已经明确的内容，准备以下参数。

使用 Python 3 调用[首轮提示词生成脚本](../scripts/render-subagent-prompt.py)。调用时使用当前已加载 Skill 中该脚本的实际绝对路径。

| 参数 | 生成要求 |
| --- | --- |
| `--worktree` | 使用 [SKILL.md 的“确定工作区”步骤](../SKILL.md)已经选定的 Worktree 绝对路径，目录必须已存在。 |
| `--goal` | 根据用户请求，整理本次方案要解决的问题和预期结果。使用非空文本，保留已经明确的目标。 |
| `--context` | 整理子 Agent 执行所需的已确认背景、范围、约束、决策及项目约定，包括 issue tracker、发布位置和 triage 标签。按照 [SKILL.md 的“已确认设计要点”规则](../SKILL.md#已确认设计要点)，完整传递已整理的设计要点并保留编号，同时说明仍需澄清的内容。另列“执行信息”，包含主 Agent 针对目标项目查询并核实的 `to-spec` 和 `to-tickets` 实际入口，以及本次已选定偏好文件的实际绝对路径；这些信息与用户设计要点分开说明。将对话中必要的信息完整提取到此参数，使用非空文本，可分行描述。 |
| `--sources` | 列出本次需要参考的实际资料。使用 JSON 数组，每项仅包含 `name` 和 `location`，分别填写资料名称及绝对文件路径或 HTTP(S) 链接，两者均为非空单行文本。没有额外参考资料时传入空数组。 |
| `--notes` | 填写补充说明及同一进度文件的绝对路径、任务标识和原目标项目。说明进度由主对话维护，子 Agent 回传结果，不创建或更新进度文件。 |

保存脚本标准输出中的完整提示词，作为子 Agent 的首条消息。

`--context` 同时保留适用的测试范围结论、用户确认依据及未决事项，供子 Agent 按 [SKILL.md 的“测试范围的承接与细化”规则](../SKILL.md#测试范围的承接与细化)复用或补充。

子 Agent 使用主 Agent 传入的已核实入口。需要重新定位依赖时，将问题交回主 Agent，由其针对原目标项目重新查询并传递结果。

脚本执行失败时，按照 [SKILL.md 中“意外中断”的处理要求](../SKILL.md#意外中断)处理。

# 3. 启动并确认创建结果

使用当前宿主的原生子 Agent 工具，在当前主对话下创建子 Agent，使用已确定的模型和强度，将生成的提示词原样作为首条消息提交。

记录工具返回的子 Agent 标识，供后续检查、通信和继续执行使用。

“创建成功”必须同时满足：

- 子 Agent 已创建。
- 首条提示词已成功提交。

发起创建后，等待 30 秒检查状态：

- 创建成功：进入本执行说明的“等待并处理子 Agent 消息”。
- 明确创建失败，或状态不明、无法确认仍在正常启动：停止本次启动尝试，按照 [SKILL.md 中“意外中断”的处理要求](../SKILL.md#意外中断)处理。
- 能够确认仍在正常启动、只是较慢：再等待 60 秒，重新检查一次。创建成功时继续；失败或仍未创建成功时，停止本次启动尝试，按照上述意外中断要求处理。

检查时已收到阶段确认、完成或中断消息，直接进入“等待并处理子 Agent 消息”，处理对应消息。

# 4. 等待并处理子 Agent 消息

创建成功后，主对话停止主动推进方案，使用当前宿主的原生等待机制，等待该子 Agent 的确认请求、完成结果或中断报告。

收到消息后，先按[设计边界与变更](../SKILL.md#设计边界与变更)核对事项和授权。需要用户决定时，暂停受影响工作，取得决定后反馈给子 Agent，通知其按该规则更新相关产物再继续；已有授权内的事项和普通内部实现细节由主 Agent 判断。主 Agent 的代为确认不能替代必要的用户决定。

其余消息按照下面的消息类型处理。

## Spec 执行过程中的确认

根据子 Agent 提交的具体事项，结合方案目标、范围、约束和已有决策进行判断。

测试范围事项按[测试范围的承接与细化](../SKILL.md#测试范围的承接与细化)处理；已有确认覆盖时，将结论及依据反馈给子 Agent，直接继续。

向该子 Agent 明确回复确认结论或修改要求，通知其继续或修订，然后重新进入等待。

## Spec 产物确认

读取子 Agent 提交的实际 Spec，检查是否符合已明确的方案目标、范围、约束和决策。对照方案依据及传递给子 Agent 的设计要点，检查 Spec 中的清单是否完整、准确，并逐项核对方案是否落实这些要点。

按确认消息中的判断标准，决定是否需要拆分 Tickets。

向该子 Agent 明确回复：

- Spec 是否确认通过；未通过时说明具体修改要求。
- 是否需要拆分 Tickets；无需拆分时说明原因。
- 确认通过后，通知其继续。

回复后重新进入等待。

## Tickets 草案确认

读取实际草案，判断粒度、阻塞关系，以及是否需要合并或进一步拆分；核对每个 Ticket 的交付结果和验收条件与 Spec 要求的对应关系，确认相关设计要点已记录或明确引用且得到遵守，以及整组 Tickets 对本次必要交付内容的覆盖情况。

同时按 [Tickets 依赖与并行机会](../SKILL.md#tickets-依赖与并行机会)核对前置产物依据及并行安排。

上述判断由主 Agent 完成。

发现影响方案成立或 Tickets 切分的必要决策缺口时，通知子 Agent 暂停 Tickets 拆分，按本说明“等待并处理子 Agent 消息”中的规则核对授权并取得必要决定。将处理结论反馈给原子 Agent，通知其按首轮提示词“生成并确认 Spec”中的规则修订原 Spec、更新原产物，并重新提交 Spec 确认。确认通过后，通知其重新读取更新后的 Spec，再继续调整相关 Tickets。已确认框架内的普通实现细节，按前述设计边界自行判断。

需要调整时，向该子 Agent 说明具体修改要求；确认通过时，明确批准按当前草案发布。

回复后重新进入等待。

## 任务完成

收到子 Agent 的完成结果后，返回主流程登记“生成方案”完成，再按照 [SKILL.md 中“任务完成”的处理要求](../SKILL.md#任务完成)验收实际产物。

验收需要修订时，使用当前宿主支持的继续执行或追加任务能力，将具体问题交回该子 Agent。修订完成后重新验收。

## 意外中断

收到子 Agent 的中断报告后，按照 [SKILL.md 中“意外中断”的处理要求](../SKILL.md#意外中断)处理。

需要恢复执行时，先按照 [SKILL.md 中“意外中断”的处理要求](../SKILL.md#意外中断)核对已有产物和实际执行状态，再将处理结论、已核实的进展和剩余工作明确通知原子 Agent。尚未核实的操作应明确说明，保持相关操作暂停。
